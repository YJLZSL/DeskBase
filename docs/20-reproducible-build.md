# 20 · 可复现构建

> **一句话**：同一份源码、同一套工具链，任何人构建出来的 `deskbase.exe` 都是**同一个哈希**。
> 这不是口头承诺 —— 下面有实测方法和实测结果。

---

## 为什么关心这件事

这个项目**没有代码签名证书**（见 [ADR-0018](adr/0018-unsigned-self-update.md)），
所以 Windows 会提示"未知发布者"，而"你下载到的确实是官方构建的那一份"这件事，
没法靠签名证明。

剩下的路只有一条：**可复现构建**。它把"信任"换成"验证" ——
任何人拿同一份源码、用同一套工具链构建一次，比对哈希就知道发布物有没有被改过。

## 实测：怎么验

```bash
# 1) 取源码（认准 tag）
git checkout v1.0.0

# 2) 构建
node scripts/build.cjs

# 3) 比对官方发布页给的 SHA-256
node -e "const c=require('crypto'),f=require('fs');\
console.log(c.createHash('sha256').update(f.readFileSync('app/target/release/deskbase.exe')).digest('hex'))"
```

比出来的值应当与 Releases 页面里的 `.sha256` **完全一致**。

## 实测结果

在 Windows + MSVC 工具链上，同一份源码连做两次 release 构建：

| | SHA-256 |
|---|---|
| 第一次 | `84382f915746054bafd09c28b2a663493b036a7250301ac318cfb2d9ee392646` |
| 第二次（改动无关文件的 mtime 强制重编） | `84382f915746054bafd09c28b2a663493b036a7250301ac318cfb2d9ee392646` |

**一致**。两次之间还刻意 `touch` 了源文件，确认是"真的重新编译了"而不是命中了缓存。

### 之前不是这样的（这条改进是有来历的）

第一次实测时**不一致**。原因：MSVC 链接器默认会把**时间戳**写进 PE 头，
（调试信息里也会带绝对路径）—— 每次构建都不同。

修法是一行链接器标志：

```toml
# app/.cargo/config.toml
[target.x86_64-pc-windows-msvc]
rustflags = ["-C", "link-arg=/Brepro"]
```

`/Brepro` 就是链接器的 "build reproducible" 开关。

## 边界（哪些**不**可复现）

说清边界比宣传结论重要：

| 项 | 可复现？ | 说明 |
|---|:---:|------|
| `deskbase.exe` | ✅ | 见上表 |
| **便携 zip** | ❌ | ZIP 格式把每个文件的 **mtime** 写进头部，而打包目录每次都是新建的。里面的 exe 与 SBOM 是确定的，不确定的只是容器的元数据 |
| SBOM（`.cdx.json`） | ✅ | 组件清单来自 `cargo metadata`，内容确定 |
| 跨工具链版本 | ❌ | Rust 版本、链接器版本不同就不保证。**验证时请用与发布同一版本的工具链** |

> 所以发布页给的是**校验和**，不是"可复现构建"的完整承诺 ——
> **能做到的部分说做到，做不到的部分不含糊**。

## 与"完整性链路"的关系

可复现构建是 [ADR-0018](adr/0018-unsigned-self-update.md) 那条"等效完整性链路"的一部分：

| 环节 | 状态 |
|------|:----:|
| SHA-256 随产物发布 | ✅ |
| SBOM 随产物发布 | ✅ |
| 自替换默认关闭（或有五步校验链） | ✅ |
| 发布页与界面如实说明 SmartScreen 会拦 | ✅ |
| **构建可复现（本文件）** | ✅ |

**局限仍然存在，必须一起说**：这些校验和与文件清单都来自同一个 Release ——
**账号一旦被攻破，整条链会一起失效**。可复现构建能防"构建过程被污染"，
防不了"发布账号被盗"。
