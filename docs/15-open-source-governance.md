# 15 · 开源治理、许可证、社区协作与插件生态

> 开源不是"把代码扔到 GitHub"。它是一套让陌生人愿意为你花时间、并且花得放心的机制。

---

## 一、许可证选择

### 1.1 结论

| 部分 | 许可证 | 理由 |
|------|-------|------|
| **核心程序** | **Apache License 2.0** | 见下 |
| **插件 SDK / 接口定义** | **Apache License 2.0** | 让插件作者无顾虑使用 |
| **文档与教程** | **CC BY 4.0** | 便于翻译、转载、改编 |
| **示例数据** | **CC0 1.0**（公共领域） | 无任何使用限制 |
| **品牌与 Logo** | 保留商标权（见 [GOVERNANCE.md](../GOVERNANCE.md)） | 防止被冒用 |

### 1.2 为什么选 Apache-2.0

| 优势 | 说明 |
|------|------|
| **明确专利授权** | 第 3 条提供专利许可，免除下游用户的专利顾虑——这对数据库/桌面软件很重要 |
| **允许闭源集成** | 企业可以把 DeskBase 集成进内部系统而不必开源自己的代码 |
| **允许商用** | 不限制商业使用，便于被集成、被分发 |
| **贡献者条款清晰** | 第 5 条明确贡献即按同一许可授权，无需签署 CLA |
| **被广泛理解** | 企业法务熟悉，降低采用门槛 |
| **与生态兼容** | 兼容 MIT、BSD、Apache-2.0 系依赖；可与大量开源组件共存 |

**对于"桌面工具 + 插件生态"这个形态，Apache-2.0 是平衡性最好的选择**：

- 桌面工具需要被广泛分发（包括被预装、被集成），许可越宽松越容易扩散。
- 插件生态需要让作者无顾虑（他们可能是商业公司），宽松许可更友好。
- 我们靠产品与生态建立影响力，而不是靠许可限制。

### 1.3 为什么不选其他许可证

| 许可证 | 不选的理由 |
|-------|-----------|
| **MIT / BSD** | 缺少明确的专利授权条款；对本项目涉及的加密、数据库技术，专利确定性有价值 |
| **MPL-2.0** | 文件级 copyleft 对插件生态有摩擦（插件与核心的边界难以清晰界定） |
| **LGPL** | 动态链接要求对桌面软件分发（尤其 Electron 类打包）易产生合规争议 |
| **GPL-3.0** | 强 copyleft 会阻止企业集成与商业分发，与"让更多人用上"的目标冲突 |
| **AGPL-3.0** | 针对网络服务场景；本项目是本地应用，用 AGPL 属于过度限制且会劝退用户 |
| **SSPL / BUSL** | 不是 OSI 认可的开源许可；与"开源项目"定位不符 |
| **BSL（时间延迟开源）** | 同上，且会损害社区信任 |
| **CC0 / Unlicense** | 放弃太多权利，无法保护商标，也无法提供专利授权 |

### 1.4 关于"防止被云厂商白嫖"

这是一个常见顾虑。我们的立场：

> 本项目是**本地优先的桌面工具**，不是可以被云厂商打包成 SaaS 的服务。云厂商拿走代码对我们几乎没有实际损害，反而可能扩大用户基数。用 AGPL 之类的许可去"防白嫖"，代价是劝退大量正常用户与企业，得不偿失。

如果未来出现商业托管版本，正确的做法是**用商标与服务区分**，而不是收紧核心代码的许可。

### 1.5 许可证变更政策

| 项 | 规定 |
|----|------|
| 变更条件 | 需核心维护者 2/3 同意（L4 决策） |
| 前置公告 | 至少提前 30 天公告 |
| 溯及力 | **不溯及既往**。新许可适用于之后发布的版本，已发布的旧版本保持原许可 |
| 贡献者同意 | 若变更会收紧许可，需征得主要贡献者同意 |
| 兼容性 | 只允许向兼容性更宽松或等价的方向变更（如 Apache-2.0 → MIT），不允许反向收紧 |

## 二、仓库与协作结构

### 2.1 仓库组织建议

```
deskbase/                       主仓库（应用）
├── README.md
├── LICENSE
├── CONTRIBUTING.md
├── CODE_OF_CONDUCT.md
├── SECURITY.md
├── ROADMAP.md
├── GOVERNANCE.md
├── CHANGELOG.md
├── docs/                       产品与工程文档
│   └── adr/                    架构决策记录
├── .github/                    Issue / PR 模板、CI 配置
├── src/                        源码（结构随技术选型确定）
├── tests/                      测试
├── scripts/                    构建与工具脚本
└── ...
```

**配套仓库（按需拆分）**

| 仓库 | 用途 | 何时拆分 |
|------|------|---------|
| `deskbase` | 主应用 | — |
| `deskbase-plugins-sdk` | 插件 SDK 与类型定义 | M7 插件阶段 |
| `deskbase-plugins` | 官方插件集合 | M7 |
| `deskbase-website` | 官网与文档站 | 需要时 |
| `deskbase-relay` | 自托管中继服务 | M6 |
| `deskbase-templates` | 模板与示例数据 | M1 之后 |

> **不要过早拆分。** 单仓库在项目早期便于统一变更与 CI。拆分的成本是跨仓库的子模块/依赖管理。

### 2.2 分支策略

| 分支 | 用途 |
|------|------|
| `main` | 开发主线，始终可构建、CI 全绿 |
| `release/x.y` | 发布维护分支，只接受缺陷与安全修复 |
| `feat/*` `fix/*` `docs/*` | 功能分支，命名见 [CONTRIBUTING.md](../CONTRIBUTING.md) |

| 规则 | 说明 |
|------|------|
| 保护 `main` | 禁止直接推送，必须经 PR |
| 线性历史 | 优先 rebase；合并时 squash |
| 标签 | 语义化版本，如 `v1.2.0` |
| 提交信息 | Conventional Commits（见 [CONTRIBUTING.md](../CONTRIBUTING.md)） |

### 2.3 CI 建议流程

```
PR 触发
  ├── 静态检查（lint / format 校验）
  ├── 类型检查
  ├── 单元测试
  ├── 集成测试
  ├── 端到端测试（关键流程）
  ├── 构建（三平台）
  ├── 体积检查（超过阈值则失败）
  ├── 依赖漏洞扫描（SCA）
  ├── 许可证合规检查
  ├── 性能基准对比
  └── 可复现构建校验（发布分支）
```

**关键原则**：CI 必须在**无网络**依赖注入的情况下可复现（依赖预缓存）。

## 三、社区协作机制

### 3.1 沟通渠道

| 渠道 | 用途 | 响应期望 |
|------|------|---------|
| GitHub Issues | 可复现缺陷、明确需求 | 维护者 3 个工作日内分类 |
| GitHub Discussions | 提问、交流、RFC | 社区互助，维护者不定期参与 |
| Security Advisory | 安全问题 | 48 小时内响应（见 [SECURITY.md](../SECURITY.md)） |
| 公开会议（可选） | 季度路线图讨论 | 会议记录公开 |

**我们不做**：私密的、只对部分人可见的决策渠道。所有决策必须留下公开记录。

### 3.2 新贡献者友好度

| 机制 | 说明 |
|------|------|
| `good first issue` 标签 | 明确标注适合新人的任务 |
| 详细的任务描述 | 新人不需要猜 |
| 欢迎机器人 | 首次 PR 自动欢迎并给出指引 |
| 耐心评审 | 不因"风格不统一"打击新人 |
| 文档优先 | 让新人能从文档入手而非直接啃代码 |
| 明确的"如何搭环境" | 一条命令能跑起来 |

### 3.3 维护者负担控制

| 措施 | 说明 |
|------|------|
| 明确关闭标准 | 见 [CONTRIBUTING.md](../CONTRIBUTING.md#会被直接关闭的-pr) |
| 自动分类 | 用标签与机器人减少手工整理 |
| 超时关闭 | 90 天无进展的 Issue 自动关闭（可重开） |
| 拒绝范围蔓延 | 明确"不做清单"，减少无谓争论 |
| 定期归档 | 季度清理过期 Issue |

### 3.4 决策透明

| 要求 | 说明 |
|------|------|
| 所有 L3/L4 决策有 ADR | 见 `docs/adr/` |
| RFC 讨论公开 | 含被拒绝的 RFC 与拒绝理由 |
| 路线图公开 | 见 [ROADMAP.md](../ROADMAP.md) |
| 发布决策公开 | Release Notes 说明何时为何发布 |

## 四、插件生态设计

### 4.1 设计原则

| 原则 | 说明 |
|------|------|
| **权限最小化** | 插件只获得声明的权限 |
| **进程隔离** | 插件在独立进程运行，崩溃不影响主程序 |
| **可审计** | 权限清单可见、行为可记录 |
| **可关闭** | 一键禁用，立即生效 |
| **可彻底卸载** | 卸载后不留文件、配置、后台进程 |
| **不进核心** | 插件不能替代核心承诺（备份、加密、隐私开关必须是核心功能） |
| **平台中立** | 插件接口不绑定特定前端框架或运行时 |

### 4.2 插件形态

| 形态 | 能力 | 限制 |
|------|------|------|
| **UI 扩展** | 增加面板、菜单项、视图 | 不能改核心界面结构 |
| **数据处理** | 导入/导出格式扩展、数据转换 | 不能绕过权限读取数据 |
| **动作提供者** | 为自动化提供新动作 | 需声明网络/文件权限 |
| **集成适配** | 对接外部服务（需网络权限） | 默认无网络权限 |
| **主题** | 界面配色与图标 | 不能注入脚本 |

### 4.3 权限清单

插件必须在清单中声明所需权限，用户在安装时逐项确认：

| 权限 | 范围 | 默认 |
|------|------|------|
| `data.read` | 读取数据（需指定库/表范围） | 授予（受限范围） |
| `data.write` | 写入数据 | 需用户确认 |
| `file.read` | 读取文件（需指定目录） | 需用户确认 |
| `file.write` | 写入文件 | 需用户确认 |
| `network` | 访问网络（需指定域名） | **默认拒绝** |
| `clipboard` | 读写剪贴板 | 需用户确认 |
| `ui.panel` | 添加界面面板 | 授予 |
| `notification` | 发送系统通知 | 授予 |
| `settings` | 读写自己的配置 | 授予 |
| `schedule` | 注册定时任务 | 需用户确认 |

**权限规则**

- 不允许"全部文件访问"这类过宽权限。必须指定具体目录。
- 不允许"访问任意网络地址"。必须声明域名白名单。
- 权限变更需重新确认（插件更新后提高权限时，需用户重新授权）。
- 权限可在任意时刻撤销，撤销后插件立即失去相应能力。

### 4.4 插件沙箱

| 隔离维度 | 措施 |
|---------|------|
| 进程 | 每个插件独立进程 |
| 内存 | 硬性上限（默认 256 MB） |
| CPU | 使用率上限（默认 10%），超出则降频或暂停 |
| 执行时间 | 单次调用超时（默认 30 秒） |
| 文件系统 | 只能访问声明过的目录 |
| 网络 | 默认禁止；开启后只能访问声明过的域名 |
| 数据访问 | 只能访问被授权的库/表；服务端校验，不信任插件 |
| 崩溃隔离 | 插件崩溃只影响自身，主程序提示"插件 X 已停止" |

### 4.5 插件市场

| 维度 | 设计 |
|------|------|
| 官方源 | 官方维护的插件索引 |
| 自建镜像 | 支持企业/个人自建市场源（配置 URL） |
| 纯本地 | 可完全禁用市场，只装本地插件 |
| 上架审核 | 人工审查权限清单与行为；不做内容审查 |
| 签名 | 鼓励插件作者签名；市场标注签名状态 |
| 评分与下载量 | **本地统计，不上报**（不违反隐私承诺） |
| 更新 | 默认手动检查；可开自动检查 |
| 下架 | 发现恶意行为可下架，但已安装的插件会在用户端提示风险 |

> **不上报使用数据是硬约束**。插件市场的评分与下载量必须来自公开可见的来源（如仓库 Star、社区投票），而不是用户端的静默埋点。

### 4.6 插件开发体验

| 提供物 | 说明 |
|--------|------|
| SDK | 类型定义、接口文档、示例代码 |
| 模板仓库 | 一条命令生成插件骨架 |
| 本地加载 | 开发者模式可直接加载本地目录，无需打包 |
| 调试工具 | 日志、权限模拟、接口调用追踪 |
| 测试工具 | 插件测试框架 |
| 文档 | 完整的接口文档与最佳实践 |

### 4.7 插件红线

| 红线 | 处理 |
|------|------|
| 静默联网 | 下架 + 公告 |
| 收集用户数据 | 下架 + 公告 |
| 请求过宽权限且无正当理由 | 拒绝上架 |
| 绕过权限访问数据 | 下架 + 公告 |
| 替换核心功能（如提供"更好的备份"并要求用户关闭核心备份） | 拒绝上架 |
| 包含广告或推广 | 拒绝上架 |
| 不提供源码或可复现构建 | 标注"未审计"，用户安装时警示 |

## 五、可审计性设计

> 这是本项目在开源治理上的核心差异点：**让"我们说我们没做坏事"变成"你可以自己验证我们没做坏事"**。

| 机制 | 落地方式 |
|------|---------|
| **依赖锁定** | 全部依赖写入锁文件，锁文件入库 |
| **SBOM** | 每次发布生成 SPDX / CycloneDX 格式的软件物料清单 |
| **可复现构建** | 提供构建说明，CI 校验产物哈希与预期一致 |
| **代码签名** | 三平台签名，公布签名指纹 |
| **校验和** | 每个产物公布 SHA-256 |
| **网络行为审计** | 程序内提供审计日志，记录全部出站连接尝试 |
| **数据落点审计** | 程序内提供"我本机存了什么"视图 |
| **权限清单** | 插件权限在界面上可见、可撤销 |
| **公开性能数据** | Release Notes 公布实测指标 |
| **第三方许可证清单** | 随发布附带全部依赖的许可证文本 |

### 5.1 面向审计者的支持

| 支持 | 说明 |
|------|------|
| 安全研究员友好 | 明确漏洞报告渠道与响应时效 |
| 提供构建指南 | 任何人可在本地复现官方二进制 |
| 公开依赖决策 | 引入重要依赖时有 ADR 说明理由 |
| 接受第三方审计 | 欢迎并公示第三方审计报告 |
| 不封禁研究者 | 不因披露漏洞而采取法律行动（善意披露豁免） |

## 六、可持续性

### 6.1 维护者可持续

| 机制 | 说明 |
|------|------|
| 角色分工 | 见 [GOVERNANCE.md](../GOVERNANCE.md)，不依赖单一维护者 |
| 领域负责人 | 每个模块有明确负责人 |
| 荣誉维护者 | 退出者的贡献被记录 |
| 负担控制 | 明确的不做清单减少争论消耗 |
| 文档即契约 | 减少重复解释 |

### 6.2 资金（可选，且必须与产品原则兼容）

若未来接受资助，遵守以下约束：

| 允许 | 禁止 |
|------|------|
| 接受个人捐赠 | 接受要求加入广告的赞助 |
| 接受企业支持（不附带产品控制权） | 出卖用户数据或引入遥测 |
| 接受基金会支持 | 让资助方决定产品路线 |
| 提供付费支持服务 | 把核心功能设为付费 |
| 提供付费的企业版（增加企业特性） | 削弱开源版功能以推销企业版 |

**铁律**：商业模式不得以牺牲用户隐私或核心功能为代价。宁可项目慢一点。

## 七、与用户的关系

| 承诺 | 说明 |
|------|------|
| 不强制升级 | 用户可用任何历史版本 |
| 不远程禁用 | 程序不会因为"版本过旧"而停止工作 |
| 不绑架数据 | 全部数据可导出为开放格式 |
| 不静默改变行为 | 影响用户的功能变更必须在 Release Notes 与程序内公告 |
| 不抛弃旧平台 | 停止支持某平台需提前公告并提供迁移建议 |
| 长期可维护 | 数据格式向前兼容；破坏性变更提供迁移工具 |
