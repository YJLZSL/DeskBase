# 02 · 目标用户与典型使用场景

> 设计不是给「用户」做的，是给**某个具体的人在某个具体的下午**做的。

---

## 一、用户分层

我们把用户分成三层。**第一层是必须服务的，第二层是必须留住的，第三层是必须不挡路但也不讨好的。**

```
        ┌───────────────────────────────┐
        │  ③ 专业/轻技术用户（约 10%）    │  要 SQL、要索引、要性能、要 API
        ├───────────────────────────────┤
        │  ② 办公进阶用户（约 25%）       │  要表格、要备份、要跨设备
        ├───────────────────────────────┤
        │  ① 普通办公用户（约 65%）★核心   │  要能用、要简单、要不丢、要不外泄
        └───────────────────────────────┘
```

---

### ① 普通办公用户 ★ 核心服务对象

**画像**

| 维度 | 描述 |
|------|------|
| 年龄 | 25–55 |
| 技术能力 | 会用 Word / Excel / 微信 / 浏览器，不懂 SQL，不知道「主键」是什么 |
| 设备 | 一台 Windows 笔记本，可能还有一台家里台式 |
| 关键诉求 | 东西记下来别丢；找得到；别人看不到 |
| 心理状态 | **怕麻烦**。任何需要读文档才能用的功能，等于不存在 |
| 失败信号 | 打开后看到一堆不认识的按钮 → 关掉，再也不开 |

**他们真正想要的一句话**

> 「我就想把我那些乱七八糟的东西有个地方放，别丢，别让别人看见，别让我学新东西。」

**设计约束**

- 首启后 **30 秒内**必须能完成第一个有价值动作（建一条笔记或清单一类）。
- 界面上任何一处文字，都必须是「不需要解释就能懂」的中文。
- 绝不出现裸 SQL、字段类型选择器、外键设置这些概念——除非用户主动点开「高级」。
- 报错信息必须写「怎么办」，而不是写「发生了什么」。

**典型人物**

> **陈静，38 岁，社区诊所护士长**
> 用 Excel 管着 200 多个老人的用药记录。上个月 Excel 崩了一次，文件没保存，哭了半天。她听人说「数据库不会丢」，但打开过一款数据库软件，看到满屏英文和表结构，5 分钟关掉了。
> 她需要的不是数据库，是**一个不会丢的 Excel**。

---

### ② 办公进阶用户 ★ 必须留住

**画像**

| 维度 | 描述 |
|------|------|
| 年龄 | 25–45 |
| 技术能力 | 会用 Excel 公式和数据透视表；写得出简单 SQL；装过 Docker |
| 设备 | 办公笔记本 + 家里电脑 + 手机 |
| 关键诉求 | 数据能关联、能查询、能备份、能在手机上随时看一眼 |
| 心理状态 | **有洁癖**。容忍不了数据散落在五六个工具里，也容忍不了软件偷偷联网 |
| 失败信号 | 发现表格超过 5 万行就卡 → 迁移走 |

**他们真正想要的一句话**

> 「我的数据我自己管，但要给我顺手的工具——别让我在五六个 App 之间来回复制粘贴。」

**设计约束**

- 表格必须能扛住 10 万行；滚动必须跟手。
- 必须有数据关联（哪怕叫「关联」而不是「外键」）。
- 必须有可信的备份与恢复，并且**能验证**（健康检查 + 演练）。
- 必须有手机端，但**不能依赖第三方云**。
- 必须有导出：他们不信任何单一软件。

**典型人物**

> **林维，31 岁，独立摄影师**
> 手上有 400 多个客户、2000 多张交付记录、一堆器材清单和报价单。现在用 Excel + 备忘录 + 微信收藏 + 系统截图混着管。手机里存了 300 多张报价截图，找一张要翻五分钟。
> 他需要的不是更漂亮的工具，是**一个能查询的地方 + 截图后能提取文字**。

---

### ③ 专业 / 轻技术用户 ★ 不讨好但不能挡路

**画像**

| 维度 | 描述 |
|------|------|
| 技术能力 | 会写复杂 SQL、懂索引与执行计划、会看日志、会读源码 |
| 关键诉求 | 性能可预期、行为可预测、可脚本化、可审计、可编程扩展 |
| 心理状态 | **挑剔且重要**。他们往往是社区的种子用户与插件作者 |
| 失败信号 | 发现「不能写原生 SQL」或「导出被阉割」→ 公开吐槽并劝退别人 |

**他们真正想要的一句话**

> 「别替我决定。给我完整的 SQL 能力、公开的接口、可读的日志，剩下的我自己来。」

**设计约束**

- SQL 能力**不阉割**：视图、触发器、索引、执行计划、事务都要有。
- 暴露调试能力：日志级别可调、慢查询记录、SQL 执行日志可选。
- 插件接口公开且文档化，允许本地开发与调试。
- 版本演进中，破坏性变更必须有迁移路径与充足公告期。

**典型人物**

> **老赵，44 岁，小厂信息化负责人**
> 想给车间做一个设备点检记录系统，预算为零，不想上云（怕数据外泄）。他试过用 SQLite + 一堆脚本自己拼，能跑但难维护。
> 他需要的是**一个有 GUI 的本地数据库 + 能生成 API + 能定时跑任务**，最好还能封成插件丢给车间同事用。

## 二、典型使用场景

每个场景都给出：**触发时刻 → 当前痛点 → DeskBase 的做法 → 成功判据**。

---

### 场景 1 · 陈静的用药记录（核心场景 · 数据安全）

**触发时刻**
周一早上 7:40，陈静打开电脑准备更新上周的用药记录。上次 Excel 崩溃让她心有余悸。

**当前痛点**
- Excel 文件放在桌面，手动另存为「版本2」「版本3」，现在已经到「版本17最终最终版」
- 不知道哪天误删了一行
- 不放心放在云盘，觉得「万一被别人看到」

**DeskBase 的做法**

1. 打开 DeskBase → 首页显示「最近的表格：用药记录」，一键进入。
2. 表格已有 200 行，新增一行只需在末尾直接输入，回车即保存。
3. 每次修改自动产生版本，右侧「历史」可看到三天前删掉的那一行，一键恢复。
4. 系统设置里备份默认开启，每天晚上自动备份到本地 D 盘，保留最近 30 份。
5. 设置里点「备份健康检查」，显示绿色的「最近一次备份可用，已通过校验」。

**成功判据**
> 陈静**从未感觉到自己在用数据库**，但她再也没有丢过一行数据。

**覆盖模块**：办公工具（表格）、备份与恢复、工作台

---

### 场景 2 · 林维的报价截图（核心场景 · 办公效率）

**触发时刻**
客户在微信里发来一张手写的报价单照片，林维需要把它变成可搜索的记录。

**当前痛点**
- 截图存在「图片」文件夹，文件名是 `IMG_20260912_143022.png`
- 三个月后想找「那个 8000 块的婚礼报价」完全找不到
- 手打一遍太慢，而且容易错

**DeskBase 的做法**

1. 按全局快捷键 `Ctrl+Shift+A` → 框选微信窗口里的报价单 → 截图完成。
2. 截图悬浮窗上直接点「提取文字」→ 本地 OCR 识别出报价内容，**不联网**。
3. 识别结果一键「存入表格」→ 自动带入金额、日期字段。
4. 表格里可以直接搜索「8000」，或者搜索客户名，这张截图会作为附件一起被检索到。
5. 需要给客户发截图时，从截图历史里找到原图，右键「复制」。

**成功判据**
> 从看到报价单到变成可搜索记录，**不超过 30 秒**；且全程没有一张图片上过网。

**覆盖模块**：办公工具（截图、OCR、表格、剪贴板）、AI（可选增强：从非结构化文本抽取字段）

---

### 场景 3 · 林维的客户台账（关联与查询）

**触发时刻**
月底了，林维想看看「所有今年没付尾款的客户」。

**当前痛点**
Excel 里客户信息、订单、收款分成三个 Sheet，靠手工 VLOOKUP 对，稍微改一下就错位。

**DeskBase 的做法**

1. 三张表已建立关联：「客户」→「订单」→「收款」。
2. 新手路径：点「查询向导」→ 选择「我要找：收款记录」→ 加条件「状态 = 未结清」+「日期在 2026 年内」→ 生成结果表格。
3. 高级路径：点右上角「查看 SQL」，看到向导生成的 SQL，想改就改。
4. 结果直接「导出为 Excel」发给会计。

**成功判据**
> 一个从没写过 SQL 的人，**用勾选和下拉框**拿到了需要 JOIN 三张表才能得到的结果。

**覆盖模块**：数据库（查询向导、关系、JOIN）、办公工具（导出）

---

### 场景 4 · 老赵的设备点检（自动化 + 性能）

**触发时刻**
车间主管说：「每天下班前要能看到当天的点检汇总，自动发到群里。」

**当前痛点**
手工统计，容易漏；用云表格又怕数据出去。

**DeskBase 的做法**

1. 建一张「点检记录」表，车间同事在平板上通过**局域网远程端**录入。
2. 建一条自动化规则：每天 17:30 触发 → 汇总当天记录 → 生成报表 → 保存到指定目录。
3. 表数据涨到 60 万行后，给「设备编号 + 日期」建复合索引，查询依然是毫秒级。
4. 开启审计日志，能看到谁在什么时候录入了什么。

**成功判据**
> 60 万行数据下，常用查询 ≤ 50 ms；每天自动出报表，**不需要任何人记得去做**。

**覆盖模块**：自动化、数据库（索引、性能）、远程访问、审计

---

### 场景 5 · 小吴的读书笔记（关联 + 搜索 + 版本）

**触发时刻**
小吴读完了第 80 本书，想把笔记整理成可检索的体系。

**当前痛点**
笔记散在备忘录、微信收藏、纸本、OneNote 里，找一句话要翻半天。

**DeskBase 的做法**

1. 笔记模块支持 Markdown + 双向链接，写到「《人类简史》」会自动关联到所有提到它的笔记。
2. 全局搜索 `Ctrl+K` 一搜，10 万条记录首屏 300 ms 内出结果。
3. 给笔记打标签，标签可跨模块（也能标在表格行、日历事件上）。
4. 引用关系图，看到自己的知识结构。

**成功判据**
> 「我好像在哪本书里看过一个概念」→ **3 秒内找到**。

**覆盖模块**：办公工具（笔记、标签、全局搜索）

---

### 场景 6 · 断电那一刻（容灾）

**触发时刻**
周三下午，小城突然停电。陈静正在录入第 187 行数据。

**当前痛点**
Excel 直接白屏，最后半小时白干。

**DeskBase 的做法**

1. 每次单元格提交都是一次事务，已经写入 WAL 并 `fsync`。
2. 来电后开机，DeskBase 启动时检测到上次未正常退出 → **自动弹出恢复向导**（不静默忽略）。
3. 向导显示：「检测到异常退出，已完成崩溃一致性检查。最后一次成功提交：14:32:07。是否查看恢复报告？」
4. 陈静点「查看」→ 看到 187 行之前的全部数据完好，187 行处于草稿状态，可选择保留或丢弃。
5. 恢复完成后自动生成一次「事故后快照」，防止二次损坏。

**成功判据**
> 停电最多损失**最后一次未提交的操作**，绝不是「最后半小时的工作」。

**覆盖模块**：备份与恢复（断电保护、恢复向导）、存储层

---

### 场景 7 · 手机在厨房（远程访问）

**触发时刻**
林维在客户现场，需要查一下某位客户的联系方式，手机不在身边，但平板在包里。

**当前痛点**
数据在电脑里，要么远程桌面（慢、不安全），要么开云同步（不放心）。

**DeskBase 的做法**

1. 出门前确认桌面端「远程访问」已开，且仅在**局域网**或**自托管中继**下生效。
2. 平板打开 DeskBase 远程端 → 扫二维码配对（一次性配对码 + 设备指纹）。
3. 通道端到端加密，中继服务器**看不到内容**。
4. 平板只有「查看客户表」权限，没有删除权限。
5. 查看完成后自动断开，不后台常驻。

**成功判据**
> 抓包**读不出明文**；平板**不常驻高耗电**；权限精确到「只能看这一张表」。

**覆盖模块**：远程访问、隐私安全、移动端

---

### 场景 8 · 想用 AI 整理一堆乱糟糟的短信（本地 AI）

**触发时刻**
陈静把一堆家属短信复制进了笔记，想知道「哪些老人这个月该复诊」。

**当前痛点**
可以用 ChatGPT，但要先把 200 条短信粘到别人的服务器上——她不愿意。

**DeskBase 的做法**

1. 笔记页点「AI 助手」→ 选择本地模型。
2. 提问：「从这段文本里提取姓名、复诊日期，做成表格」。
3. 推理在本机完成，**整个过程中网卡没有任何流量**。
4. 生成结果以「预览表格」呈现，用户确认后写入。AI 不会直接改数据。
5. 如果用户想把模型换成外部 API，界面会弹出：「此操作会把选中的文本发送到 xxx 服务器。以下是实际将发送的内容：[预览]。确认发送？」——**逐次确认**。

**成功判据**
> 断网状态下 AI 功能**完全可用**；若启用外部服务，用户在发送前**看得见要发什么**。

**覆盖模块**：AI 助手、隐私安全

---

### 场景 9 · 卸载（信任的最后一关）

**触发时刻**
陈静换了新电脑，或者试用三个月觉得不适合。

**当前痛点**
很多软件卸不干净，`AppData` 里留一堆东西，注册表一堆垃圾，电脑越用越慢。

**DeskBase 的做法**

1. 卸载器是**自有品牌界面**，不是系统默认灰框。
2. 两个选项：
   - **保留数据卸载**：「我会移除程序，但保留你的数据（位于 `D:\DeskBaseData`），下次安装可继续使用。」
   - **彻底清除卸载**：「将永久删除以下内容：[逐条列出：程序文件 512 MB、数据 1.2 GB、备份 3.4 GB、日志 8 MB、缓存 240 MB、注册表项 6 项、计划任务 0 项]。此操作不可撤销。」
3. 选彻底清除 → 二次确认需**手动输入「彻底删除」**（防止误点）。
4. 卸载完成后自动运行一次**残留检查**，并显示报告：「未发现残留。系统已恢复到安装前状态。」

**成功判据**
> 卸载后残留项 **= 0**，且用户**亲眼看到**了这个结论。

**覆盖模块**：安装与卸载、安全与资源优化

---

### 场景 10 · 换机搬家（可迁移）

**触发时刻**
林维买了新笔记本。

**DeskBase 的做法**

1. 老电脑：`设置 → 基础 → 导出全部数据` → 生成一个目录包（含数据库、附件、配置、说明文件）。
2. 拷到 U 盘（如果开了加密，需输入口令）。
3. 新电脑：装好 DeskBase → 首启选「从已有数据导入」→ 选择该目录 → 完成。
4. 或者**更简单的方式**：直接用便携版放到 U 盘，数据目录设成 U 盘上的目录，插到哪台电脑都能用。

**成功判据**
> 换机过程**不需要联网**、**不需要登录**、**不经过任何第三方服务器**。

**覆盖模块**：备份与恢复、安装（便携版）、可迁移原则

## 四、反面场景（明确不为谁优化）

| 不为谁优化 | 原因 |
|-----------|------|
| 需要 50 人同时在线编辑的团队 | 冲突检测与实时协同需要中心化服务，属协作产品范畴 |
| 需要管理 TB 级数据仓库的数据分析师 | 本地单文件库不适合；建议用专业 OLAP 工具 |
| 需要 7×24 高可用集群的企业 IT | 属 DBA 运维工具范畴 |
| 只想白嫖免费云盘同步的用户 | 我们不做默认云同步，这是立场问题不是能力问题 |
| 依赖广告或推荐流量的内容消费者 | 我们不做广告 |

## 五、可用性验证方法

设计是否真的服务了目标用户，用以下方式验证：

| 方法 | 对象 | 观测指标 |
|------|------|---------|
| **首次使用测试**（5 人） | ① 普通用户 | 30 秒内完成第一个有价值动作的比例 ≥ 4/5 |
| **任务完成测试** | ① ② 用户 | 完成指定任务（如"找出未结清客户"）的中位时间 |
| **困惑点记录** | 全部 | 用户主动提问「这是什么意思」的次数 |
| **信任测试** | ① 用户 | 被问「你觉得你的数据在哪儿」，能否正确回答「在我电脑上」 |
| **卸载体验测试** | ① ② 用户 | 卸载后是否认为「干净」；是否愿意再次安装 |
| **性能体感测试** | ② ③ 用户 | 10 万行表滚动是否被感知为"卡" |
| **离线压力测试** | 全部 | 拔网线后能否完成完整工作流 |

> 详细测试方法与通过判据见 [14 · 性能优化与量化指标](14-performance-budget.md) 与 [16 · 路线图、风险与验收](16-roadmap-risks-acceptance.md)。
