# 04 · 完整功能矩阵

> 每一条功能都必须回答一个问题：**它属于 MVP、进阶，还是插件？**

---

## 一、分级定义

| 标记 | 含义 | 判定标准 |
|------|------|---------|
| **MVP** | 首个对外发布版本必须包含 | 缺了它，产品无法成立或承诺被打破 |
| **进阶** | MVP 之后的核心能力，进入后续里程碑 | 提升上限，但不做也不影响核心闭环 |
| **插件** | 通过插件机制扩展，不进入核心代码 | 需求真实但受众窄，或引入合规/体积风险 |
| **不做** | 明确排除 | 与定位冲突，见 [01](01-vision-boundary-principles.md) |

**MVP 的判定三问**（全部为"是"才进 MVP）：

1. 缺了它，用户能否完成一条完整的工作闭环（记录 → 组织 → 查询 → 保护）？
2. 缺了它，是否会让某个已做出的承诺（不丢数据 / 不泄露 / 不污染 / 可迁移）落空？
3. 它是否服务于核心用户（普通办公用户）的日常？

## 三、MVP 范围界定（一句话版）

> **MVP = 一条完整闭环：**
> 打开就能记（笔记/表格/待办）→ 截图能存能认字（截图/长截图/OCR）→ 能组织能找（标签/搜索）
> → 数据在库里能被查询（建表/导入/查询向导/基础 SQL）
> → 数据不会丢（自动备份/崩溃恢复/回收站）
> → 数据不会外流（网络默认关闭/剪贴板本地/OCR 本地）
> → 能干净装干净卸（便携版零污染、卸载干净）

**MVP 明确不含**：本地 AI、远程访问、自动化、插件、加密存储、视图/触发器/索引的高级管理。

这些不是不重要，而是**先要把"能用、不丢、不泄露"三条腿立稳**，再长出别的能力。

## 四、功能取舍记录

以下功能经过讨论被**降级或推迟**，记录理由以备复查：

| 功能 | 原计划 | 调整 | 理由 |
|------|-------|------|------|
| 云同步到第三方网盘 | MVP | 移除 | 与隐私承诺冲突；改为插件 + 自托管方向 |
| 富文本文档编辑 | MVP | → 进阶(M8) | Markdown 已覆盖 MVP 需求，富文本排版引擎成本高 |
| 数据透视表 | MVP | → 进阶(M8) | 目标用户频次低于筛选排序，先用查询向导覆盖 |
| 录屏 | MVP | → 插件 | 体积与编解码库成本高，受众相对窄 |
| 连接外部数据库 | MVP | → 插件 | 会稀释"本地单文件"的核心定位 |
| 图表可视化 | MVP | → 进阶(M8) | 先保证数据正确与可查询，可视化后置 |
| 语音转写 | MVP | → 进阶(M5) | 依赖本地模型，等 AI 阶段一起做 |
| 多人协作 | 设想 | → 不做 | 定位冲突 |
| 云端账号 | 设想 | → 不做 | 定位冲突 |
| 加密默认开启 | MVP | → 首启询问 | 加密会带来口令丢失风险，需用户知情选择 |

## 五、插件化的判定标准

一个功能什么时候应该做成插件，而不是进核心？

**满足以下任意两条，考虑插件化：**

1. 引入它会使安装包体积增长超过 **5%**。
2. 引入它需要新的系统权限（如摄像头、麦克风、网络监听）。
3. 它有明确的**法律或合规**风险（如文件同步、外部服务对接）。
4. 只有 **< 15%** 的用户会用到它。
5. 它需要频繁独立更新，与主程序发布节奏不同步。
6. 它可以让第三方生态发挥，而不必我们投入长期维护。
7. 它涉及把数据送到本机以外的地方（必须由用户显式安装才成立）。

**反过来说，以下必须留在核心：**

- 涉及**数据安全底线**的能力（备份、恢复、加密、审计）
- 涉及**隐私承诺**的能力（网络开关、AI 隐私面板）
- **基础办公能力**（笔记、表格、截图、OCR、搜索）
- **任何会改变数据格式**的能力

> 铁律：**插件不得成为核心承诺的替代品。** 备份永远是核心功能，不能"用插件补"。
