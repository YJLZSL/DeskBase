# 07 · 备份、恢复、断电保护与容灾设计

> **没做过恢复演练的备份，不算备份。**
> 这是本项目的第六原则，也是本文档存在的理由。

---

## 一、设计目标与不变量

### 1.1 三条不变量

| 不变量 | 含义 | 违反后果 |
|--------|------|---------|
| **I1 · 崩溃安全** | 任何时刻断电，重启后数据库必须处于一致状态 | 库文件损坏，全部数据不可读 |
| **I2 · 有界丢失** | 异常退出最多丢失"最后一次未提交事务" | 丢失最近若干分钟的工作 |
| **I3 · 可验证恢复** | 每一份备份都必须能被验证为可恢复 | "以为有备份"的假安全 |

### 1.2 分层防线

```
第 1 层  事务与 WAL          ← 防单次写入中断
第 2 层  原子写入 + fsync    ← 防文件系统层面撕裂
第 3 层  自动 checkpoint      ← 防 WAL 无限增长与恢复时间过长
第 4 层  草稿与自动保存       ← 防应用层未提交内容丢失
第 5 层  版本历史             ← 防误改、误删
第 6 层  回收站               ← 防误删（用户可见）
第 7 层  快照                 ← 防批量误操作
第 8 层  自动备份（全量/增量） ← 防文件损坏、介质故障
第 9 层  多目标备份           ← 防介质同时失效
第 10 层 恢复演练             ← 防"备份不可用"
```

**任何一层都不能被跳过。** 尤其第 10 层——它验证的是前 9 层是否真的有效。

## 二、存储层：崩溃一致性与断电保护

### 2.1 事务

| 要求 | 说明 |
|------|------|
| ACID | 单库内保证原子性、一致性、隔离性、持久性 |
| 隔离级别 | 默认 `SERIALIZABLE` 或等价的快照隔离（嵌入式单机场景下性能损失可接受，正确性优先） |
| 事务边界 | 用户的一次"保存"、一次批量导入的一个批次、一次结构变更 = 一个事务 |
| 嵌套 | 支持 SAVEPOINT（内部使用，不必暴露给用户） |
| 长事务保护 | 超过阈值（默认 30 秒）的事务被记录告警；超过硬上限（默认 5 分钟）被强制回滚并通知用户 |
| 提交同步 | 每次 `COMMIT` 必须等待 WAL 落盘（`synchronous=FULL` 或等价），**不允许为性能牺牲持久性** |

> **取舍声明**：我们选择"每次提交都 `fsync`"，代价是写入吞吐量下降。对本产品的使用场景（人工录入、批量导入）来说，这个代价换来的可靠性是值得的。批量导入场景通过"分批提交"（每 N 行一次）来平衡。

### 2.2 WAL（Write-Ahead Log）或等价机制

**核心机制**

```
写入流程：
  1. 把变更写入 WAL 文件（append-only）
  2. fsync WAL                ← 此刻事务已持久
  3. 返回提交成功给用户
  ...
  （之后异步地）把 WAL 中的变更合并进主数据库文件
  （合并完成后）可以安全地回收 WAL 中已合并的部分
```

**关键参数**

| 参数 | 默认值 | 说明 |
|------|-------|------|
| WAL 模式 | 开启 | 不可关闭 |
| 同步级别 | `FULL` | 每次提交都 fsync |
| checkpoint 阈值 | 1000 页 或 4 MB | 达到阈值触发自动 checkpoint |
| checkpoint 时机 | 空闲时执行 | 避免影响交互 |
| WAL 最大体积 | 64 MB | 超过则强制执行 checkpoint |
| WAL 文件位置 | 与主库同目录 | 便于整体搬迁；可配置到更快介质 |

**若底层引擎不提供 WAL**，必须实现等价的机制：

- 影子分页（Shadow Paging）
- 先写日志文件 + 原子重命名
- 双写（Double Write）+ 校验

**核心要求不变**：任何时刻中断，重启后必须能判断出"哪个状态是完整的"。

### 2.3 原子写入

| 场景 | 实现方式 |
|------|---------|
| 写入新文件 | 写临时文件 → `fsync` → 原子重命名覆盖 |
| 修改配置 | 同上（配置损坏不应导致程序无法启动） |
| 写入备份 | 写临时文件 → 校验 → 原子重命名（未完成的备份不会以正式名字出现） |
| 迁移数据库格式 | 新文件写完后才切换指针，旧文件保留直到验证通过 |

### 2.4 fsync 策略

| 操作 | 是否 fsync |
|------|-----------|
| 事务提交 | **必须** |
| WAL 文件创建 | 必须（含父目录 fsync，确保目录项落盘） |
| checkpoint 完成 | 必须 |
| 备份文件完成 | 必须（然后才可标记备份为"可用"） |
| 缓存写盘 | 否 |
| 日志写盘 | 可延迟（默认缓冲 1 秒） |

> **目录 fsync**：创建或重命名文件后必须 fsync 父目录，否则断电后可能文件内容存在但目录项丢失。这是一个容易被忽略的细节。

### 2.5 checkpoint 策略

| 触发条件 | 行为 |
|---------|------|
| WAL 达到阈值大小 | 后台执行 |
| 自上次 checkpoint 后写入量达到阈值 | 后台执行 |
| 应用空闲 10 秒 | 后台执行 |
| 应用正常退出 | 执行一次完整 checkpoint |
| 距离上次 checkpoint 超过 5 分钟 | 强制执行 |

**checkpoint 期间**：用户操作不被阻塞（读写继续走 WAL）；checkpoint 可被暂停以让出资源。

### 2.6 崩溃一致性检测

**启动时的检测流程**

```
启动
  ↓
检查是否存在"脏标志"（正常退出时清除，启动时设置）
  ↓
┌─────────────────────────────┐
│ 标志为脏 → 上次未正常退出    │
└─────────────────────────────┘
  ↓
扫描 WAL：找出最后一个完整事务的边界
  ↓
尝试自动恢复（重放已提交事务，丢弃未提交事务）
  ↓
运行一致性检查（完整性检查 + 关键不变量校验）
  ↓
┌──────────────┬──────────────┐
│   通过       │    失败      │
└──────────────┘──────────────┘
  ↓                     ↓
显示恢复报告        进入恢复向导
（含恢复详情）      （从备份/快照恢复）
  ↓                     ↓
清除脏标志          保留原始文件以备人工分析
  ↓
正常使用
```

**恢复报告内容**

```
异常退出恢复报告
─────────────────────────────────────
检测到上次未正常退出：2026-09-17 14:32:07
恢复完成时间：2026-09-17 14:35:22

已重放事务：128 个
已丢弃未提交事务：1 个
检查结果：一致性检查通过 ✔

数据状态：
  最后成功提交：2026-09-17 14:32:06
  可能丢失内容：14:32:06 之后的未提交操作

草稿恢复：
  · 《会议记录》 2 分钟前 1.2 KB   [ 查看 ] [ 恢复 ]
  · 《采购清单》 8 分钟前 340 B    [ 查看 ] [ 恢复 ]

已自动创建事故快照：snapshot-before-recovery-20260917-143522
  [ 查看快照详情 ]   [ 打开快照目录 ]
─────────────────────────────────────
                     [ 完成 ]  [ 查看详细日志 ]
```

**关键设计**

- **不静默恢复**。即使用户不需要做任何操作，也必须显示恢复报告——用户有权知道曾发生过异常。
- **自动创建事故快照**。恢复前的原始状态被完整保留，防止恢复过程本身造成二次损坏。
- **草稿单独呈现**。未提交的编辑内容与事务数据分开处理，因为它们的恢复策略不同（草稿是"尽量恢复"，事务是"要么全有要么全无"）。

## 三、应用层：自动保存与草稿恢复

### 3.1 自动保存

| 内容类型 | 触发时机 | 原子性 |
|---------|---------|-------|
| 笔记正文 | 输入停止 1.5 秒 | 事务提交 |
| 表格单元格 | 编辑完成（失焦/回车） | 事务提交 |
| 数据库记录 | 字段编辑完成 | 事务提交 |
| 看板卡片 | 拖拽结束 | 事务提交 |
| 日历事件 | 编辑面板关闭 | 事务提交 |
| 待办项 | 状态变更即提交 | 事务提交 |
| 设置项 | 变更即保存 | 原子写入 |

**强制保存时机**（不等自动保存间隔）

- 切换页面 / 切换标签
- 窗口失焦超过 30 秒
- 程序准备退出
- 系统发出休眠 / 关机信号
- 检测到即将断电（笔记本电池临界，若系统提供该信号）

### 3.2 草稿机制

| 场景 | 行为 |
|------|------|
| 编辑中长期未提交 | 内容周期性写入草稿区（独立于主库，避免污染事务） |
| 崩溃后重启 | 扫描草稿区，列出可恢复内容让用户选择 |
| 草稿保留 | 恢复后保留 7 天再清理；用户也可立即清理 |
| 草稿隔离 | 草稿区是独立文件，损坏不影响主库 |
| 草稿加密 | 跟随全局加密设置 |

### 3.3 睡眠与休眠

| 事件 | 行为 |
|------|------|
| 系统进入睡眠 | 收到信号 → 强制 checkpoint → fsync → 允许睡眠 |
| 系统从睡眠恢复 | 校验连接与文件句柄有效性，必要时重开 |
| 系统休眠（hibernate） | 同睡眠，但更严格：完整 checkpoint + 关闭 WAL |
| 突然断电 | 依赖 WAL 与崩溃一致性检测 |

## 四、版本历史

### 4.1 分层历史

| 层级 | 粒度 | 触发 | 保留 |
|------|------|------|------|
| **文档版本** | 单篇笔记/文档 | 每 5 分钟或每 50 次编辑 | 默认 90 天，可配 |
| **记录版本** | 数据库单行 | 每次变更（需用户开启，默认关） | 默认 30 天 |
| **结构版本** | 库结构（DDL） | 每次结构变更 | 默认永久保留最近 100 个 |
| **库快照** | 整库 | 自动（每日）/ 手动 | 按备份保留策略 |

### 4.2 历史查看与回滚

| 能力 | 说明 |
|------|------|
| 时间线 | 按时间倒序列出所有版本，显示大小与变更摘要 |
| diff 查看 | 文本内容显示行级差异（新增绿、删除红）；结构化数据显示字段级差异（旧值 → 新值） |
| 单键回滚 | 一键恢复到某版本 |
| 回滚保护 | 回滚前自动创建当前版本的快照（回滚本身可撤销） |
| 版本对比 | 任选两个版本对比 |
| 版本锁定 | 重要版本可锁定，永不自动清理 |
| 版本导出 | 导出某一版本为文件 |

### 4.3 回收站

| 能力 | 说明 |
|------|------|
| 覆盖范围 | 笔记、表格、数据库记录、看板卡片、文件引用、模板、标签 |
| 保留窗口 | 默认 30 天，可配 7 / 30 / 90 / 永久 |
| 恢复 | 一键恢复到原位置 |
| 清空 | 手动清空（二次确认，显示将删除项数与占用空间） |
| 显示 | 显示原位置、删除时间、大小 |
| 自动清理 | 到期自动清理，清理前可选通知 |

## 五、备份体系

### 5.1 备份类型

| 类型 | 说明 | 体积 | 恢复速度 | 默认频率 |
|------|------|------|---------|---------|
| **全量备份** | 完整复制全部数据 | 100% | 最快 | 每周 |
| **增量备份** | 自上次任意备份以来的变化 | 小 | 较慢（需链式恢复） | 每天 |
| **差异备份** | 自上次全量以来的变化 | 中 | 中等 | 每天 |
| **快照** | 某一时刻的完整状态副本 | 100% | 最快 | 手动 + 重要操作前 |
| **时间点恢复** | 基于 WAL/日志回放到任意时间点 | — | 最慢 | 按需 |

**默认策略**：每天增量 + 每周全量 + 关键操作前自动快照。

### 5.2 备份目标

| 目标 | 支持方式 | 默认 |
|------|---------|------|
| 本地目录 | 直接路径 | **是**（默认目标） |
| 移动硬盘 / U 盘 | 直接路径（检测可移动设备，提示拔盘风险） | 可选 |
| NAS（网络共享） | SMB / WebDAV / NFS | 可选 |
| 自托管服务 | 用户自己的服务器 / S3 兼容对象存储 | 可选 |
| 第三方云盘 | **默认不支持，不内置** | 明确不做 |

> **红线**：不默认、不推荐、不内置向任何第三方公有云上传备份。若用户坚持，必须通过显式安装的插件实现，且安装时有明确警告。

### 5.3 备份内容

| 内容 | 是否默认包含 |
|------|-------------|
| 主数据库 | ✅ |
| 附件与截图 | ✅ |
| 版本历史 | ✅ |
| 模板与自定义配置 | ✅ |
| 设置（脱敏后） | ✅ |
| 缓存 | ❌（可重建） |
| 日志 | ❌ |
| 加密密钥 | ❌（**永不备份进备份包**，单独管理） |
| AI 模型文件 | ❌（体积大、可重新下载） |
| 向量索引 | ⚙️ 可选（可重建，默认不含以节省空间） |

### 5.4 备份加密

| 项 | 设计 |
|----|------|
| 默认 | 跟随主库加密状态；用户可单独为备份设置口令 |
| 算法 | AEAD（如 AES-256-GCM 或 ChaCha20-Poly1305） |
| 密钥派生 | 口令 → KDF（Argon2id 或 scrypt）→ 加密密钥；参数按当时硬件能力设定并记录在备份头 |
| 密钥存储 | 不存进备份文件；可用系统密钥链记住（用户可选） |
| 口令丢失 | **数据不可恢复**，必须在设置加密时明确告知，并提供恢复码机制 |
| 恢复码 | 生成一串离线保存的恢复码，可用于重置口令 |

### 5.5 备份完整性

**每个备份必须携带**

```
backup-20260917-020000.deskbase-backup/
├── manifest.json          ← 版本、时间、类型、内容清单、大小
├── checksums.sha256       ← 每个文件的 SHA-256
├── database/              ← 数据库文件
├── attachments/           ← 附件
├── history/               ← 版本历史
├── config/                ← 配置
├── metadata.json          ← 引擎版本、加密参数、压缩算法
└── verify.json            ← 备份完成后自动生成的验证结果
```

**备份完成后的自动验证（默认开启）**

1. 校验所有文件的 SHA-256 与 `manifest.json` 一致
2. 校验备份包可解密（用当前密钥试解一个文件头）
3. 尝试打开备份中的数据库副本并运行完整性检查
4. 把验证结果写入 `verify.json` 与备份索引
5. **验证失败的备份标记为"不可用"并显著告警**

### 5.6 备份保留策略

| 策略 | 默认值 | 说明 |
|------|-------|------|
| 保留份数 | 30 | 超出后删最旧（受锁定保护的不删） |
| 保留时长 | 90 天 | 超期删除 |
| 容量上限 | 无（可设） | 超出后按策略清理 |
| 锁定 | 手动 | 重要备份可锁定，永不自动清理 |
| 清理时机 | 备份完成后 | 清理前后都通知（可关闭通知） |
| 清理确认 | 首次开启自动清理时 | 之后静默执行 |

## 六、恢复体系

### 6.1 恢复来源与优先级

```
优先尝试（自动）：
  ① WAL 重放 + 崩溃一致性恢复        ← 最快，数据最新
  ② 草稿恢复                          ← 恢复未提交的编辑
  ③ 最近快照回滚                      ← 用于误操作场景
  ④ 最近备份恢复                      ← 用于文件损坏场景
  ⑤ 历史版本恢复                      ← 用于局部误改场景
  ⑥ 上一份可用备份                    ← 备份损坏时的降级路径
```

### 6.2 恢复向导

**流程**

```
第 1 步 · 选择恢复源
   ○ 从自动备份恢复          （最近可用：2026-09-17 02:00）
   ○ 从手动备份恢复          （共 3 份）
   ○ 从快照恢复              （共 12 个）
   ○ 从时间点恢复            （选择日期时间）
   ○ 从历史版本恢复          （选择具体文档/记录）
   ○ 从外部文件恢复          （选择 .deskbase-backup 文件或目录）

第 2 步 · 选择恢复方式
   ○ 恢复到新位置      ← 默认推荐：不动现有数据，最安全
   ○ 覆盖当前数据      ← 需二次确认，恢复前自动创建快照
   ○ 合并恢复          ← 只恢复指定表/笔记，处理冲突

第 3 步 · 选择范围（可选）
   ☑ 数据库   ☑ 笔记   ☑ 表格   ☐ 附件   ☑ 配置   ☑ 历史

第 4 步 · 预览（关键步骤）
   在沙箱中打开备份内容，显示：
     · 备份时间与来源
     · 数据规模（表数、记录数、笔记数、附件数）
     · 与当前数据的差异摘要
     · 抽样的内容预览（可浏览但不修改）
   [ 浏览数据 ]  [ 查看差异 ]

第 5 步 · 确认与执行
   显示：将恢复多少数据、将覆盖多少数据、预计耗时
   [ 开始恢复 ]   （覆盖模式需输入 "确认覆盖"）

第 6 步 · 恢复报告
   · 恢复了什么、耗时多久
   · 校验结果
   · 被跳过的内容及原因
   · 恢复后数据的完整性检查结果
```

### 6.3 恢复的失败处理

| 失败情形 | 处理 |
|---------|------|
| 备份文件校验和不符 | 拒绝恢复，说明哪个文件损坏，建议改选其他备份 |
| 备份无法解密 | 提示口令错误；建议尝试恢复码 |
| 恢复中途失败 | 已恢复部分回滚（恢复到新位置时则保留新位置，标记为不完整） |
| 恢复后完整性检查失败 | 保留现场，标记该备份为可疑，回溯上一份可用备份 |
| 空间不足 | 恢复前预检空间，不足时明确说明需要多少 |

## 七、备份健康检查与恢复演练

> 这是本文档开头那句话的落地。

### 7.1 备份健康检查

**触发**：手动（备份模块内按钮）+ 自动（每周一次，可关）

**检查项**

| 检查 | 说明 |
|------|------|
| 备份文件存在性 | 索引中的备份是否都还在 |
| 校验和验证 | 逐文件校验 SHA-256 |
| 可解密性 | 用当前密钥试解密头部 |
| 可读性 | 尝试打开备份中的数据库并运行完整性检查 |
| 链完整性 | 增量/差异备份的父备份是否都还在（否则无法恢复） |
| 空间余量 | 目标磁盘剩余空间是否够存下一份备份 |
| 时间新鲜度 | 最近一次成功备份距今多久（超过阈值告警） |
| 目标可达性 | 备份目标（NAS/U 盘/自托管）是否可达 |

**输出**

```
备份健康检查报告                          2026-09-17 10:00
─────────────────────────────────────────────────────────
整体状态：⚠ 有 1 项需要注意

✔ 备份文件存在性        30/30 份都在
✔ 校验和验证            全部通过（共 4.2 GB）
✔ 可解密性              通过
✔ 可读性                通过（抽查最近 3 份，完整性检查通过）
✔ 链完整性              增量链完整
✔ 空间余量              目标磁盘剩余 120 GB，充足
⚠ 时间新鲜度            最近一次备份：26 小时前（策略为每日）
                       建议：检查计划任务是否被系统阻止
✔ 目标可达性            D:\DeskBaseBackup 可达
─────────────────────────────────────────────────────────
                         [ 立即备份 ]  [ 查看详细报告 ]
```

### 7.2 恢复演练

**目的**：证明备份真的能用。检查校验和只能证明文件没坏，不能证明恢复流程能跑通。

**触发**：手动 + 每季度提醒

**流程**

```
1. 在沙箱目录中（不触碰任何现有数据）
2. 完整执行一次恢复流程（使用最新的可用备份）
3. 对恢复后的数据运行完整性检查
4. 与当前数据进行抽样比对（记录数、表结构、抽查内容）
5. 记录耗时
6. 输出演练报告
7. 清理沙箱（或保留供用户查看，由用户选择）
```

**演练报告**

```
恢复演练报告                              2026-09-17 10:15
─────────────────────────────────────────────────────────
使用备份：backup-20260917-020000（自动全量+增量）
演练结果：✔ 通过

耗时分解：
  解压与解密        12.4 s
  数据库恢复         8.1 s
  附件恢复          21.7 s
  完整性检查         3.2 s
  总计              45.4 s

数据校验：
  表数量            24 / 24  ✔
  记录总数          187,432 / 187,432  ✔
  笔记数量          512 / 512  ✔
  附件数量          2,340 / 2,340  ✔
  抽样内容比对      20/20 一致  ✔

结论：该备份可在 46 秒内完整恢复到可用状态。

下一步建议：
  · 建议至少保留一个异地备份（当前仅 1 个目标）
  · 下次演练建议：2026-12-17
─────────────────────────────────────────────────────────
```

> **演练不做任何"模拟"。** 它执行真实的恢复流程，只是恢复位置在沙箱。这是唯一能证明备份可用的方法。

## 八、灾难恢复（DR）场景矩阵

| 场景 | 影响 | 恢复手段 | 目标 RTO | 目标 RPO |
|------|------|---------|---------|---------|
| 应用崩溃 | 未提交内容 | 崩溃恢复 + 草稿 | < 10 秒 | 最后一次未提交事务 |
| 断电 | 未提交内容 | 崩溃恢复 + 草稿 | < 30 秒 | 最后一次未提交事务 |
| 误删记录/笔记 | 局部数据 | 回收站 → 版本历史 | < 1 分钟 | 0 |
| 误改内容 | 局部数据 | 版本历史回滚 | < 1 分钟 | 0 |
| 误操作（批量改错） | 批量数据 | 快照回滚 | < 5 分钟 | 上次快照 |
| 主库文件损坏 | 全库 | 备份恢复 | < 10 分钟 | 上次备份 |
| 备份文件损坏 | 备份不可用 | 改选其他备份 | < 10 分钟 | 更早的备份点 |
| 数据目录被误删 | 全部 | 备份恢复 | < 15 分钟 | 上次备份 |
| 硬盘物理损坏 | 全部 | 备份恢复（异地） | < 1 小时 | 上次备份 |
| 勒索软件加密 | 全部 | 离线/只读备份恢复 | < 2 小时 | 上次离线备份 |
| 备份目标（NAS）失联 | 无备份产生 | 切换备用目标 | — | — |

**关于勒索软件**：唯一有效的防线是**离线或只读备份**。因此：

- 强烈建议至少一个备份目标为**离线介质**（定期接上的移动硬盘）。
- 备份目标为可写网络位置时，界面提示勒索软件风险。
- 提供「只读备份模式」：备份完成后把文件设为只读，降低被加密的风险（尽力而为，不构成保证）。

## 九、卸载、迁移与备份的关系

### 9.1 卸载时的数据处置

卸载器必须让用户明确选择（见 [12 · 安装与卸载体验](12-installer-and-uninstaller.md)）：

| 选项 | 行为 |
|------|------|
| **保留数据卸载** | 移除程序，保留数据目录、配置、备份。明确告知数据位置 |
| **导出后卸载** | 先执行一次「一键全量导出」，把结果写到用户指定位置，再卸载 |
| **彻底清除卸载** | 二次确认 + 列出将删除的全部内容，之后删除一切 |

### 9.2 迁移（换机）

| 方式 | 步骤 |
|------|------|
| **整目录搬迁** | 复制数据目录 → 新机安装 → 指向该目录。**最简单，推荐** |
| **备份包迁移** | 旧机备份 → 拷贝备份包 → 新机用恢复向导导入 |
| **全量导出迁移** | 导出为开放格式目录 → 新机导入（跨软件迁移时用） |
| **便携版迁移** | 便携版 + 数据目录都在 U 盘 → 插上即用 |

**迁移必须满足**

- 不需要联网
- 不需要登录
- 不经过任何第三方服务器
- 加密数据迁移后仍可用原口令解锁

### 9.3 版本升级时的数据迁移

| 要求 | 说明 |
|------|------|
| 自动迁移 | 打开旧版本数据时自动升级结构 |
| 迁移前备份 | **强制**先创建一份完整备份，失败可回退 |
| 迁移可回滚 | 提供回滚脚本与旧文件保留 |
| 不静默 | 明确告知用户"正在升级数据格式，已先创建备份" |
| 前向兼容声明 | 数据格式变更必须提前一个次版本公告 |

## 十一、不可协商的设计红线

| 红线 | 原因 |
|------|------|
| 备份功能必须在**一级模块**，不得藏进设置 | 核心承诺必须最高可达 |
| 校验和生成与备份后验证**不可关闭** | 无法验证的备份等于没有备份 |
| 覆盖式恢复前必须自动创建快照 | 恢复操作本身不应成为数据丢失的原因 |
| 不默认上传第三方云 | 隐私承诺 |
| 不静默忽略异常退出 | 用户有权知道发生了什么 |
| 不因性能而降低持久性（`fsync` 不可省） | 数据完整性优先于吞吐量 |
| 加密密钥绝不进入备份包 | 否则备份包被拿走 = 数据被拿走 |
| 迁移前必须强制备份 | 数据格式升级是高风险操作 |
| 卸载前必须让用户明确选择数据去留 | 卸载不应意外删数据 |
| 恢复演练必须执行**真实**恢复，不允许模拟 | 模拟无法发现问题 |
