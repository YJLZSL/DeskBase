# 01 · 愿景、边界与核心原则

> 一个产品能不能守住自己，取决于它敢不敢明确说「我不做什么」。

---

## 一、愿景

### 愿景陈述

> **让每个人都能拥有一个真正属于自己的数据仓库——不需要懂数据库，不需要交出隐私，不需要担心数据丢失。**

### 展开

我们相信三件事：

1. **普通人的数据值得被正经对待。**
   一个人的记账、通讯录、客户名单、藏书清单、孩子的体检记录——它们在结构复杂度上不输给小公司的业务库，却通常只被塞进备忘录、Excel 或微信收藏。它们值得一个有类型、有关系、能查询、能备份、能约束的容器。

2. **「简单」和「强大」不该是单选题。**
   传统数据库工具把「表结构、主键、外键、索引、事务」当作前置知识，把大多数人挡在门外。但这些概念不该是入门门槛，而应该是**需要时才能被展开的第二层**。

3. **隐私不是一种功能，而是默认状态。**
   用户不该为了用一个小工具而注册账号、接受隐私政策、交出使用数据。本地优先是一种设计立场，不是营销话术。

### 五年后我们希望听到的评价

> 「我把十年攒下来的东西都放在 DeskBase 里，换过三台电脑，从没丢过，从没被谁看过一眼。」

---

## 二、产品边界

### 2.1 我们要解决的三个核心问题

| # | 问题 | 现状痛点 | DeskBase 的答案 |
|---|------|---------|----------------|
| **P1** | 半结构化信息无处安放 | 备忘录没有结构，Excel 越用越卡，数据库工具太陡 | 用办公工具的形态提供数据库能力 |
| **P2** | 数据散落在十几个工具里 | 笔记一个软件、待办一个软件、截图在系统里、表格在云上 | 一个本地应用承载多类数据，且互相关联 |
| **P3** | 数据安全感缺失 | 云服务可能改政策、涨价、关停；本地文件又怕丢 | 本地优先 + 可验证备份 + 开放格式导出 |

### 2.2 明确的能力边界

**我们做的（In Scope）**

- 单机为主的多类办公数据管理与关联
- 内置轻量但完整的 SQL 能力（单文件库级别）
- 本地优先的备份、恢复与容灾
- 本地 AI 辅助（推理不出网）
- 局域网 / 自托管中继的手机远程访问
- 可审计的插件扩展机制

**我们不做的（Out of Scope）**

| 不做的事 | 理由 |
|---------|------|
| 在线实时协作 | 需要中心化服务与常驻账号，与本地优先冲突 |
| 云端账号与云端订阅 | 会引入强制登录、数据托管与商业压力 |
| 遥测 / 埋点 / 崩溃上报 | 与隐私承诺根本矛盾 |
| 广告、推广、联盟链接 | 侵蚀产品判断力 |
| 多人权限的复杂 RBAC 体系 | 目标用户是个人与极小团队，企业级需求请用企业产品 |
| 分布式数据库 / 集群 / 主从复制 | 属于 DBA 运维工具范畴 |
| 通用多方言 SQL 客户端 | 功能稀释风险高，先做好本地这一件事 |
| 云盘同步作为默认能力 | 同步必须是可选项，且必须自托管或端到端加密 |

### 2.3 边界上的灰色地带（判定规则）

有些需求介于内外之间，用以下规则判定：

| 情形 | 判定 | 规则 |
|------|------|------|
| 用户想在两台自己的电脑间同步 | **做**，但必须是可选、可自托管、端到端加密 | 同步能力涉及「用户自己的数据」，不涉及托管 |
| 用户想邀请同事一起看一张表 | **不做核心，交给导出** | 涉及多用户与托管，属于协作范畴 |
| 用户想用公司自建的大模型 API | **做**，走外部 AI 授权流程 | 用户显式选择，且需逐次确认与脱敏 |
| 用户想连公司 MySQL 做运营分析 | **不做核心，插件化** | 属于通用数据库客户端范畴，可作插件 |
| 用户想要手机 App | **做远程端**，不做独立云端 App | 手机端是桌面端的安全遥控器，不是独立数据源 |

### 2.4 边界维护机制

边界不是一成不变的，但变动成本很高。任何打破上述边界的提议：

1. 必须走 **RFC**（见 [CONTRIBUTING.md](../CONTRIBUTING.md) 第十一节）；
2. 必须论证它不会稀释 P1/P2/P3 的解决力度；
3. 必须说明它对「隐私承诺」与「零污染承诺」的影响；
4. 需 2/3 维护者同意（L3 决策，见 [GOVERNANCE.md](../GOVERNANCE.md)）。

## 三、核心原则

十条原则，按重要性排序。**排序靠前的原则优先于靠后的原则**——冲突时按序取舍。

---

### 原则 1 · 本地优先（Local-First）

**含义**
数据的主副本永远在用户设备上。应用在无网络时功能不缩水。

**具体要求**

- 首启不要求登录、不要求联网、不要求激活。
- 全部核心功能（笔记、表格、数据库、截图、备份、本地 AI）在断网下完整可用。
- 网络是**例外状态**，不是默认状态。程序启动时不得静默建立任何外部连接。
- 数据目录与程序目录可分离，且整个数据目录可整体搬移。

**反例（不允许出现）**

- ❌ 首次启动强制检查更新才能继续
- ❌ 登录后才能使用本地笔记
- ❌ 联网失败导致界面报错
- ❌ 把用户的文件路径、使用时长发到服务器

**验证方式**
在完全断网的虚拟机中安装并完成一次完整使用闭环（建库 → 导入 → 查询 → 截图 → 备份 → 恢复）。

---

### 原则 2 · 渐进式复杂度（Progressive Disclosure）

**含义**
新手看到的是 5 个入口，高级用户看到的是 50 个。中间不是一道墙，而是一根滑杆。

**具体要求**

- 一级模块的可见项默认 **不超过 7 个**。
- 高级功能默认折叠，折叠处必须标注「可能影响稳定性或隐私」。
- 提供明确的**模式切换**：`简洁模式` / `高级模式`，切换后界面元素渐进展开，不丢失任何数据。
- 同一份数据提供两套操作路径（如建表：可视化设计器 / DDL 编辑器），内部使用同一套模型。
- 每个复杂功能旁必须有 **「这是什么？」** 的入口，一点开就是通俗解释。

**判定标准**
> 一个新用户在不读任何文档的情况下，能否在 10 分钟内完成"记一条笔记 + 建一张清单 + 截一张长图"？

**反例**

- ❌ 主界面上同时出现 30 个按钮
- ❌ 用「高级模式」隐藏了破坏性操作，但不加警示
- ❌ 新手模式阉割数据能力（导致用户升级后要重建数据）

---

### 原则 3 · 零污染（Zero Footprint）

**含义**
装了能干净卸掉，便携版换机即用。系统不该因为装过这个软件而留下任何痕迹。

**具体要求**

| 形态 | 承诺 |
|------|------|
| 便携版 | 不写注册表、不写系统目录、不装服务、不建计划任务、不改文件关联、不装驱动、不开机自启 |
| 安装版 | 只写入卸载所必需的最小注册表项，卸载时 100% 删除 |
| 两者共同 | 不捆绑、不静默安装第三方组件、不强制重启、不强制登录、不强制联网 |

**具体清单（卸载后必须为 0）**

- 残留目录（程序目录、数据目录、缓存、日志、临时文件）
- 残留注册表项
- 残留服务 / 驱动
- 残留计划任务
- 残留开机启动项
- 残留防火墙规则
- 残留文件关联
- 残留后台进程与句柄

**反例**

- ❌ 「为了加速启动」偷偷注册一个后台常驻服务
- ❌ 卸载后 `%AppData%` 里还留着一个 500 MB 的缓存
- ❌ 安装时默认勾选「创建桌面快捷方式 + 关联 8 种文件类型 + 开机自启」

---

### 原则 4 · 默认最克制（Privacy by Default）

**含义**
所有开关的默认值都指向「更少权限、更少联网、更少驻留」。

**具体要求**

| 开关 | 默认值 |
|------|-------|
| 遥测 / 埋点 / 崩溃上报 | **关闭**，且不提供开启入口（根本不存在） |
| 自动更新检查 | 关闭（用户可手动检查） |
| 远程访问 | 关闭 |
| 局域网发现 | 关闭 |
| AI 外部服务 | 关闭，且需逐次授权 |
| 云端同步 | 关闭 |
| 安装时创建快捷方式 | 桌面：不勾 / 开始菜单：勾（可在安装向导修改） |
| 安装时关联文件 | 不勾 |
| 开机自启 | 不勾 |
| 数据库加密 | **首启时询问**，解释利弊后由用户选择，不替用户决定 |
| 数据目录 | 默认用户目录下的独立文件夹，可改；便携版默认程序目录 |
| 备份 | 自动备份**开启**（因为"不丢数据"优先级高于"最少活动"），但备份位置默认在本地数据目录旁，不上云 |

> **注**：自动备份默认开启是一个刻意的例外。原则 5（不丢数据）在排序上高于原则 10（安静），且备份完全本地、不产生网络活动，不违反隐私承诺。

**反例**

- ❌ 「为了改善产品」默认开启使用数据收集
- ❌ 安装向导所有选项默认全勾选
- ❌ 默认开启远程访问且无密码

---

### 原则 5 · 不丢数据（Durability First）

**含义**
用户把真实工作托付在这里，丢数据是不可接受的失败。

**具体要求**

- **存储层**：事务 + WAL（或等价机制）+ 原子写入 + `fsync` + 定期 checkpoint + 崩溃一致性检测。
- **异常处理**：检测到上次异常退出，下次启动**必须**进入恢复向导，而不是静默忽略。
- **编辑层**：笔记 / 文档 / 表格 / 记录级自动保存（间隔可配），崩溃后草稿可恢复。
- **版本层**：文档与记录级版本历史，可查看 diff、可回滚。
- **删除层**：回收站 + 误删恢复，默认保留窗口可配。
- **备份层**：自动备份、手动备份、快照、时间点恢复。
- **验证层**：备份健康检查 + 恢复演练——**没做过恢复演练的备份不算备份**。

**验收方式**
写入过程中强杀进程 100 次，第 101 次启动后数据库通过完整性校验，且最多丢失最后一个未提交事务。

**反例**

- ❌ 崩溃后直接重建空数据库
- ❌ 自动保存只在正常退出时触发
- ❌ 备份失败但静默不提示
- ❌ 恢复时发现备份文件已损坏，且没有第二个可用的备份

---

### 原则 6 · AI 不出网（AI Stays Local）

**含义**
AI 是助手，不是数据泄露通道。

**具体要求**

- 默认使用**本地模型**推理。模型文件可离线下发或从可信来源校验后下载。
- 模型、向量索引、对话记录、临时推理数据**全部本地存储**。
- **禁止**默认调用云端 AI API。
- 若用户主动配置外部 AI 服务：显式授权 + 逐次确认 + 可脱敏 + 可审计 + 可完全关闭。
- 每次外发前提供 **脱敏预览**——明确显示实际将发送的文本内容。
- AI 对外部数据的访问必须**受权限约束**：默认只能访问用户当前显式指定的数据范围。

> 详见 [09 · 本地 AI 架构](09-local-ai.md)。

---

### 原则 7 · 可审计（Auditable）

**含义**
用户和第三方都应能验证这个软件到底做了什么。

**具体要求**

- 依赖固定版本，锁文件入库。
- 每次发布生成 **SBOM**（SPDX / CycloneDX 格式）。
- 提供**可复现构建**说明，并在 CI 中验证构建可复现性。
- 发布包提供数字签名与 SHA-256 校验和。
- 程序内提供「**我本机存了什么**」视图：列出全部数据目录、缓存、日志、临时文件及其大小与用途。
- 提供**审计日志**：记录全部网络请求（目标、时机、触发原因）、全部提权操作、全部外部数据访问。
- 插件必须声明权限清单，权限范围可在界面上查看与撤销。

**反例**

- ❌ 依赖使用 `latest` 标签
- ❌ 发布包无签名
- ❌ 用户无法知道程序在哪些目录写了文件

---

### 原则 8 · 可迁移（No Lock-in）

**含义**
用户随时可以带着数据离开，且不需要这个软件也能读到自己的数据。

**具体要求**

- 全部用户数据可导出为**开放格式**：CSV、JSON、Markdown、SQL、标准图片格式。
- 主数据库文件采用**标准或开放格式**，第三方工具可直接读取。
- 提供「**一键全量导出**」：把笔记、表格、数据库、附件、配置一次性打包成人类可读的目录结构。
- 不设计任何需要联网验证才能读取的加密格式（除非用户主动选择并明确知晓）。
- 插件不得引入私有托管依赖。

> 注意：如果用户选择了强加密，可迁移性会受口令保护约束——这是用户的选择，但必须在开启加密时明确告知「口令丢失 = 数据不可恢复」。

---

### 原则 9 · 分区清晰（Clear Information Architecture）

**含义**
每个功能都有唯一且明确的归属地；用户永远不会问「那个功能到底在哪儿」。

**具体要求**

- 三层结构：一级模块 → 二级功能 → 三级设置。
- 一个功能只属于一个一级模块（横切能力除外，见下）。
- 明确禁止的错位：
  - ❌ 截图放进数据库模块
  - ❌ 备份藏在设置深处
  - ❌ OCR 塞进 AI 模块（OCR 属办公工具，AI 只是可选增强）
  - ❌ 快捷键设置散落在各功能页
- **横切能力**（全局搜索、命令面板、最近使用、收藏、通知、帮助）不归属任何单一模块，但必须在每处可达且行为一致。
- AI 隐私开关在两处可见（AI 模块 + 隐私设置），状态双向同步。

> 完整结构见 [03 · 信息架构](03-information-architecture.md)。

---

### 原则 10 · 安静（Quiet by Default）

**含义**
一个好工具应该像空气——用的时候在，不用的时候不存在。

**具体要求**

- 空闲 CPU 平均 ≤ **0.3%**，不允许出现周期性轮询尖峰。
- 禁止秒级轮询。需要定期做的事（如备份检查）必须有合理间隔、可合并、可暂停、且在系统休眠时自动延后。
- 空闲内存 ≤ **180 MB**。
- 退出后不残留任何后台进程、服务、计划任务、驱动、系统钩子。
- 不注册全局键盘钩子以外的系统级钩子；快捷键钩子必须可在设置中关闭。
- 日志自动轮转，临时文件自动清理，缓存有硬性容量上限。
- 不申请超出功能的权限（不申请麦克风除非用户开启语音转写）。

**验收方式**
装好后静置 30 分钟，用系统性能监视器记录 CPU / 内存 / 磁盘 IO / 网络 IO 曲线；退出后检查进程表、服务表、计划任务表、防火墙规则表。

## 四、原则冲突时的取舍

冲突不可避免。以下是预设的取舍规则：

| 冲突 | 取舍 | 理由 |
|------|------|------|
| 本地优先 vs 便利性（如云端自动同步） | **本地优先** | 便利可以靠可选的同步功能补，隐私丢了补不回来 |
| 不丢数据 vs 安静（自动备份会占资源） | **不丢数据**，但备份必须可配置、可暂停、低开销 | 数据丢失不可逆；资源占用可优化 |
| 渐进式复杂度 vs 功能全面 | **渐进式**，把高级功能折叠而非删除 | 隐藏 ≠ 阉割，用户升级路径不能有断层 |
| 零污染 vs 开机自启这类便利 | **零污染**，自启默认关闭且可选项 | 原则 3 排序高于便利性 |
| 可迁移 vs 强加密 | 用户选择强加密时，**明确告知代价**并强化恢复手段（恢复码、多密钥托管选项） | 这是用户的知情选择，不是我们的隐瞒 |
| 功能速度 vs 隐私承诺 | **隐私承诺** | 宁可少发一个特性 |

## 五、如何判断一个决策是否符合本原则

给维护者和贡献者一把尺子。面对一个设计选择时，依次问：

1. **它会让数据离开用户的设备吗？** 会 → 必须是可选项且默认关闭。
2. **它会写注册表 / 装服务 / 建计划任务 / 加自启吗？** 会 → 必须可在安装时拒绝，且卸载时彻底清除。
3. **它会让新用户第一次打开时看到更多东西吗？** 会 → 必须折叠进高级模式。
4. **它会让崩溃后有数据不可恢复吗？** 会 → 重新设计。
5. **它会让用户更难看懂自己在哪、数据在哪吗？** 会 → 信息架构有问题。
6. **它会在空闲时占资源吗？** 会 → 必须有合理间隔、可暂停、可关闭。
7. **它会让数据更难导出吗？** 会 → 必须补一条导出路径。
8. **它能否被第三方审计？** 不能 → 说明理由，若无正当理由则不做。

八问全过，才进入实现讨论。
