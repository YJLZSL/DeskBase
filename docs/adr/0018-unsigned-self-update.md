# 0018 · 无签名前提下的自更新（取代 ADR-0016 的「不做自替换」一条）

- **状态**：**已接受**（2026-09-19 发起人决定）
- **日期**：2026-09-19
- **取代**：`ADR-0016` 「补充决定」表中「**下载并自替换 exe：不做，且在本决定改变前不得做**」一行。
  ADR-0016 的其余结论（默认关闭、用户可见、可中止、可回滚、全程审计、不碰数据）**继续有效**。

---

## 背景

ADR-0016 的补充决定是：不购买代码签名证书 → **不做自替换**。理由是外部调研的原话 ——
*"一个未签名的更新通道，比它本来要去修的那些 bug 更危险"*：在没有办法验证"下载到的二进制
是不是真来自本项目"之前实现自更新，等于给攻击者开一个正门。

2026-09-19 发起人明确指示：**不用 MirrorChyan（第三方分发平台），直接 GitHub 下载替换。**

这条指示改变了上面的权衡，但**没有改变那个风险本身** —— 它是被"接受"了，不是消失了。
本 ADR 的职责就是把"接受"写清楚：接受的是哪一部分、用什么补偿、残余风险是什么、
以及哪些补偿是**不可再让步**的。

---

## 决策

### 1. 做自替换，但校验链一步都不能省

没有签名的情况下，能做的校验就是下面这五步，**全部通过才允许替换**：

| # | 检查 | 防的是 |
|:-:|------|--------|
| 1 | 只从 `api.github.com/repos/YJLZSL/DeskBase/releases/latest` 取版本与资产清单，**下载源的 URL 不接受任何配置**（写死在代码里） | 把下载地址变成注入点 |
| 2 | 资产名必须严格匹配 `deskbase-<版本>-windows-x64-portable.zip`，且 API 报告的 `size` 与实下载字节数一致 | 抓错文件、下到半截 |
| 3 | 下载 Release 里配套的 `.sha256` 资产，逐字节比对 | 传输损坏、CDN 缓存串包 |
| 4 | 打开 zip，**必须**含 `deskbase.exe` 与 `README.md`；从 zip 里的说明读出它自报的版本，必须等于资产名里的版本 | 内容与名字不符（改名 arm64→x64 这类） |
| 5 | 解压后的 exe 必须是有效 PE，且其内嵌版本等于目标版本 | 最终落地的那一个文件是真的 |

任何一步不过 → 中止、删除临时目录、**保持程序原状态**，并把原因写进审计日志。

### 2. 诚实标注：这不是签名的替代品

**第 3 步的 SHA-256 与第 2 步的资产清单来自同一个 Release。** 如果 GitHub 账号被攻破、
或 Release 被人替换成"新版本 + 配套的新哈希"，**整条校验链会一起失效**。

这不是可以靠工程手段补上的缺口 —— 它是"不购买证书"的**已知代价**。因此：

- 界面与 `README` 必须写明这一条，措辞不许含糊
- 设置页必须显示"本程序自己下载的更新无法验证发布者身份"这句原话
- 无签名的 exe 仍会被 SmartScreen 拦截 —— 这是**不会因为下载方式改变而消失**的

### 3. 默认关闭，三步各自确认

继承 ADR-0005 与 ADR-0016：**默认零网络行为**。三档开关：
`从不检查`（默认）/ `只检查并提醒` / `检查并在询问后替换`。

即使开到第三档，**检查、下载、替换仍各自要用户点一次确认**，且替换前必须展示：
从哪个版本到哪个版本、将替换哪些文件、数据目录不受影响。

### 4. 替换方式：用同一份 exe 的 `--apply-update` 模式，不引入第二个二进制

主进程退出后由 `deskbase.exe --apply-update <暂存目录>` 完成替换。理由：

- **不新增产物**：不加第二个 exe，也不用 `.ps1` / `.bat`
  —— 本机踩过"脚本文件 + 非 ASCII 路径 = 编码损坏"，而安装目录里带中文是常态
- 同一份 exe 意味着"版本对不对"在替换前后是同一个判断逻辑

替换流程：等旧进程退出 → 把当前 exe 备份为 `deskbase.exe.bak-<旧版本>` →
覆盖程序文件（exe / README / LICENSE / 便携版说明）→ 重启 → 校验能起来；
任一步失败则从 `.bak-*` 回滚。

### 5. 数据零风险（结构性优势，要守住）

DeskBase 的数据在 `%USERPROFILE%\DeskBaseData`，**与程序目录分离**。
替换只动程序文件，一个数据文件都不碰 —— MAA 那个"全量包会清理安装目录同级文件、
必须装在独立文件夹"的坑，我们天然没有。

**这条是红线**：`--apply-update` 只允许写程序目录，任何指向数据目录的路径都必须拒绝。

### 6. 下载源：只用官方 API，不接第三方镜像

发起人 2026-09-19 明确：**不用 MirrorChyan**。对应地：

- 不引入任何第三方分发/加速服务（它要求连第三方域名，与 ADR-0005「网络默认关闭」
  和「不泄露」两条承诺正面冲突）
- 国内网络下 `github.com` 可能不可达 —— 这是**已知限制**，界面在检查失败时要如实说明
  "连不上 GitHub，可以手动到发布页下载覆盖"，而不是假装网络没问题

### 7. 与 ADR-0016 第 7b 节的一处**有理由的偏离**

ADR-0016 定的技术路线是"清单放 Release 上的静态 `update.json`"。本 ADR 改为
**直接读 Releases API**，理由：

- API 给出的信息是清单的超集（资产名、`size`、`asset_id`、`browser_download_url`），
  再加一份 `update.json` 就多一个**可能与实际产物不一致**的文件
  —— 本项目刚因为同类问题吃过亏（`Cargo.lock` 的版本号没跟上 `Cargo.toml`）
- 下载可以走 `GET /repos/.../releases/assets/<id>`（`Accept: application/octet-stream`），
  **连下载请求的第一跳也落在 `api.github.com`**

其余路线结论不变：自研最小更新器、不引第三方框架、不做差分（5.9 MB 全量包不值得）。

## 备选方案

| 方案 | 否决理由 |
|------|---------|
| 继续只做"检查并提醒" | 发起人已决定改；对非程序员用户，"自己下载覆盖"等于没有更新 |
| 接 MirrorChyan（免费检测 + 付费下载） | 发起人 2026-09-19 明确不用；且要连第三方域名，与 ADR-0005 冲突 |
| 买证书后做真正的签名校验 | 不排斥，是**首选未来**。证书到位后按 ADR-0016 第 2 节补上 WinVerifyTrust，本 ADR 的第 1 节降级为"签名之外的额外检查" |
| 引入第三方更新框架（WinSparkle 等） | 同 ADR-0016 方案 B：带进自己的网络栈与遥测点，行为不受 ADR-0005 约束 |

## 影响与待实测

| 新模块 | `app/src/updater.rs`（检查 / 下载 / 校验 / 暂存 / 替换 / 回滚） |
| IPC | `app.updateCheck`、`app.updateDownload`、`app.updateApply`、`app.updateState` |

| 依赖 | 需要 HTTPS 客户端。**未实测**用系统 WinHTTP 还是引 HTTP crate；两者都要过体积守卫（阈值 10 MB） |
| 体积增量 | **未实测**，目标 ≤ 150 KB |
| 必须配的测试 | 版本比较、五步校验的**逐一失败路径**、`--apply-update` 的备份与回滚、拒绝写数据目录 |
| 残余风险 | 见第 2 节：无签名 → 无法验证发布者身份。**这条不会因为本 ADR 而消失** |

## 复核条件

1. 代码签名证书到位 → 按 ADR-0016 第 2 节补签名校验，本 ADR 第 1 节退为附加检查
2. 引入 HTTP 客户端依赖（体积与网络行为需重新评估）
3. 出现任何一次"校验通过但包是错的"实例 → 立即停做自替换，回到只提醒
4. ADR-0005 被修订
