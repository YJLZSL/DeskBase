# 0018 · 无签名前提下的自更新（取代 ADR-0016 的「不做自替换」一条）

- **状态**：**已接受**（2026-09-19 发起人决定）
- **日期**：2026-09-19
- **取代**：`ADR-0016` 「补充决定」表中「**下载并自替换 exe：不做，且在本决定改变前不得做**」一行。
  ADR-0016 的其余结论（默认关闭、用户可见、可中止、可回滚、全程审计、不碰数据）**继续有效**。

---

## 背景

ADR-0016 的补充决定是：不购买代码签名证书 → **不做自替换**。理由是外部调研的原话 ——
*"一个未签名的更新通道，比它本来要去修的那些 bug 更危险"*：在没有办法验证"下载到的二进制
是不是真来自本项目"之前实现自更新，等于给攻击者开一个正门。

2026-09-19 发起人明确指示：**不用 MirrorChyan（第三方分发平台），直接 GitHub 下载替换。**

这条指示改变了上面的权衡，但**没有改变那个风险本身** —— 它是被"接受"了，不是消失了。
本 ADR 的职责就是把"接受"写清楚：接受的是哪一部分、用什么补偿、残余风险是什么、
以及哪些补偿是**不可再让步**的。

---

## 决策

### 1. 做自替换，但校验链一步都不能省

没有签名的情况下，能做的校验就是下面这五步，**全部通过才允许替换**：

| # | 检查 | 防的是 |
|:-:|------|--------|
| 1 | 只从 `api.github.com/repos/YJLZSL/DeskBase/releases/latest` 取版本与资产清单，**下载源的 URL 不接受任何配置**（写死在代码里） | 把下载地址变成注入点 |
| 2 | 资产名必须严格匹配 `deskbase-<版本>-windows-x64-portable.zip`，且 API 报告的 `size` 与实下载字节数一致 | 抓错文件、下到半截 |
| 3 | 下载 Release 里配套的 `.sha256` 资产，逐字节比对 | 传输损坏、CDN 缓存串包 |
| 4 | 打开 zip，**必须**含 `deskbase.exe` 与 `README.md`；从 zip 里的说明读出它自报的版本，必须等于资产名里的版本 | 内容与名字不符（改名 arm64→x64 这类） |
| 5 | 解压后的 exe 必须是有效 PE，且其内嵌版本等于目标版本 | 最终落地的那一个文件是真的 |

任何一步不过 → 中止、删除临时目录、**保持程序原状态**，并把原因写进审计日志。

### 2. 诚实标注：这不是签名的替代品

**第 3 步的 SHA-256 与第 2 步的资产清单来自同一个 Release。** 如果 GitHub 账号被攻破、
或 Release 被人替换成"新版本 + 配套的新哈希"，**整条校验链会一起失效**。

这不是可以靠工程手段补上的缺口 —— 它是"不购买证书"的**已知代价**。因此：

- 界面与 `README` 必须写明这一条，措辞不许含糊
- 设置页必须显示"本程序自己下载的更新无法验证发布者身份"这句原话
- 无签名的 exe 仍会被 SmartScreen 拦截 —— 这是**不会因为下载方式改变而消失**的

### 3. 默认关闭，三步各自确认

继承 ADR-0005 与 ADR-0016：**默认零网络行为**。三档开关：
`从不检查`（默认）/ `只检查并提醒` / `检查并在询问后替换`。

即使开到第三档，**检查、下载、替换仍各自要用户点一次确认**，且替换前必须展示：
从哪个版本到哪个版本、将替换哪些文件、数据目录不受影响。

### 4. 替换方式：用同一份 exe 的 `--apply-update` 模式，不引入第二个二进制

主进程退出后由 `deskbase.exe --apply-update <暂存目录>` 完成替换。理由：

- **不新增产物**：不加第二个 exe，也不用 `.ps1` / `.bat`
  —— 本机踩过"脚本文件 + 非 ASCII 路径 = 编码损坏"，而安装目录里带中文是常态
- 同一份 exe 意味着"版本对不对"在替换前后是同一个判断逻辑

替换流程：等旧进程退出 → 把当前 exe 备份为 `deskbase.exe.bak-<旧版本>` →
覆盖程序文件（exe / README / LICENSE / 便携版说明）→ 重启 → 校验能起来；
任一步失败则从 `.bak-*` 回滚。

### 5. 数据零风险（结构性优势，要守住）

DeskBase 的数据在 `%USERPROFILE%\DeskBaseData`，**与程序目录分离**。
替换只动程序文件，一个数据文件都不碰 —— MAA 那个"全量包会清理安装目录同级文件、
必须装在独立文件夹"的坑，我们天然没有。

**这条是红线**：`--apply-update` 只允许写程序目录，任何指向数据目录的路径都必须拒绝。

### 6. 下载源：只用官方 API，不接第三方镜像

发起人 2026-09-19 明确：**不用 MirrorChyan**。对应地：

- 不引入任何第三方分发/加速服务（它要求连第三方域名，与 ADR-0005「网络默认关闭」
  和「不泄露」两条承诺正面冲突）
- 国内网络下 `github.com` 可能不可达 —— 这是**已知限制**，界面在检查失败时要如实说明
  "连不上 GitHub，可以手动到发布页下载覆盖"，而不是假装网络没问题

### 7. 与 ADR-0016 第 7b 节的一处**有理由的偏离**

ADR-0016 定的技术路线是"清单放 Release 上的静态 `update.json`"。本 ADR 改为
**直接读 Releases API**，理由：

- API 给出的信息是清单的超集（资产名、`size`、`asset_id`、`browser_download_url`），
  再加一份 `update.json` 就多一个**可能与实际产物不一致**的文件
  —— 本项目刚因为同类问题吃过亏（`Cargo.lock` 的版本号没跟上 `Cargo.toml`）
- 下载可以走 `GET /repos/.../releases/assets/<id>`（`Accept: application/octet-stream`），
  **连下载请求的第一跳也落在 `api.github.com`**

其余路线结论不变：自研最小更新器、不引第三方框架、不做差分（5.9 MB 全量包不值得）。

## 补充（2026-09-19 实测修正：取数接口不再是 `/releases/latest`）

第 1 节第 ① 步写的是"只从 `api.github.com/repos/YJLZSL/DeskBase/releases/latest` 取"。
**实现前实测发现这个接口在本仓库上不可用**：

```
GET /repos/YJLZSL/DeskBase/releases/latest      → 404 Not Found
GET /repos/YJLZSL/DeskBase/releases?per_page=20 → 200，返回 4 个 Release
    v0.2.0-beta.3  draft=false  prerelease=true  assets=3
    v0.2.0-beta.2  draft=false  prerelease=true  assets=3
    v0.2.0-beta.1  draft=false  prerelease=true  assets=3
    v0.1.0-alpha.1 draft=false  prerelease=true  assets=3
```

**原因**：GitHub 的 `/releases/latest` 语义是"**最近一个非预发布**的 Release"。
本仓库**迄今四个发布全部是** `prerelease: true`（我们一直按 alpha/beta 发），
所以它永远 404。

**如果照原样实现，每个用户点"检查更新"都会看到一个 404**，而且这个错误看起来
像是网络问题 —— 排查起来会很费劲。这正是"先实测再实现"的价值。

**修正**：

1. 取数改为 `GET /repos/YJLZSL/DeskBase/releases?per_page=20`，**按版本号自己挑最高的一个**
2. 增加**通道**概念，且通道必须显式：
   - `稳定通道`（默认）：只看 `prerelease = false` 的
   - `测试通道`：连预发布一起看
3. **没有稳定版时不许含糊过去**：稳定通道下若只找到预发布，要明确告诉用户
   "还没有正式版；现在只有测试版 vX（想跟进测试版请在设置里切换通道）"，
   而不是报 404、也不是把 beta 当正式版装上去
4. 仍然过滤 `draft = true`（草稿不该被任何人拿到）
5. 第 1 节其余四步（严格同名、size 一致、SHA-256、包布局、`--version` 核对）**一字不改**

> 夹具：真实响应（去掉 body 等体积字段，字段名与类型与 API 一致）已存进
> `testdata/github-releases-sample.json`，解析逻辑对着它测 —— 不对着想象测。

## 备选方案

| 方案 | 否决理由 |
|------|---------|
| 继续只做"检查并提醒" | 发起人已决定改；对非程序员用户，"自己下载覆盖"等于没有更新 |
| 接 MirrorChyan（免费检测 + 付费下载） | 发起人 2026-09-19 明确不用；且要连第三方域名，与 ADR-0005 冲突 |
| 买证书后做真正的签名校验 | 不排斥，是**首选未来**。证书到位后按 ADR-0016 第 2 节补上 WinVerifyTrust，本 ADR 的第 1 节降级为"签名之外的额外检查" |
| 引入第三方更新框架（WinSparkle 等） | 同 ADR-0016 方案 B：带进自己的网络栈与遥测点，行为不受 ADR-0005 约束 |

## 实测补记（2026-09-19，实现过程中）

### ① 体积：整条更新链约 **+21.5 KB**

| 时点 | release 产物 | 说明 |
|------|-------------|------|
| 加特性之前 | 6 276 096 字节（5.985 MB） | 基线 |
| 只声明特性、还没调用 | 6 275 584 字节 | Cargo.lock 无变化，**不新增任何包** |
| ⚠️ 只加了代码、**还没有调用方** | 6 275 584 字节 | **这个数字是假的**，见下 |
| **代码真正可达之后**（接上 `app.updateCheck`） | **6 297 600 字节（6.006 MB）** | **+22 016 字节 ≈ +21.5 KB** |

> **为什么第三行是个假数字（这值得记下来）**：那时候更新器整体还没有调用方，
> 而 release 构建**会把这些死代码整个优化掉** —— 于是"体积没变"看起来像"WinHTTP 不要钱"，
> 其实只是**根本没被编进去**。真正的代价要等代码可达才量得到。
>
> 正确的测法很简单：**先让它可达，再量**。所以顺序是"接 IPC → 重新量"，
> 而不是"量完再决定要不要接"。
>
> 教训与 `docs/adr/0018` 之外那些"靠眼熟判断"的坑是同一类：
> **测出来的数字也要问一句"我测的到底是什么"**。

**+21.5 KB 这个代价可以接受**：ADR 里写的目标是 ≤150 KB，实际用掉七分之一。
而且这是**一次性**的 —— 再往更新器里加功能（下载、暂存、替换）不会改变"WinHTTP 已链入"这个事实。

**为什么不引纯 Rust HTTP crate**：HTTPS 必然要 TLS。用系统 WinHTTP 时，
winhttp.dll 在操作系统里，我们只付胶水代码的钱；引 rustls 是把**整个 TLS 实现静态链进来**
（上 MB 量级），对一个更新器来说完全不划算。

> **诚实标注**：第一步只证明"**声明是免费的**"，不证明"用起来是免费的" ——
> 真正的代价在调用处。采用 WinHTTP 的关键理由是 winhttp.dll 是**系统 DLL**，
> 只有导入表与我们的胶水代码计入体积；而引 rustls 是把整个 TLS 实现静态链进来。

### ② 一个把错误码逼出来的坑：`PCWSTR` 必须带结尾 NUL

第一版把 Rust 字符串转宽字符时没有补 `\0`，`WinHttpOpenRequest` 直接返回
`ERROR_INVALID_PARAMETER(87)`。原因是 `PCWSTR` 按 **NUL 结尾**读，
不带 NUL 的缓冲区会让 WinHTTP 读到缓冲区之外。报 87 而不是崩溃，属于运气好。

**真正让这个坑快速定位的，是把 Win32 错误码带进错误信息里。**
第一版只写了"构造请求失败"，只能靠猜；补上 `GetLastError()` 后一次就找到。
所以现在所有 WinHTTP 失败路径都带错误码与人话解释（`explain()`）。

（配套的相反规则：给 `WinHttpSendRequest` 的头部切片**不能带 NUL** ——
windows-rs 把 `slice.len()` 当字符数传，多一个 NUL 会被当成头的最后一个字符。
代码里用 `wide()` / `wide_len()` 两个函数把这两条相反的规则分开写清。）

### ③ 未认证的 GitHub API 有硬限流：60 次/小时/出口 IP

实测拿到：`{"message":"API rate limit exceeded for 47.131.183.139. ..."}`

注意那个 IP 是**代理的出口 IP** —— 本实现用 `WINHTTP_ACCESS_TYPE_AUTOMATIC_PROXY`
（读系统代理，本机开着 Clash 时能自己走对路），代价是**出口 IP 与他人共享**，
配额更容易被别人用光。

**这条直接约束了"检查更新"的设计**（已体现在实现里）：

- 检查必须**低频**（每次启动至多一次，结果要缓存），不能做成轮询
- 错误信息必须能区分"限流"与"网络不通" —— 前者等一会儿就好，后者要用户去处理
- **非 200 的响应体要一起带出来**：限流的原因就写在响应体里，少了它只剩一个干巴巴的 403

### ④ 网络传输已实测跑通

`fetch_releases()` 发起真实请求并拿到 GitHub 的结构化响应（含限流时的 JSON 错误体），
证明 **TLS、系统代理、重定向、请求头、状态码、读响应体**这条链路是通的。

该验证是一条 `#[ignore]` 的手动测试（`cargo test -- --ignored`）。理由：
网络不可靠，**一个"有时红有时绿"的测试最后一定会被无视掉 —— 那比没有测试更糟**。
所以它只容忍"限流"这一种**可识别**的情况，其它错误（DNS / TLS / 404 / 解析失败）一律算失败。

## 复核条件

1. 代码签名证书到位 → 按 ADR-0016 第 2 节补签名校验，本 ADR 第 1 节退为附加检查
2. 引入 HTTP 客户端依赖（体积与网络行为需重新评估）
3. 出现任何一次"校验通过但包是错的"实例 → 立即停做自替换，回到只提醒
4. ADR-0005 被修订
