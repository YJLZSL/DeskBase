# ADR-0016: 程序内更新：默认关闭、显式开启、强制签名校验、更新不碰数据

- **状态**：提议（2026-09-18 起草，**待发起人确认**——它放宽了"手动检查更新"的现状）
- **日期**：2026-09-18
- **决策者**：核心维护者（待确认）
- **相关**：[ADR-0005 网络访问默认关闭](0005-network-closed-by-default.md)、[ADR-0015 分发与安装器策略](0015-distribution-and-installer-strategy.md)、[docs/12 安装与卸载](../12-installer-and-uninstaller.md)

---

## 背景

用户提出：想要**自动更新**。这与 ADR-0005「网络默认关闭」看起来冲突，但实际不冲突——
ADR-0005 第 2 条已经把「检查更新」列为**独立开关、默认关闭、提供手动检查**。
也就是说红线留了口子，缺的是"这个开关打开之后，更新具体怎么落地"的约定。

现状的更新路径是：设置页按钮 → 用系统浏览器打开发布页 → 用户自己下载覆盖（提交 0557538 之前即如此）。
它满足"程序零请求"，但代价是：用户要自己盯版本、自己判断下哪个文件、自己覆盖 exe——
对"给非程序员用的工具"来说，这条路径等于没有更新。

要解决的问题只有一个：**在保留"默认无任何网络行为"的前提下，让愿意的人能安全、省事地升级。**

---

## 决策

### 1. 更新的开关继承 ADR-0005，不做例外

- 网络**总开关**（默认关闭）之下的独立开关「自动检查更新」，**默认关闭**。
- 关闭时，程序网络 IO 必须为 0 字节——这条硬指标不变，用它做回归门禁。
- 提供三档：`从不检查`（默认）/ `有新版时提醒我`（只检查不下载）/ `下载并询问后安装`。
  没有"静默自动安装"这一档——见备选方案 A。

### 2. 更新只信任签名 + 校验和，任何一项不过就中止

按顺序校验，**任一失败即停止并明确告警，绝不替换自身**：

1. **代码签名**（Windows Authenticode）：用系统 `WinVerifyTrust` 自绑验证，不引新依赖。
   证书未到位前，这一关无法启用——**更新机制可以先把管道铺好，但默认禁用**（见第 7 条）。
2. **SHA-256 与发布页的 `.sha256` 文件逐字比对**（该文件已随每个 Release 分发）。
3. **体积与 SBOM 合理性检查**：与 `.cdx.json` 记录的组件数比对，防止被换成夹带私货的包。

> 更新机制是这个程序里唯一会**替换自身二进制**的功能，也是唯一"从网上拿东西并执行"的入口。
> 这里的任何一次"差不多就行"都会把本地优先的全部承诺一次性赔进去。

### 3. 更新绝不碰用户数据

- 便携版数据目录默认在 `%USERPROFILE%\DeskBaseData`（**不在程序目录内**），
  更新只替换程序文件；安装版同理，数据留在用户目录。
- 更新流程**禁止**写入、移动、删除数据目录内的任何文件——包括"顺手清理旧文件"。
- 更新**之前**自动做一次数据快照（依赖 M3 的备份能力，备份模块未完成时降级为
  "更新前提示用户自己导出"，不许假装备份过）。

### 4. 更新全程用户可见、可中止

显示：当前版本 → 新版本、变更摘要（取 Release Notes）、包大小、SHA-256、签名者。
每一步都要用户点确认；下载中和安装中都可中止；中止后程序保持原状态可用。

### 5. 更新必须可回滚

保留上一个版本的可执行文件副本（放在数据目录的 `updates/previous/` 下），
启动失败或校验失败时提供"回到上一个版本"的入口。**回滚不删数据**。

### 6. 全部联网尝试记审计日志

与 `app.openExternal` 一样：成功与被拒绝的都记，用户在设置页能看到次数。
更新相关的日志不记录数据目录内容、不记录用户数据。

### 7. 证书到位前的过渡状态（诚实版）

现在没有代码签名证书，所以：
- 更新机制的**实现可以先做**（开关、校验管道、UI、审计、回滚），
  但功能**默认禁用**并在界面上写明原因："没有签名证书，无法验证下载到的程序是否真的来自本项目"。
- 在此期间，设置页继续提供"打开发布页"手动路径，并且**明确告知**
  无签名的 exe 会被 SmartScreen 拦截（这是分发链的一号阻塞，见 `VERSION_PLAN.md` 第 5 节）。

## 备选方案

### 方案 A：静默自动更新（否决）

行业惯例，但直接违反三条承诺：用户不知道程序在联网、不知道自己换成了哪个版本、
也无法验证换上来的东西。**"静默"和"可验证"不能兼得**，本项目选可验证。

### 方案 B：引入第三方更新框架（否决）

现成方案会带进自己的网络栈、遥测点与体积（通常 MB 级），且其联网行为不受
ADR-0005 的开关约束。为一个一年用几次的功能付出"网络行为不可控"的代价，不划算。

### 方案 C：只做"检查更新"提醒，不做下载安装（部分采纳）

成本最低、风险最小，也符合"程序零请求"。但用户仍然要自己去下载覆盖——
对目标用户（非程序员）等于没解决。**采纳它的前半段**作为默认档位：
`有新版时提醒我` 是安全默认值，`下载并询问后安装` 供愿意的人开启。

## 影响与待实测

| 项 | 说明 |
|----|------|
| 新模块 | `app/src/updater.rs`（检查 / 下载 / 校验 / 替换 / 回滚），IPC 命令 `app.updateCheck` / `app.updateInstall` 等 |
| 体积增量 | **未实测**。设计目标 ≤ 100 KB（自绑 WinVerifyTrust，不引 HTTP 客户端之外的新依赖） |
| 依赖 | 需要 HTTPS 客户端。若 `ureq` 之类会拉进 rustls/OpenSSL，**优先用系统 WinHTTP**（零体积代价）——选型需 PoC 实测 |
| 风险 | 自替换 exe 在 Windows 上会锁文件：需要"下载到临时文件 → 校验 → 交给小更新器进程 → 主进程退出 → 替换"。这段最容易出错，必须配崩溃/中断测试 |
| 未完成前置 | 代码签名证书（采购）、M3 备份能力（更新前快照依赖它） |

## 复核条件

出现以下任一情况，本 ADR 必须重新评审：

1. 代码签名证书到位（第 7 条的过渡状态结束，需实测签名校验链路）
2. 引入 HTTP 客户端依赖（体积与网络行为需重新评估）
3. ADR-0005 被修订
