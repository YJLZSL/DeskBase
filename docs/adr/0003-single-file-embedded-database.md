# ADR-0003: 采用单文件嵌入式数据库，不自研存储引擎

- **状态**：已接受
- **日期**：2026-09-17
- **决策者**：核心维护者
- **相关**：[06 · SQL 数据库能力设计](../06-sql-database.md)、[07 · 备份、恢复与断电保护](../07-backup-recovery-dr.md)、[17 · 技术选型建议](../17-tech-selection.md)

---

## 背景

本项目的核心之一是内置数据库能力。存储层的实现方式决定了：

- 数据能否整体携带与迁移
- 崩溃一致性如何保证
- 用户是否需要安装与配置数据库服务
- 第三方工具能否直接打开数据文件（可迁移性）
- 加密如何实现

---

## 决策

1. **采用单文件嵌入式数据库引擎**，一个库 = 一个文件。
2. **不自研存储引擎。**
3. 引擎必须满足硬性要求：ACID 事务、WAL（或等价崩溃一致性机制）、单文件、支持嵌入式调用、许可宽松、支持中文标识符。
4. 具体引擎通过 PoC 比较后由后续 ADR 固化。
5. 若引擎不原生支持页级加密，采用**应用侧加密层**或成熟的加密扩展，不自行设计密码算法。

---

## 备选方案

### 方案 A：多用户客户端-服务器数据库（如 PostgreSQL / MySQL 系）
- 优点：成熟的并发、权限、备份体系；企业熟悉
- 缺点：需安装服务、需配置连接、跨平台分发包大、用户门槛高、需开端口
- **为什么不选**：与"打开即用""零污染""不装服务"的承诺冲突。

### 方案 B：自研存储引擎
- 优点：完全可控，可为办公场景做极致定制
- 缺点：崩溃一致性、并发控制、加密、索引、查询优化是极深的水域；需要数年积累；任何一个 bug 都可能导致用户数据损坏
- **为什么不选**：**这是最危险的选择。** 对以"不丢数据"为核心承诺的产品，自研存储引擎意味着把用户数据押在我们对一个极难问题的初级理解上。成熟引擎已经解决了这些问题，并且经过了数百万小时的实践检验。

### 方案 C：嵌入式分析型数据库（如 DuckDB 系）
- 优点：分析查询极快；单文件；MIT 许可
- 缺点：写入路径与事务能力面向分析场景，逐行写入与更新不是其强项；生态工具较少
- **为什么暂不选（但保留观察）**：本项目的主要负载是"人工录入 + 中小规模查询"，而不是大规模聚合分析。OLTP 型引擎更匹配。未来若需要强分析能力，可考虑作为可选的分析引擎并存。

### 方案 D：内嵌键值库 / 文档库
- 优点：写入快；灵活
- 缺点：无 SQL；关系表达弱；与"内置 SQL 数据库能力"的产品定位不符
- **为什么不选**：用户要的是"能用 SQL 的表"，而不是键值存储。

---

## 后果

### 正面
- 单个文件便于备份、迁移、U 盘携带
- 不需要安装服务、不开端口、不写系统目录
- 第三方工具通常能直接打开该文件（可迁移性保障）
- 崩溃一致性依赖成熟实现，风险可控
- 团队精力可投入产品层，而非存储层

### 负面
- 受引擎能力边界约束（如并发写模型、某些 SQL 语法）
- 大规模并发（多客户端同时写）不是其强项 —— 但本项目是单主端设计，影响有限
- 若引擎有历史包袱或性能瓶颈，我们只能通过优化使用方式缓解
- 加密可能需要在应用层实现，带来额外性能开销

### 中性
- 引擎选择本身成为一项需要 PoC 的决策（见 [ADR-0010](0010-desktop-shell-selection.md) 同类流程）

---

## 验证方式

| # | 验证项 | 判据 |
|---|-------|------|
| 1 | 崩溃一致性 | 写入过程中强杀进程 100 次，重启后完整性检查全部通过 |
| 2 | 性能 | 10 万行表索引查询 ≤ 50 ms；100 万行表索引查询 ≤ 200 ms |
| 3 | 中文支持 | 中文表名、字段名、中文全文检索全流程可用 |
| 4 | 可迁移性 | 第三方数据库工具可直接打开数据文件并读出数据 |
| 5 | 加密可行性 | 开启加密后第三方工具读不出明文；性能下降 ≤ 30%（查询） |
| 6 | 单文件 | 一个库对应一个数据文件（WAL 等附属文件可接受） |
| 7 | 备份一致性 | 使用引擎提供的在线备份能力或 WAL 一致点，恢复后数据完整 |
