# 0019 · 网络边界澄清：把「数据不出本机」与「默认不联网」拆成两条规则

- **状态**：**已接受**（2026-09-19 发起人澄清）
- **日期**：2026-09-19
- **决策者**：发起人
- **相关**：[ADR-0005 网络默认关闭](0005-network-closed-by-default.md)、[ADR-0007 AI 默认本地](0007-ai-local-first.md)、[ADR-0016](0016-in-app-update-mechanism.md) / [ADR-0018](0018-unsigned-self-update.md) 更新机制、[ADR-0017 AI 协助的隐私边界](0017-ai-assistance-privacy-boundary.md)

---

## 背景

发起人 2026-09-19 澄清了 ADR-0005 的**原始动因**：

> 当初把网络默认关掉，主要是**防止 AI 协助把用户的隐私数据带出去**，
> 而不是"这个程序永远不许联网"。

这条澄清很重要，因为 ADR-0005 后来被**过度泛化**了 —— 变成"程序做任何联网都等于违背承诺"。
最直接的一处后果就是本文件写下的记录：2026-09-19 评估第三方分发通道时，
理由是"它要求连第三方域名，与 ADR-0005 正面冲突" —— 而那个判断其实**站不住**：
更新检查既不涉及用户数据，也不是"偷偷联网"。

根因是把两件**性质完全不同**的事混成了一条规则：

| 混在一起的两件事 | 真实性质 |
|------------------|----------|
| 会不会把**用户的数据**传出去 | 安全与承诺问题，**不可让步** |
| 程序有没有在用户**不知道**的情况下联网 | 信任与可验证问题，**靠默认关闭 + 审计解决** |

混在一起的代价很具体：**该守的那条失去焦点**（"数据不出本机"淹没在一堆
"这个能不能联网"的争论里），而合理功能又因为一条被误读的禁令卡死。

---

## 决策

拆成两条独立规则，各有各的强度。**实现任何网络功能前先问：它属于哪一条。**

### R1 · 数据红线（不可让步）

**用户的数据不得离开本机。** 除用户**逐次显式授权**外，一个字节都不出去。

- 无遥测、无埋点、无崩溃上报、无使用统计 —— **不是开关，是功能不存在**
- AI 协助按 `ADR-0017` 执行：默认本地推理；本机没模型时**不许静默降级到云端**；
  外部调用逐次授权 + 展示将发送的内容 + 默认只发结构信息不发数据行
- 任何"为了体验更好""为了排查问题""反正是匿名的"都不构成放宽理由
- 远程访问 / 同步走 `ADR-0006`，端到端加密是前置条件

### R2 · 默认关闭（信任机制，不是禁令）

**程序自主发起的联网默认关闭**，且必须可验证 —— 这是为了回答
"这程序有没有在我不知道的时候联网"，而不是为了禁止联网本身。

1. 网络总开关默认关闭；每个联网功能**各自还有独立开关**，也各自默认关闭
2. 全部出站尝试（**含被拒绝的**）记本地审计日志，用户可查看、导出
3. 功能关闭时**网络 IO 必须为 0 字节**（硬性指标，可自证）
4. **R2 不禁止任何联网功能。** 功能可以有，条件是：默认关、用户能开、
   开的时候看得见、关掉时真的不发包

## 推论（把已经产生分歧的地方一次说清）

| 功能 | 归哪条 | 结论 |
|------|--------|------|
| **检查更新 / 下载 / 自替换** | **只归 R2** | 它只交换"程序自己的产物与版本号"，**不涉及用户数据**。可以做，按 ADR-0018：默认关 + 三步各自确认 + 全记审计 |
| **第三方分发通道（MirrorChyan 之类）** | **只归 R2** | 它**不涉及用户数据**（最多暴露"有人用了这个应用"）。所以"泄露数据"**不是**否决它的理由 |
| **AI 协助（含自然语言转 SQL、报错解释）** | **归 R1**（最严） | 见 ADR-0017。这是当初关网络真正要防的那件事 |
| **遥测 / 埋点 / 崩溃上报** | **归 R1 且不存在** | 不做，也不提供开关 |
| **字体、资源、依赖** | 归 R2 | 一律内嵌，不联网下载；`README` 已如此 |

> **关于 MirrorChyan 的更正**：发起人 2026-09-19 已决定**不用**它，这个决定**不变**。
> 但理由要更正为 —— **多一个第三方依赖与信任面**（要连它的域名、要用户理解"为什么更新还要买卡"、
> 它的可用性成为我们的可用性问题），而**不是**"它会泄露用户数据"。
> 把它写在 R1 名下是错的，会污染 R1 的可信度。见 `OPEN_QUESTIONS` Q-044。

---

## 备选方案

| 方案 | 否决理由 |
|------|---------|
| 维持"一律禁止联网" | 把两条不同性质的事混在一起：该守的数据红线失去焦点，合理功能被误读的禁令卡死；而且 ADR-0005 原文本来就没这么写 |
| 取消默认关闭，只留数据红线 | 用户就无法验证"程序没在偷偷传数据"了 —— **可验证性正是这条产品的立身之本**，不能为了少点摩擦丢掉 |
| 把更新检查列为默认开启 | ADR-0005 方案 A 已否决过，理由仍然成立（用户无法确定程序是否真没在传数据） |

---

## 后果

### 正面

- **R1 更清楚**：一句"用户数据不出本机"就能对外讲清，不必再解释一堆例外
- **R2 可操作**：新功能该不该做，看它涉不涉及用户数据，不再需要逐案争论
- 更新机制不必再背"违背隐私承诺"的包袱（ADR-0018 因此站得住）

### 负面（如实记录）

- 收窄了 R1 的适用面之后，**"默认关闭"这条会被人用来推动更多联网功能**。
  这是真实风险，所以 R2 的三条要求（各自开关、审计、关掉时 0 字节）**一条都不能省**
- 文档里此前把两者混写的表述需要逐处校正，否则读者会继续按旧理解推断

---

## 验证方式

| 验证 | 怎么做 |
|------|--------|
| R1 | 断网下功能不缩水；抓包/审计日志里没有任何用户数据出站；`docs/08` 的自检清单逐条过 |
| R2 | 全部联网功能默认关闭；**关闭状态下出站字节数为 0**；每次出站（含被拒）在审计日志里查得到 |

## 复核条件

1. ADR-0005 或 ADR-0007 被修订
2. 出现任何一次"用户数据出站"的实例 → 立即按 R1 处理，并重新评审全部联网功能
3. 有人以"R2 允许"为理由新增联网功能，而该功能实际会接触到用户数据 → 本 ADR 需补充判据
