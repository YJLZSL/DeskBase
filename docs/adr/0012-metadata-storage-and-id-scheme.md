# ADR-0012: 元数据与主数据的存储划分及 ID 方案

- **状态**：已接受
- **日期**：2026-09-17
- **决策者**：核心维护者
- **相关**：[04 · 数据模型参考设计](../local-docs/reference/04-data-model-reference.md) 第八节问题 1、6、[03 · 单文件嵌入式数据库](0003-single-file-embedded-database.md)、[06 · 单主端 + 远程访问](0006-single-primary-remote-access.md)、[07 · 备份、恢复与断电保护](../07-backup-recovery-dr.md)、[08 · 隐私、安全、加密、权限与审计](../08-privacy-security.md)

## 背景

数据模型参考设计（`04-data-model-reference.md`）的第八节留下两个待确认问题：

1. **元数据表（`sys_`/`meta_`/`log_`/`ai_`/`remote_` 前缀）与用户自建表，是否放在同一个数据库文件？**
2. **主键 ID 用 UUID v4 / ULID / 自增？**

这两个决策约束着备份粒度、迁移复杂度、加密范围、冲突检测能力与分页性能，必须在 P1 内核开工前定稿。

已确认的硬约束：

- ADR-0003：单文件嵌入式数据库，一个库 = 一个文件，不自研存储引擎；便于携带、迁移、第三方工具读出。
- ADR-0006：单主端架构，桌面端是唯一数据真相来源，不做双向同步，冲突合并场景有限。
- docs/07：提供「一键全量导出」「整目录搬迁」；备份与恢复以单个库文件为单元。
- 数据模型原则 #4：ID 采用不透明标识，便于未来多端合并与冲突检测。
- docs/08：加密分库级（页级 AEAD）与字段级（S2/S3）；加密随主库。

---

## 决策

### 决策一：元数据表与用户表同库同文件

元数据表（`sys_`、`meta_`、`log_`、`ai_`、`remote_` 前缀）与用户自建表（无前缀）**存储在同一个数据库文件内**，仅通过命名空间前缀隔离（沿用 `04-data-model-reference.md` 第二节约定）。

理由：

- **备份一致性**：docs/07 要求「一键全量导出」「整目录搬迁」，且每个备份携带一份校验和。同库 = 一次备份 = 一份校验和 = 一次完整性检查；分库需跨多个文件协调一致性点（事务无法跨文件），备份/恢复的正确性成本高得多。
- **事务一致性**：结构变更（DDL）与 `meta_column` 元数据更新必须在同一事务内提交（见 ADR-0014 问题 8）。同库使「改表结构 + 改元数据 + 写审计」成为单个原子事务；分库则跨文件事务不可得，易产生漂移。
- **迁移简单**：整目录复制或一键导出即完成迁移，无需处理多文件引用关系。
- **加密范围**：加密采用库级（页级 AEAD）随主库（docs/08），整库统一一个加密域；分库会引入多密钥/多文件加密管理，复杂度上升而收益有限。敏感字段的细粒度加密由 `meta_column.is_sensitive` + 字段级加密解决，不依赖分库。

### 决策二：ID 采用 ULID（业务实体）+ 自增 INTEGER（内部关联/日志表）

- **业务实体主键**（笔记、待办、事件、附件、标签、数据库对象、看板、日历、对话、消息、模板、远程设备等所有有业务语义、可能被外部引用或未来跨端合并的实体）统一使用 **ULID**（26 字符 Crockford Base32，时间前缀 + 随机后缀）。
- **内部关联表与日志表**（`*_link`、`*_ref` 等多对多连接表，`log_*` 审计/查询/健康/演练表，`meta_attachment_ref` 等纯行标识表）沿用**自增 INTEGER** 主键——这些表无业务语义、不参与跨端合并、顺序无意义，自增开销最低。

## 备选方案

### 方案 A：元数据与用户表分库存放（问题 1）

- 优点：理论上可对不同文件设不同加密粒度；用户表损坏不影响元数据。
- 缺点：破坏 ADR-0003「一个库 = 一个文件」的便携性承诺；跨文件无法用单一事务保证 DDL 与元数据一致；docs/07 备份/一键导出需协调多文件，校验和与恢复正确性复杂化；加密粒度问题已由字段级加密（docs/08）覆盖，分库收益不成立。
- **为什么不选**：收益被字段级加密吸收，而代价（一致性、备份、迁移）直接冲击核心承诺。

### 方案 B：UUID v4（问题 6）

- 优点：标准、易生成、完全无序随机，跨端不冲突。
- 缺点：128 比特无序，作为聚簇/主键会导致索引页碎片化、写入随机化；无时间序，列表分页与「最近创建」排序需额外索引列；字符串长度 36，比 ULID 长且含连字符。
- **为什么不选**：无序性对索引与分页不友好，且本项目需要按时间排序的列表（最近笔记、最近事件）。

### 方案 C：自增 INTEGER 作为全部主键（问题 6）

- 优点：最短、最快、天然有序、实现零成本。
- 缺点：原则 #4 要求不透明标识以便未来多端合并；自增暴露数据规模（可推测行数），且一旦引入多主端/导入合并会出现主键冲突，需重新映射。
- **为什么不选（仅限业务实体）**：与原则 #4 冲突，且单主端虽降低冲突概率但不应预先锁死合并能力。内部无语义表不受此约束，故仍可用自增。

### 方案 D：ULID 作为业务实体主键（采纳）

- 优点：时间前缀使字典序即时间序，分页与「最近」排序可直接用主键；随机后缀保证跨端生成不冲突（单主端下更无压力）；26 字符不含易混字符，比 UUID v4 短且更紧凑；生成器实现极小（数十行，无需重依赖）。
- 缺点：需引入一个 ULID 生成函数（实现成本低）；字符串主键比 INTEGER 略占索引空间（万行级影响可忽略，docs/14 索引查询 ≤ 50 ms 目标不受影响）。
- **为什么选它**：在「不透明 + 时间有序 + 跨端不冲突 + 低实现成本」四个诉求上取得最优平衡。

## 后果

### 正面

- 单文件库满足 ADR-0003 的便携/可迁移/第三方可读承诺。
- 备份、导出、迁移以单文件为单元，与 docs/07 设计天然契合。
- ULID 兼顾不透明性与时间有序，列表分页与最近排序无需额外索引。
- 内部表用自增 INTEGER，零成本且无语义负担。

### 负面

- 同库意味着库级加密下所有表共享一个加密域，无法对「仅元数据」做不同加密（已被字段级加密缓解）。
- ULID 字符串主键比 INTEGER 多占少量索引空间（万行级可忽略）。

### 中性

- 用户自建表的**主键由用户决定**（默认自增 INTEGER，见 `04` 第五节）；系统实体用 ULID，二者不冲突——单主端下用户表无需跨端合并主键（见下方「发现的张力」）。

---

## 验证方式

| # | 验证项 | 判据 |
|---|-------|------|
| 1 | 单文件 | 一个工作空间对应一个数据库文件（WAL 等附属文件除外），`04` 全部 `sys_/meta_/log_/ai_/remote_` 表与用户表共存于该文件 |
| 2 | 备份单元 | 一次「一键全量导出」产出单一库文件 + 附件目录，恢复后元数据与用户表一致；校验和验证通过 |
| 3 | ULID 格式 | 业务实体新行主键符合 ULID 规范（26 位 Crockford Base32、时间前缀单调不减、无 `ILOU` 字符） |
| 4 | 时间序分页 | 按主键 `ORDER BY` 的「最近笔记/事件」列表，结果与 `created_at` 排序一致 |
| 5 | 跨端不冲突 | 模拟两台设备各自生成 10 万个 ULID，碰撞数 = 0 |
| 6 | 内部表自增 | `*_link`/`*_ref`/`log_*` 表主键为自增 INTEGER，无业务代码依赖其具体值 |
