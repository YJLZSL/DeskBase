# ADR-0021: 彻底移除 SQL，改用自研单文件存储引擎

- **状态**：已接受
- **日期**：2026-09-20
- **决策者**：核心维护者
- **取代**：[ADR-0003](0003-single-file-embedded-database.md)（"不自研存储引擎"这一条结论被本 ADR 取代，其余关于单文件的要求继续有效）
- **相关**：[ADR-0022 · 关联与协同更新模型](0022-linked-tables-and-sync-rules.md)、[ADR-0012 · 元数据存储与 ID 方案](0012-metadata-storage-and-id-scheme.md)、[ADR-0020 · 表格优先的 UI](0020-table-first-ui-and-ai-tables.md)、调研 `local-docs/reference/18-storage-engine-research.md`

---

## 背景

产品设计发生方向性变更：

> **去掉 SQL。但保留 SQL 的关键特征 —— 多分表、改一张表的数据另一张表协同更新，并且这种"共通可更新"的关系要能配置、能看见。**

SQL 在这里承担的三件事，必须分别找到新载体：

| SQL 提供的 | 新载体 |
|-----------|--------|
| 多表 + `JOIN` | 关联字段（Link） |
| 触发器 / 外键级联 | 显式同步规则（SyncRule） |
| `SELECT / WHERE / ORDER BY` | 命名视图（View） |

同时，继续使用 SQLite 意味着代码里存在一个完整的 SQL 引擎 —— 与"彻底去掉 SQL"的要求直接冲突。

---

## 决策

1. **彻底移除 SQL。** 主程序不再依赖任何 SQL 引擎（`rusqlite` / `libsqlite3-sys` 全部移除），
   代码中不再出现 SQL 语句字符串，界面不再提供 SQL 输入框。
2. **自研存储引擎 `store`**：单文件，**append-only 日志 + 快照**，纯 Rust 实现，无新增第三方依赖。
3. **上层自建数据模型 `model`**：表 / 字段 / 记录 / 视图，**不含查询语言**，查询通过结构化视图配置表达。
4. **关联与协同更新**由 ADR-0022 定义。
5. **旧版 SQLite 数据文件不直接读取。** 迁移路径为「旧版导出 JSON/CSV → 新版导入」。
   主程序的依赖树里因此不需要保留 SQLite。
6. ADR-0003 中"单文件、不需要装服务、许可宽松、可整体带走"等要求**继续有效**；
   被取代的只有"不自研存储引擎"这一条。

---

## 为什么是自研，而不是换一个非 SQL 的嵌入式库

备选 redb / fjall / sled 都是成熟方案，落选理由（详见调研文档）：

- 它们依然是"换个数据库"，对内对外都要额外解释；
- 引入新的第三方依赖，而本机网络环境间歇性不可靠，拉取即风险；
- 数据格式不自主 —— 备份加密、版本升级、导出、远程同步都要跟着引擎节奏走。

自研的**范围被严格限定**，这正是它变得可接受的理由：

```
写入：追加 [len][crc32][payload] → fsync
读取：装载最新快照 → 回放其后日志
并发：单写者 + 多读者快照（DeskBase 是单主端单进程，见 ADR-0006）
索引：内存 BTreeMap，从日志重建，不持久化
```

**不做的部分**：无 B+tree 页管理、无查询优化器、无多写者并发控制、无持久化索引。
这四块是自研存储引擎真正的深水区，也恰好是本项目用不到的部分。

## 格式约定

数据文件默认 `<数据目录>/data/main.dkb`，日志同目录 `main.dkb.log`。

### 日志条目

```
┌────────┬─────────┬─────────┬─────────────────────┐
│ magic  │  len    │  crc32  │  payload (len 字节)  │
│ 4 字节 │ 4 字节  │ 4 字节  │                      │
└────────┴─────────┴─────────┴─────────────────────┘
   "DKB1"  u32 LE    u32 LE     msgpack 风格的自编码
```

- `payload` 顶层是 **UTF-8 JSON**（可读性优先，便于排障与人工拯救数据）；
- 尾部一条不完整的条目（长度不足 / CRC 不符 / 非 magic）**一律丢弃**，不报错、不猜；
- 每条含自增 `seq`，快照记录"已回放到的 seq"。

### 快照

- 触发条件：日志条目数 ≥ 50 000 或日志字节数 ≥ 8 MB（可在设置中调整）；
- 写入 `main.dkb.snap.tmp` → `sync_all` → `rename` 覆盖 `main.dkb.snap` → 目录 `sync_all`；
- 快照成功后**原子截断日志**：新日志写 `main.dkb.log.tmp` → 落盘 → rename 覆盖。

### 崩溃一致性判据

| 场景 | 期望 |
|------|------|
| 事务未提交时被杀 | 该事务完全不存在 |
| 事务已 `sync_all` 后被杀 | 该事务完整存在 |
| 日志尾部半写 | 半写条目被丢弃，之前的数据全部完好 |
| 快照临时文件残留 | 下次启动忽略 `.tmp` 并清理 |

## 后果

### 正面

- **彻底无 SQL**：依赖树、代码、界面三处同时清零；
- 构建更快、产物更小：去掉 9 MB 的 `sqlite3.c` 编译（本机 MSVC 优化该 C 文件会崩，Cargo.toml 里为此留过 workaround，一并删除）；
- 数据格式自主：备份加密、结构升级、导出、远程同步都握在自己手里；
- 崩溃安全可验证：三条机制都能写成确定性测试；
- 产品叙事统一："DeskBase 的数据就是 DeskBase 的格式"。

### 负面

- 需自行承担存储正确性的责任 —— 用崩溃测试与模糊测试对冲；
- 第三方工具不能直接打开 `main.dkb` —— 用「一键导出 SQLite / CSV / Excel / JSON」补偿
  （**导出侧**允许使用 SQLite，那是"给用户带走"，不是内部存储）；
- 日志有写放大（一次更新 = 一条新日志）—— 靠快照截断控制在有界范围；
- 失去了 SQL 引擎的成熟索引能力 —— 10 万行量级内靠内存索引 + 有序键足够，超出量级需在后续版本引入磁盘索引（已登记为风险）。

### 中性

- 迁移：0.x 不承诺兼容，走"导出 → 导入"，不写 SQLite 读取代码；
- 原 `schema.rs`（4850 行，大量 DDL 拼装与 SQL 词法判断）整体作废，由 `model/` 取代。

## 验证方式

| # | 验证项 | 判据 |
|:-:|--------|------|
| 1 | 无 SQL 残留 | 全仓库搜索 `rusqlite` / `libsqlite3` / `SELECT ` / `CREATE TABLE` 在 `app/src` 与 `app/ui` 下命中 0（排除导出模块与测试夹具） |
| 2 | 崩溃一致性 | 强杀 100 次，重启后校验通过，最多丢最后一个未提交事务 |
| 3 | 半写丢弃 | 人工截断/污染日志尾部，能正确丢弃并保住之前的数据 |
| 4 | 快照截断 | 达到阈值后日志归零，数据完整 |
| 5 | 关联同步 | 见 ADR-0022 验证表 |
| 6 | 体积 | `check-size` 不超预算；release 产物对比移除前应下降 |
| 7 | 迁移 | 旧库导出 JSON → 新格式导入，记录条数一致 |
