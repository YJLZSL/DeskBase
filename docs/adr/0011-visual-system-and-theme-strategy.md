# ADR-0011: 采用「宣纸为默认 + 多主题可切换 + token 驱动」的视觉系统策略

- **状态**：已接受
- **日期**：2026-09-17
- **决策者**：核心维护者
- **相关**：[18 · 视觉、质感、字体与动效设计系统](../18-visual-and-motion-design.md)、[13 · 设置、教程与帮助系统](../13-settings-tutorial-help.md)、[ADR-0009](0009-dual-ui-mode.md)

---

## 背景

产品需要确定视觉基调与主题能力。来自产品负责人的明确要求：

1. 默认采用**中式宣纸质感**作为主题；
2. 同时提供**多种可选主题**供切换；
3. 字体需支持**导入与切换**；
4. UI/UX 切换动画与交互动效的细节要**让人感到愉悦**。

这三件事（默认主题、主题可扩展、字体可换）如果处理方式不当，会造成严重的返工与性能问题。因此需要在写第一个组件之前确定策略。

---

## 决策

### 一、视觉系统由 token 驱动，组件不得硬编码色值

建立三层 token：

```
primitive（原始色阶，主题不变）
    → semantic（语义 token，主题重新映射）
        → component（组件 token）
```

**组件只能引用 token，禁止硬编码颜色、阴影、圆角、时长。**

### 二、默认主题为「宣纸」，但不是唯一

- 默认启用 `xuan`（宣纸），亮色、中式质感。
- 同时内置 9 个主题：`xuan` 宣纸、`qingci` 青瓷、`zhuqing` 竹青、`zhumo` 朱墨、`yemo` 夜墨（暗）、`songyan` 松烟（暗）、`xuantie` 玄铁（暗）、`hicon-light` 高对比（亮）、`hicon-dark` 高对比（暗）。
- 另提供「跟随系统」：`system`，系统亮色 → `xuan`，系统暗色 → `yemo`。
- 支持第三方主题导入/导出（JSON token 包 + 校验）。
- **主题只改颜色、阴影、纹理、字体，不改尺寸与间距。**

### 三、宣纸质感的约束

纸张质感由四层叠加实现（基色 + 纤维 + 帘纹 + 晕染），**总不透明度 ≤ 8%**，并且：

- **首选程序化生成**（噪声函数，零资源体积、分辨率无关、参数可调）；小尺寸可平铺位图（≤256×256、≤32KB）作为备选；
- 只作用于背景层，不覆盖文字、图标、图片；
- 提供"关闭纹理"开关与四档强度（关 / 轻 / 标准 / 明显，默认轻）；
- 关闭后帧率与纯色背景一致。

**不做**文化符号堆砌（祥云、回纹、剪纸、书法字标）。

### 四、字体策略：不内嵌中文字体，支持用户导入

- 默认使用各平台最优系统字体栈，**不内嵌中文字体**（否则会击穿安装包 80 MB 的目标）。
- 用户可从本地导入 `.ttf/.otf/.woff/.woff2/.ttc`，分别指派给界面 / 正文 / 代码 / 数字。
- 字体加载**不得阻塞首屏**（先渲染回退字体再替换）。

### 五、动效的原则是"愉悦"而非"华丽"

愉悦感的来源明确为五项：**即时反馈、物理感、连续性、恰到好处、一致性**。

硬性约束：

- 常规交互动效 ≤ **320 ms**；
- 只动 `transform` 与 `opacity`，禁止动画会触发布局重排的属性；
- 动效期间帧率 ≥ **55 FPS**；
- 提供"减少动效"模式，且跟随系统设置；
- **禁止**：循环装饰动画、元素飞入、视差滚动、线性缓动、大幅回弹、主题切换白屏。

### 六、实现顺序：token 先于组件，第二主题要早做，纹理放最后

```
① token 层  →  ② 组件（先用 token）  →  ③ 宣纸主题打磨
→  ④ 高对比主题（验证 token 完整性）  →  ⑤ 暗色主题
→  ⑥ 纹理层
```

- **token 必须先于组件**：组件一旦写死颜色，改主题就要逐个改组件，是最常见返工来源。
- **第 ④ 步必须早做**：只做一个主题时，很容易把该主题的特有属性硬编码进组件。用一个风格差异大的主题（如高对比）交叉验证，才能确认 token 抽象真的中立。
- **纹理放最后**：纹理最容易影响性能，放到最后打磨，避免早期就被性能问题拖住。

## 备选方案

### 方案 A：单一内置主题，不做主题系统
- 优点：实现最简单；无需 token 抽象层
- 缺点：无法满足"多种主题可选"的要求；后续加主题需要重写全部组件
- **为什么不选**：需求明确要求多主题；且后加主题的成本远高于先建 token 层。

### 方案 B：直接使用现成组件库的主题能力
- 优点：起步快；已有主题机制
- 缺点：主题能力受库的设计约束；宣纸质感这类"非标准"需求往往需要大量覆盖；可能引入体积与远程资源依赖
- **为什么不选**：本项目的视觉定位（中式质感、极低纹理强度、克制动效）与成品组件库的默认审美差距较大，覆盖成本可能高于自建。但**允许**在其上封装自有的 token 层（见"中性"部分）。

### 方案 C：把宣纸质感做成贴图资源
- 优点：视觉可控、效果直接
- 缺点：体积与分辨率适配成本（不同分辨率下需多套图、易模糊失真）
- **为什么改为备选而非排除**：位图作为备选存在体积与分辨率适配成本，因此首选程序化生成；但若程序化方案在某些平台表现不佳（如生成质量差或性能不稳），则回退到 ≤256×256 的小尺寸可平铺位图（≤32KB）。

### 方案 D：默认暗色主题（行业惯例）
- 优点：符合"开发者工具"的审美惯性；省电（OLED）
- 缺点：与产品负责人明确的审美要求不符；长文阅读在暗底上对部分用户更累
- **为什么不选**：产品负责人已明确要求默认中式宣纸（亮色）。暗色作为可选主题（`yemo` 夜墨）提供。

### 方案 E：内嵌一款中文字体确保观感一致
- 优点：跨平台渲染完全一致
- 缺点：中文字体 5–20 MB，直接击穿体积目标
- **为什么不选**：体积代价不可接受。改为"系统字体栈 + 用户可导入"。

### 方案 F：token 驱动 + 多主题 + 用户可导入（采纳）
- 优点：主题中立、可扩展、体积零成本、满足全部三项要求
- 缺点：需要先建 token 层（前置投入）；需要交叉验证抽象是否够用；测试矩阵增加
- **为什么选它**：唯一同时满足需求、体积目标与长期可维护性的路径。

## 后果

### 正面
- 视觉基调明确，且与产品"安静、克制、长期使用"的定位一致
- 主题可扩展，第三方可贡献，甚至可形成主题生态（插件形态）
- 字体可换，满足阅读偏好与无障碍需求
- token 层让"改视觉"不触碰业务代码
- 零体积成本实现质感（程序化纹理）
- 明确的动效规范避免"越做越花"的失控

### 负面
- **前置投入**：token 体系与运行时必须在业务组件之前完成，M0/M1 阶段没有可见产出
  - 缓解：这是必要的投资；不算入"可用版本"的功能范围，但必须做
- **测试矩阵扩大**：8 个主题 × 明暗 × 减少动效 × 无障碍模式
  - 缓解：主题只在 token 层变化，业务逻辑不受影响；用截图对比测试自动化校验
- **主题校验需要设计**：第三方主题可能对比度不达标
  - 缓解：导入时强制校验，不通过则拒绝启用（不警告后放行）
- **程序化纹理的质量风险**：生成的纹理可能"看起来假"
  - 缓解：先做原型验证；必要时用极小尺寸的可平铺噪声图作为降级方案

### 中性
- 需要定义并维护"主题包规范"，作为对外契约的一部分
- 动效规范需要团队持续遵守，否则会逐渐失控（建议在 PR 模板中加入动效检查项）

## 验证方式

| # | 验证项 | 判据 |
|---|-------|------|
| 1 | 无硬编码色值 | 代码扫描：组件目录中无 hex/rgb 字面量 |
| 2 | 主题切换质量 | 8 个主题逐一验证：无闪烁、无布局跳动、≤ 220 ms |
| 3 | 对比度 | 自动化检查：全部主题文字对比度 ≥ 4.5:1 |
| 4 | 纹理强度 | 实测总不透明度 ≤ 8% |
| 5 | 纹理性能 | 开启与关闭纹理的帧率差 ≤ 3% |
| 6 | 字体导入 | 导入 .ttf/.otf/.woff2 成功，可指派到四个用途 |
| 7 | 字体加载 | 首屏无阻塞（首帧即显示回退字体） |
| 8 | 动效时长 | 常规动效实测 ≤ 320 ms |
| 9 | 动效性能 | 动效期间帧率 ≥ 55 FPS |
| 10 | 减少动效 | 开启后无位移/缩放动画，反馈仍即时 |
| 11 | 主题校验 | 构造对比度不足的主题，导入被拒绝并指出具体项 |
| 12 | 用户主观评价 | 项目发起人 实际使用后认为"看得舒服、动效不烦" |
