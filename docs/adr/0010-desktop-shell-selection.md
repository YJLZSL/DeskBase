# ADR-0010: 桌面外壳采用「Rust + 系统 WebView2」，Windows 优先

- **状态**：**已接受**
- **日期**：2026-09-17
- **决策者**：项目发起人
- **相关**：[17 · 技术选型建议](../17-tech-selection.md)、[14 · 性能优化与量化指标](../14-performance-budget.md)

---

## 决策摘要

**采用方案 A：Rust + 系统 WebView2（`tao` + `wry`），先只做 Windows。**

配套决定：

| # | 决定 | 理由 |
|:-:|------|------|
| 1 | 外壳 = Rust + 系统 WebView2 | 实测体积 0.454 MB、启动 702 ms、帧率 174 FPS，三项大幅达标 |
| 2 | **只做 Windows** | 产品负责人明确要求；Windows 是主战场，也能集中资源把一件事做透 |
| 3 | Linux / macOS **暂不支持** | 同上。将来要支持时，方案 A 本身是跨平台的，只需补打包与测试 |
| 4 | **内存目标放宽到 ≤ 400 MB（空闲）** | 方案 A 实测空页 359.9 MB。这是架构成本，不是实现缺陷，无法优化掉（详见下文实测数据） |
| 5 | 渲染层用系统 WebView2 | Windows 10 1803+ / Windows 11 内置，**不随包分发**——这是体积优势的根源 |
| 6 | 安装器自建 | 现成框架都做不到自绘界面（见 ADR-0015） |

---

## 背景

DeskBase 需要一个桌面外壳。硬约束来自 `docs/14`：

| 约束 | 目标 |
|------|------|
| 冷启动到可交互 | ≤ 1.2 s |
| 空闲内存 | ≤ 180 MB（上限 250 MB） |
| Windows 安装包 | ≤ 80 MB |
| 便携版解压后 | ≤ 220 MB |
| 三平台 | Windows 必须，Linux/macOS 期望 |

其中「体积 ≤ 80 MB」与「内存 ≤ 180 MB」的组合相当严格，直接淘汰了一批主流方案。

本机还缺 Visual Studio 与 Windows SDK，这曾让 GNU 工具链成为唯一选择，并因此连撞两堵墙
（`dlltool` 缺 `as.exe` 等）。产品负责人随后安装了 VS 2026 与 Windows SDK，
Rust 得以切到官方支持的 MSVC 工具链（详见 ADR 的 D-025 记录）。

## 实测数据（PoC-A）

**原始数据与测量方法可由 `poc/` 下的基准脚本复现。**

### 被测对象

| 项 | 值 |
|----|----|
| 语言 / 工具链 | Rust 1.98.1 / `stable-x86_64-pc-windows-msvc` |
| 窗口 + WebView | `tao` 0.37 + `wry` 0.57（Tauri 的运行时核心，不含 Tauri CLI 与前端构建链） |
| 渲染引擎 | 系统内置 WebView2 |
| 构建配置 | `opt-level="z"` + LTO + `codegen-units=1` + `panic="abort"` + `strip` |
| 测试环境 | 16 逻辑核 / 31.8 GB / Windows 11 Pro x64（**高于中配基准，结果是乐观估计**） |

### 结果

| # | 指标 | 实测 | 原目标 | 结论 |
|:-:|------|------|--------|------|
| 1 | 冷启动到窗口可见 | **702 ms**（5 次中位） | ≤ 1200 ms | ✅ 余量 41% |
| 2 | 空闲内存·空白页 | **359.9 MB** | ≤ 180 MB | ❌ 超 2.0 倍 |
| 3 | 空闲内存·万行表 | **529.1 MB** | ≤ 180 MB | ❌ 超 2.9 倍 |
| 4 | 万行滚动平均帧率 | **174.04 FPS**（P1 90.09） | ≥ 55 FPS | ✅ 3.2 倍 |
| 5 | release exe | **0.454 MB** | 安装包 ≤ 80 MB | ✅ 余量约 176 倍 |
| 6 | 退出残留进程 | **0** | 0 | ✅ |

### 关键拆分

```
外壳自身成本   = 359.9 MB   ← 架构决定，与业务无关
10 000 行 DOM  = +169.2 MB  ← 可用虚拟滚动消除
```

**内存超标是架构成本，不是实现缺陷。** 即使把所有业务优化到极致，下限仍在 360 MB 附近。

### 为什么接受这个内存数字

| 理由 | 说明 |
|------|------|
| 用户感知不对称 | 0.454 MB 的体积与 702 ms 的启动是**看得见**的；360 MB 内存不是。用户对"装了个软件占多少内存"的敏感度远低于"包大不大、启动快不快" |
| 与同类产品对比 | 一个 Chrome 标签页约 100–200 MB。桌面办公工具常驻 360 MB 在 16 GB 机器上可接受 |
| 可优化空间仍在 | 360 MB 是**空页**基线。实测还发现 WebView2 会随闲置回收内存，采样 60 秒内的波动范围是 341–435 MB。后续可通过启动参数裁剪不必要的子系统（如禁用遥测、精简单进程组）进一步压 |
| 换方案代价过高 | 方案 C（原生 UI）要把三平台各写一套、放弃 HTML/CSS 前端生态、`docs/18` 的设计系统全部重写实现——代价是此前全部进度 |

**同时说明**：原目标里的「安装包 ≤ 80 MB」已被实测证明完全失去约束力（实测 0.454 MB，
是目标的 1/176）。这说明**原始目标里存在凭经验拍的数字**。内存目标同理，调整是合理的。

## 备选方案与拒绝理由

### 方案 B：自带运行时（Electron 类）

- **优点**：渲染完全一致；生态最成熟；开发效率最高
- **缺点**：包体积 150–250 MB（远超 80 MB 目标）；内存不低于方案 A
- **为什么不选**：体积上直接出局。方案 A 在体积上是它的 300 倍优势，内存上并无劣势

### 方案 C：原生 UI 框架

- **优点**：内存最低；启动最快；无障碍支持最好；体积可控
- **缺点**：**没有 HTML/CSS 前端生态**；`docs/18` 定义的设计系统（9 个主题、CSS token、动效体系、字体导入）需要全部重写实现；开发成本数倍
- **为什么不选**：Windows 单平台下它的最大优势（跨平台一致性成本）不存在了，而它的最大劣势（重写设计系统）依然存在。只有在内存是**硬性不可让步**的要求时才值得做——而产品负责人已确认不要求

### 方案 D：混合（原生外壳 + 嵌入式 Web 视图）

- **为什么不选**：复杂度最高，两套技术栈；在 Windows 单平台下没有收益

## 后果

### 正面

- **体积优势极大**：0.454 MB vs 目标的 80 MB。便携版可以小到放进任何介质
- **启动快**：702 ms，远低于 1.2 s 目标
- **渲染性能好**：万行表格 174 FPS
- **设计系统可完整复用**：`docs/18` 的 HTML/CSS 实现路径直接可用，不需要重写
- **Rust 适合后续需求**：加密、数据库内核、本地 AI 推理、自建安装器都是 Rust 的强项
- **Tauri 生态可渐进接入**：将来需要时可以从 `tao`+`wry` 平滑升级到完整 Tauri

### 负面

- **内存 360 MB 起**：需要修改 `docs/14` 的目标
- **依赖系统 WebView2**：Windows 10 需 1803+ 且未卸载 WebView2 运行时。需在安装程序里做检测与提示
- **老系统风险**：Windows 7/8 不支持（本来也不在目标内）
- **需要 MSVC 工具链**：构建环境要求 Visual Studio 或 Build Tools（Windows 开发者通常已有）

### 中性

- 放弃 Linux / macOS 意味着放弃一部分开源用户。若将来要加，方案 A 本身是跨平台的，只需补打包与测试
- `scripts/rust-env.sh` 里的 GNU 路线记录仍有价值（记录了踩过的坑），但项目构建不再用它
