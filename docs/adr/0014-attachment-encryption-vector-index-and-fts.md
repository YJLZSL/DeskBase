# ADR-0014: 附件加密与去重、向量索引存放、全文检索方案及 schema 同步

- **状态**：已接受
- **日期**：2026-09-17
- **决策者**：核心维护者
- **相关**：04 · 数据模型参考设计（内部调研资料，未随仓库分发） 第八节问题 3、5、7、8、[08 · 隐私、安全、加密、权限与审计](../08-privacy-security.md) 第四节、[05 · 网络访问默认关闭](0005-network-closed-by-default.md)、[11 · 视觉系统策略](0011-visual-system-and-theme-strategy.md)、[07 · 备份、恢复与断电保护](../07-backup-recovery-dr.md)、[14 · 性能优化与量化指标](../14-performance-budget.md)

## 背景

数据模型参考设计第八节留下四个待确认问题，本 ADR 一并决策：

3. **附件是否支持加密？如何与去重（内容哈希）配合？**——明文哈希去重会泄露「我是否拥有某内容」。
4（并入问题 8 视角）.**用户表结构变更如何与 `meta_column` 元数据表保持一致？**——核心风险是「绕过服务层直接执行 DDL」。
5. **向量索引是否入库？**——入库膨胀备份体积，但不入库则备份未必完整。
7. **全文检索用引擎内置 FTS 还是外部索引？**——中文分词是内置 FTS 的短板。

约束：

- docs/08：附件加密 = 分块 AEAD，跟随库级；S2/S3 默认/强制加密；密钥不进备份包（红线 10）。
- ADR-0005 / ADR-0007：网络默认关闭，AI 必须完全离线可用。
- ADR-0011：不内嵌中文字库（体积原因）——影响中文分词器选型，但不禁止轻量分词算法。
- docs/07：向量索引默认不含备份（可重建）；附件与版本历史默认进备份。
- docs/14：全文搜索首屏 10 万条 ≤ 300 ms；不内嵌模型/字库以守 ≤ 80 MB 安装包。
- 原则 #8：可迁移，元数据可导出为开放格式。
- docs/06：查询日志默认不记录 SQL 原文。

---

## 决策

### 决策一：附件支持加密，去重基于明文哈希，二者不冲突（问题 3）

- **加密**：附件文件支持加密，跟随库级加密设置（开启加密时，所有附件按主密钥派生的附件密钥分块 AEAD 加密，`nonce` 随每份密文内联存储）。截图内容、OCR 结果属 S2，开启加密即默认加密；用户可对单附件标记 S3 强制加密。
- **去重**：基于**明文 SHA-256 内容哈希**（`meta_attachment.hash`）做内容去重——相同明文只存一份物理文件，多 owner 通过 `meta_attachment_ref` 共享同一 `attachment_id`，引用计数管理生命周期。
- **与加密的配合**：去重判断发生在**明文层**（先计算哈希再决定存储），加密发生在**存储层**（按 `attachment_id` 一份密文）。因此加密不破坏去重：相同明文 → 相同哈希 → 同一份密文；不同明文各自加密各自存储。
- **哈希泄露缓解**：明文哈希用于去重本身是「存在性指纹」。缓解措施是**依赖静态加密**而非改算法——`meta_attachment` 表随主库级加密，落盘时 `hash` 列为密文，静态磁盘不暴露；本地优先架构下攻击需物理接触设备（docs/08 明确此为本产品能力边界）。**不采用确定性加密**（deterministic encryption 会再次泄露「两份明文相等」），因其收益不足以抵消新增的相等性泄露面。若用户关闭库级加密，则 `hash` 以明文落盘——此时用户已知晓明文存储风险且数据不出设备。

### 决策二：向量索引不入库（问题 5）

- 向量**本体**存于独立目录（如 `data/vectors/`），主库仅存 `ai_vector_map` 映射表（`target_kind`/`target_id`/`chunk_no`/`vector_ref`/`content_hash`）。
- 理由：向量可由文本块**重新生成**（embedding），损坏/丢失可重建，无需进备份（docs/07 默认不含，省体积）；入库会膨胀主库与备份体积；独立目录使重建与清理简单。AI 完全离线（ADR-0005/0007），无外部依赖。`content_hash` 用于判断某 chunk 是否需要重建，文本变更即触发对应块重建。
- 备份策略：向量目录默认不进备份（可重建）；若用户要求备份完整可搜索能力，可在备份设置中显式开启（此时体积上升由用户知情）。

### 决策三：全文检索用引擎内置 FTS5 + 轻量中文分词，同库同事务（问题 7）

- 采用引擎内置 FTS（FTS5），全文索引表与主数据表**同库**，增删改在**同一事务**中同步维护，从根上避免外部索引的漂移问题。
- 中文分词：选用**轻量方案**——FTS5 `trigram` tokenizer（对中文按字符三元组建索引，无需词典/字库，体积小，符合 ADR-0011 不内嵌字库）或自定义 bigram/按字符切分；trigram 对中文子串检索有效，可满足 docs/14「全文搜索首屏 10 万条 ≤ 300 ms」目标。具体分词质量通过 PoC 验证后固化引擎选型。
- 不引入独立外部全文索引进程（如独立搜索引擎库）：避免新增进程、文件与一致性同步负担，与「单文件、离线、可迁移」冲突。
- 外部索引作为**未来可选**能力（如需要更强语义/分词时可挂外接索引），不设为默认。

### 决策四：结构变更统一经服务层，启动校验漂移（问题 8）

- **唯一写入路径**：所有 DDL（CREATE/ALTER/DROP 用户表与字段）只能通过封装好的服务层接口（如 `schemaService.alterTable`），**禁止**应用其他部分、插件、远程端直接执行 DDL。
- **原子事务**：服务层在单个事务内完成「执行 DDL → 同步 `meta_column`（增/改/删对应行）→ 写 `log_version`（target_kind=schema）→ 写 `log_audit`（category=ddl）→ COMMIT」。`meta_column` 以真实 schema（`PRAGMA table_info` 或等价）为权威来源，是补充/缓存信息。
- **漂移强制检测**：打开库/启动时比对每个用户表的实际 schema 与 `meta_column` 记录；发现不一致则告警并触发修复（以 `PRAGMA` 为准重建 `meta_column` 或提示用户）。提供可独立运行的校验脚本。
- **权限收紧**：插件与远程端的「管理结构」权限默认关闭（docs/08 远程管理结构默认关），任何 DDL 均经服务端强制校验并记入审计。
- 代码层面：DDL 仅允许出现在服务层；测试与代码评审确保无绕过路径。

## 备选方案

### 方案 A：附件不加密（问题 3）

- 优点：实现最简，去重无顾虑。
- 缺点：截图、OCR、敏感附件属 S2/S3，docs/08 要求默认/强制加密；违反隐私红线。
- **为什么不选**：与 docs/08 数据分级直接冲突。

### 方案 B：加密附件用确定性加密以保留去重（问题 3）

- 优点：相同明文产生相同密文，密文层也能去重。
- 缺点：确定性加密泄露「两份附件内容相等」的相等性；且若未来换密钥则去重失效；实现复杂。
- **为什么不选**：新增泄露面，收益（密文层去重）可由明文哈希去重覆盖，不值得。

### 方案 C：向量索引入库（问题 5）

- 优点：备份即完整，恢复后立即可搜；一份文件。
- 缺点：向量体积可观（10 万向量量级数十 MB），膨胀主库与备份；向量可重建却占备份空间；与 docs/07「默认不含」相悖。
- **为什么不选**：向量可重建，入库是冗余体积，且备份完整性可由「重建」保证，不必入库。

### 方案 D：向量索引用独立向量库进程（问题 5）

- 优点：检索能力强。
- 缺点：新增进程与文件，需与主库一致性同步；离线/单文件/可迁移承诺受冲击；依赖体积风险。
- **为什么不选**：超出需求，独立目录 + 映射表已足够，且契合「可重建不备份」。

### 方案 E：外部全文索引（独立搜索引擎库）（问题 7）

- 优点：中文分词质量通常更好，检索能力强。
- 缺点：引入外部进程/文件；主数据与索引需额外同步机制，易漂移；体积与依赖增加；与 ADR-0003 单文件、docs/07 一键导出、可迁移冲突明显。
- **为什么不选**：一致性成本与离线/单文件承诺不兼容，内置 FTS 已能满足目标。

### 方案 F：内置 FTS5 + 轻量中文分词（采纳，问题 7）

- 优点：同库同事务，一致性天然；单文件、离线、可迁移；trigram 无需字库，体积小；满足 300 ms 检索目标。
- 缺点：中文分词质量依赖 tokenizer 选择，需 PoC 验证；trigram 对长词精确匹配弱于词典分词。
- **为什么选它**：在一致性、体积、离线三项硬约束下是最优解；分词质量通过 PoC 调优可接受。

### 方案 G：DDL 允许直接执行、仅事后修复（问题 8）

- 优点：灵活，插件/高级用户可改结构。
- 缺点：绕过服务层会破坏 `meta_column` 与 schema 一致，事后修复无法保证审计完整；是数据模型最大一致性风险点。
- **为什么不选**：与「禁止绕过、可验证」的强制要求冲突，风险不可接受。

### 方案 H：DDL 统一经服务层 + 启动漂移校验（采纳，问题 8）

- 优点：一致性由事务保证；漂移可被检测与修复；审计完整；与 docs/08 权限默认关闭一致。
- 缺点：所有结构变更必须经服务层，灵活性受限（对单主端产品可接受）；需写校验脚本与测试。
- **为什么选它**：以可控的灵活性换取可验证的一致性，是正确交换。

## 后果

### 正面

- 附件在本地优先前提下满足 S2/S3 加密要求，且去重不失效。
- 向量索引体积小、可重建、不污染备份。
- 全文检索与主数据强一致，离线可用，体积小，符合不内嵌字库约束。
- 结构变更一致性可验证（事务 + 启动校验），降低最大风险点。

### 负面

- 关闭库级加密时，附件内容哈希以明文落盘（存在性指纹暴露，属已知边界）。
- 内置 FTS 的中文分词质量依赖 tokenizer，需 PoC 调优；trigram 对长词精确匹配有限。
- 结构变更必须走服务层，高级场景灵活性下降（单主端可接受）。

### 中性

- 向量目录默认不进备份，但「可搜索能力」的恢复依赖重建（需 embedding，离线可完成）。
- 外部全文索引与更优分词作为未来可选，不阻塞当前架构。

## 验证方式

| # | 验证项 | 判据 |
|---|-------|------|
| 1 | 附件加密 | 开启库级加密后，附件文件以密文存储；第三方工具直接读取附件文件得不到明文（docs/08 判据） |
| 2 | 去重有效 | 上传两份相同二进制附件，物理文件仅存一份，`meta_attachment_ref` 出现两条引用；删除一条不影响另一份 |
| 3 | 哈希静态保护 | 开启库级加密时，数据库文件中 `meta_attachment.hash` 列密文存储；未解锁态抓取数据文件无明文哈希 |
| 4 | 向量不入库 | 主库文件不含向量本体；`data/vectors/` 独立存在；默认备份包不含向量目录 |
| 5 | 向量可重建 | 删除 `data/vectors/` 后执行重建，恢复全部向量且 `content_hash` 一致；全文/语义检索恢复可用 |
| 6 | FTS 同事务 | 插入/更新/删除一条被索引记录后，FTS 索引在同一事务内同步，检索结果立即反映变更 |
| 7 | 中文检索性能 | 10 万条记录中文全文搜索首屏 ≤ 300 ms（docs/14 目标） |
| 8 | 中文分词质量 | PoC 对典型中文查询（子串/长词）召回率与准确率达标，作为引擎选型依据 |
| 9 | DDL 经服务层 | 代码扫描确认 DDL 仅出现在服务层；模拟「绕过服务层直接 ALTER」被拒绝或启动校验告警 |
| 10 | 漂移检测 | 注入一次 `meta_column` 与实际 schema 不一致，启动校验能检测到并触发修复，修复后二者一致 |
| 11 | 结构审计 | 每次结构变更在 `log_audit`（category=ddl）与 `log_version`（schema）留有记录 |
