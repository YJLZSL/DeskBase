# ADR-0013: 版本历史存储方式与回收站实现方式

- **状态**：已接受
- **日期**：2026-09-17
- **决策者**：核心维护者
- **相关**：04 · 数据模型参考设计（内部调研资料，未随仓库分发） 第八节问题 2、4、[07 · 备份、恢复与断电保护](../07-backup-recovery-dr.md) 第四节、[14 · 性能优化与量化指标](../14-performance-budget.md) 第八节

## 背景

数据模型参考设计第八节留下两个待确认问题：

2. **版本历史用全文快照还是差分存储？**
4. **回收站用独立表还是软删除标记 + 快照？**

`04-data-model-reference.md` 已为这两者预留结构（`log_version` 带 `is_diff` 与 `content` 字段；`meta_note` 等带 `deleted_at` 软删除列；`meta_recycle_bin` 独立表带 `payload` 快照），但实现方式未定稿。docs/07 第四节明确了分层历史（文档版本 / 记录版本 / 结构版本 / 库快照）与回收站的能力要求。

约束：

- docs/07：版本历史默认包含在备份中；文档版本默认保留 90 天、记录版本默认 30 天、结构版本默认永久保留最近 100 个。
- docs/14：索引命中查询 ≤ 50 ms；全文搜索首屏 10 万条 ≤ 300 ms；备份体积受控（向量索引默认不含）。
- 原则 #5：软删除优先，覆盖回收站与版本历史；物理删除需显式操作。
- 可迁移：元数据可导出为开放格式。

---

## 决策

### 决策一：版本历史按内容类型分治（文本差分 + 锚点快照；结构化全文快照）

不统一采用「全文快照」或「差分」单一策略，按被版本化对象的性质分治：

- **长文本类（笔记 `note`、富文本、模板正文）**：默认存储**差分（delta）**——基于上一版本做行级/字符级 diff，仅存变化部分，显著降低存储占用。同时周期性保留**全文快照锚点**（如每 N 个版本，或 `is_locked = 1` 的版本），作为回滚快速入口与 diff 链断裂时的恢复基点。恢复某版本 = 从最近锚点全文快照向前/向后应用 diff。
- **结构化记录（数据库单行 `record`）**：单行体积小，直接存**全文快照**（整行 JSON）。diff 的存储收益低、实现复杂度高，不值得；全文快照实现简单、回滚即覆盖。
- **结构版本（`schema`，DDL）**：每次结构变更存**全文快照**（DDL 语句 + 变更后的 schema JSON），用于结构回滚与迁移审计。
- `log_version.is_diff` 字段记录该条是差分还是全文，便于读取时选择路径。

### 决策二：回收站 = 软删除标记 + 独立回收站快照表，二者协同

- **软删除标记（`deleted_at` 列）**为主：被删除实体在原表中标记 `deleted_at = 时间戳`，不真正移走。作用：快速判断「已删除」、列表过滤简单、维持外键/引用完整性（记录不消失，关联不悬空）、支持「恢复到原位置」时无需重建行。
- **独立回收站表（`meta_recycle_bin`）**存**删除时的完整内容快照**（`payload`）：提供跨类型统一的恢复入口，并在原表记录已被物理清理后仍能从快照恢复；同时记录 `original_location`、`size_bytes` 供展示。
- **删除流程**：写 `meta_recycle_bin.payload` 快照 → 原表标记 `deleted_at` → 进入保留窗口（默认 30 天）→ 到期/用户清空时物理删除原表行并清理对应快照（除非 `is_locked`）。
- 软删除实体与回收站表配合使用：前者回答「是否删除」，后者提供「恢复所需的数据」。

## 备选方案

### 方案 A：版本历史全用全文快照（问题 2）

- 优点：实现最简单；回滚即覆盖；无 diff 链断裂风险。
- 缺点：长文本笔记高频编辑（每 5 分钟或每 50 次编辑一个版本，默认 90 天）会产生大量全文副本，存储与备份体积膨胀明显。
- **为什么不选**：对长文本代价过高，差分可省下大部分空间且实现可行。

### 方案 B：版本历史全用差分（问题 2）

- 优点：最省空间。
- 缺点：结构化单行 diff 收益低却增加复杂度；长 diff 链读取需顺序回放，回滚最旧版本成本高；链中任一点损坏则后续全部失效，需额外锚点机制兜底层——最终仍要回到「差分 + 锚点」。
- **为什么不选**：对结构化数据得不偿失，且纯差分必须引入锚点才安全，不如直接分治。

### 方案 C：回收站纯软删除（无独立表，问题 4）

- 优点：实现最简单，删除即置 `deleted_at`。
- 缺点：若原表行被物理清理（到期/清空），恢复所需数据随之消失；跨类型无统一恢复入口；无法在「记录已物理删除」后重建。
- **为什么不选**：回收站的核心价值是「可恢复」，纯软删除在物理清理后失效，违背 docs/07 回收站能力要求。

### 方案 D：回收站纯独立表（删除即移出原表，问题 4）

- 优点：原表干净，无 `deleted_at` 过滤负担。
- 缺点：删除需把整行搬入回收站表，破坏外键/引用完整性（关联悬空）；列表查询需 UNION 原表与回收站；恢复到原位置需重建行与重排主键；实现复杂且易错。
- **为什么不选**：以引用完整性换取少量查询便利，代价过高。

### 方案 E：分治版本 + 软删除协同回收站（采纳）

- 优点：文本省空间、结构化简单、回收站既能快速判断又能完整恢复；与 `04` 既有结构（`is_diff`、`deleted_at`、`meta_recycle_bin`）完全吻合，无需返工。
- 缺点：两套版本逻辑（差分链 + 全文快照）需分别实现与测试；回收站需维护「标记 + 快照」双写。
- **为什么选它**：精准匹配各内容类型的成本结构，且复用既有表结构，落地成本最低。

## 后果

### 正面

- 长文本版本占用大幅下降，备份体积可控（docs/07 版本历史默认进备份）。
- 结构化记录版本实现简单、回滚可靠。
- 回收站在「快速判断已删除」与「完整可恢复」之间两全；物理清理后仍可恢复。
- 与 `04` 预留结构一致，P1 直接落地，无需改表。

### 负面

- 差分链 + 锚点的读取/回滚逻辑比纯快照复杂，需测试覆盖链断裂恢复。
- 软删除标记使所有列表查询都必须带 `deleted_at IS NULL` 过滤（可由服务层统一封装，避免遗漏）。

### 中性

- 版本清理策略（保留时长/份数、`is_locked`）沿用 docs/07，属配置项而非架构变更。

## 验证方式

| # | 验证项 | 判据 |
|---|-------|------|
| 1 | 文本差分生效 | 对一篇 5 KB 笔记连续编辑 20 次，`log_version` 中差分条总体积显著小于 20 份全文快照之和（节省 ≥ 50%） |
| 2 | 锚点恢复 | 删除中间某锚点之外的版本后，从最旧版本回滚仍可在 ≤ 1 秒内完成且内容正确 |
| 3 | 结构化全文快照 | 修改一条数据库记录后，`log_version` 该条 `is_diff = 0` 且存整行 JSON，回滚即覆盖正确 |
| 4 | 软删除过滤 | 带 `deleted_at IS NULL` 的列表查询不返回已删除项；标记后原表行仍在、引用不悬空 |
| 5 | 回收站恢复 | 原表行被物理清理后，仍可从 `meta_recycle_bin.payload` 恢复到原位置且内容完整 |
| 6 | 保留窗口 | 超过保留时长的回收站项在清理任务后自动物理删除（除非 `is_locked = 1`） |
| 7 | 备份包含 | 「一键全量导出」恢复后，版本历史与回收站数据完整（对照 docs/07 备份内容清单） |
