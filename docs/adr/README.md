# 架构决策记录（ADR）

本目录存放 DeskBase（桌库）的架构决策记录。

---

## 什么是 ADR

ADR（Architecture Decision Record）是一份**简短的、不可变的历史文档**，记录一项影响项目长期形态的技术或产品决策：当时面临什么问题、考虑过哪些方案、最终选了什么、为什么。

它解决的核心问题是：**半年后有人（包括我们自己）问"当初为什么要这么设计"，能有一个确切的答案。**

---

## 规则

| 规则 | 说明 |
|------|------|
| **不可修改历史结论** | 已接受的 ADR 不再编辑其决策内容。要改变决定，请新增一份 ADR 并声明取代关系 |
| **允许小修** | 修正错别字、补充链接、更新状态（如标记为"被 ADR-XXXX 取代"）是可以的 |
| **编号连续** | `NNNN-短标题.md`，四位数字，从 0001 开始 |
| **一页原则** | 尽量短。ADR 不是设计文档，长内容请链接到 `docs/` |
| **必须记录备选方案** | 只写"我们选了什么"没有价值，要写"我们没选什么、为什么" |
| **拒绝也是记录** | 被否决的提案如果讨论过，也应有 ADR 记录，避免重复讨论 |

---

## 状态定义

| 状态 | 含义 |
|------|------|
| `提议` | 已提交，正在讨论，尚未生效 |
| `已接受` | 已通过决策，项目应遵循 |
| `已废弃` | 曾经有效，现在不再遵循（但未指定替代） |
| `被取代` | 被新的 ADR 取代，应注明是哪一个 |

---

## 决策分级

| 级别 | 适用 | 通过条件 |
|------|------|---------|
| **L3 架构** | 数据模型、模块划分、同步协议、加密方案、插件权限模型 | RFC + 讨论 ≥ 7 天 + 2 名维护者同意 |
| **L4 治理与法务** | 许可证、治理规则、商标 | 核心维护者 2/3 多数 |

详见 [GOVERNANCE.md](../../GOVERNANCE.md)。

- **决策者**：<角色或人名>
- **相关**：<相关文档、Issue、RFC 链接>

## 背景

- 缺点：
- 为什么不选：

- ...

- ...

## 参考

- ...
