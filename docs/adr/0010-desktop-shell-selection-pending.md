# ADR-0010: 桌面外壳技术选型（提议中）

- **状态**：**提议**（尚未决策，需 PoC 后定稿）
- **日期**：2026-09-17
- **决策者**：待定（需 ≥ 2 名维护者同意，L3 决策）
- **相关**：[17 · 技术选型建议](../17-tech-selection.md)、[14 · 性能优化与量化指标](../14-performance-budget.md)

---

## 背景

桌面外壳决定了：包体积、冷启动速度、空闲内存、平台一致性、原生集成能力、开发效率与长期维护成本。

本项目的硬约束（见 [17 · 技术选型建议](../17-tech-selection.md#11-决策前置约束)）中，对外壳影响最大的是：

| 约束 | 目标 |
|------|------|
| 冷启动到可交互 | ≤ 1.2 s（中配） |
| 空闲内存 | ≤ 180 MB |
| Windows 安装包 | ≤ 80 MB |
| 便携版解压后 | ≤ 220 MB |
| 三平台支持 | Windows 必须；Linux/macOS 期望 |
| 零污染 | 便携版零注册表；安装版用户级 |
| 可复现构建 | 需支持 |

这些约束的组合比较严格——尤其是**体积 ≤ 80 MB** 与**空闲内存 ≤ 180 MB**。行业中许多主流方案（自带完整运行时类）在默认配置下难以达到这一量级，需要额外裁剪。

## 候选方案

### 方案 A：系统 WebView 方案
- **优点**：体积小；启动快；内存低；前端生态完整（可用任何 Web 技术栈）；原生侧有系统语言能力
- **缺点**：渲染依赖各平台 WebView 版本，存在差异；需处理版本兼容（尤其旧版 Windows）；原生侧开发门槛较高；调试跨语言边界较麻烦
- **满足约束**：体积 ✅ / 启动 ✅ / 内存 ✅ / 三平台 ✅ / 零污染 ✅（需自行实现安装器）

### 方案 B：自带运行时方案（Electron 类）
- **优点**：渲染完全一致；生态最成熟；开发效率最高；人才最好找；插件机制成熟
- **缺点**：包体积大（默认 80–150 MB，需大量裁剪才可能接近 80 MB）；内存占用高（默认 150–300 MB）；启动偏慢
- **满足约束**：体积 ⚠️ / 启动 ⚠️ / 内存 ⚠️ / 三平台 ✅ / 零污染 ⚠️（需自建安装器）
- **关键待验证**：是否能通过裁剪（移除未用模块、精简运行时、资源压缩）达到体积与内存目标

### 方案 C：原生 UI 框架
- **优点**：性能最好；体积可控；内存最低；原生体验最佳；无障碍支持最好
- **缺点**：三平台需分别开发或依赖跨平台层，成本高；前端生态受限；人才稀少；迭代速度慢
- **满足约束**：体积 ✅ / 启动 ✅ / 内存 ✅ / 三平台 ⚠️（成本）/ 零污染 ✅

### 方案 D：混合（原生外壳 + 嵌入式 Web 视图）
- **优点**：可针对性能敏感部分用原生实现，其余用 Web
- **缺点**：复杂度最高；两套技术栈；维护成本高
- **满足约束**：理论可行，但复杂度风险高

## 待验证的 PoC 项目

在决策前，必须完成以下 PoC 与实测。**每个候选方案至少完成 1 与 2 两项。**

### 必做 PoC

| # | 验证内容 | 测量指标 | 通过判据 |
|---|---------|---------|---------|
| 1 | **空壳应用启动与内存** | 冷启动到窗口可见、空闲内存 | 启动 ≤ 0.8 s（预留业务加载空间）；空闲内存 ≤ 100 MB |
| 2 | **万行列表渲染** | 滚动帧率、内存增量 | ≥ 55 FPS；内存增量 ≤ 120 MB |
| 3 | **打包体积** | 安装包大小、解压后大小 | 安装包 ≤ 80 MB；解压后 ≤ 180 MB |
| 4 | **便携版零注册表** | 运行后注册表快照差异 | 差异 = 0 |
| 5 | **用户级安装可行性** | 是否能做用户级安装 + 自绘安装界面 | 可行 |
| 6 | **原生能力** | 全局快捷键、截图、剪贴板监听、托盘、通知、高 DPI | 全部可用 |
| 7 | **子进程与 IPC** | 能否实现进程隔离与受限 IPC | 可行，IPC 延迟 ≤ 5 ms |
| 8 | **数据库集成** | 嵌入式数据库能否在所选语言下稳定调用 | 可行，10 万行查询 ≤ 50 ms |
| 9 | **可复现构建** | 两次构建产物哈希一致 | 一致（或差异可解释且可控） |
| 10 | **无障碍** | 屏幕阅读器能读出控件 | 基本可用 |

### 辅助验证

| # | 验证内容 | 说明 |
|---|---------|------|
| 11 | 中文输入法兼容 | 无候选框错位、无重复输入 |
| 12 | 高 DPI 缩放 | 100%–300% 无错位 |
| 13 | 三平台构建流水线 | 能否在 CI 中稳定构建三平台 |
| 14 | 团队熟悉度 | 团队学习曲线与可得人才 |
| 15 | 长期维护性 | 项目活跃度、版本升级路径、破坏性变更历史 |

## 评估维度与权重

| 维度 | 权重 | 说明 |
|------|:----:|------|
| 满足硬约束（实测） | **淘汰制** | 不满足直接出局 |
| 包体积 | 高 | 直接关系采纳率 |
| 启动与内存 | 高 | 直接影响核心体验 |
| 开发效率与人才 | 高 | 决定项目推进速度 |
| 三平台成本 | 高 | 决定能否真正跨平台 |
| 长期可维护性 | 高 | 决定项目寿命 |
| 原生集成能力 | 中 | 截图、快捷键等需要 |
| 无障碍支持 | 中 | 承诺项 |
| 可复现构建 | 中 | 承诺项 |

---

## 决策标准

1. **先过淘汰线**：PoC 1 / 2 / 3 / 4 / 7 必须通过。任一未通过即出局。
2. **在通过者中选综合最优**：按上述权重打分。
3. **优先选择能满足约束且开发效率更高的方案**：本项目需要在有限人力下完成大量功能，开发效率权重较高。
4. **允许"条件性选择"**：若某方案在关键项上接近但未达标，可记录为"若能在 X 周内解决 Y 问题则采纳"。

## 决策流程

```
① 发布本 ADR（提议）
       ↓
② 社区与维护者讨论（≥ 7 天）
       ↓
③ 完成 PoC（至少覆盖方案 A 与 C；若团队倾向 B 则一并验证）
       ↓
④ 公布实测数据（附测试环境与脚本）
       ↓
⑤ 更新本 ADR：填入决策与数据，状态改为「已接受」
       ↓
⑥ 若结论与预期不同，记录原因
```
