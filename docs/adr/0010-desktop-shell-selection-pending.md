# ADR-0010: 桌面外壳技术选型（提议中）

- **状态**：**提议**（尚未决策，需 PoC 后定稿）
- **日期**：2026-09-17
- **决策者**：待定（需 ≥ 2 名维护者同意，L3 决策）
- **相关**：[17 · 技术选型建议](../17-tech-selection.md)、[14 · 性能优化与量化指标](../14-performance-budget.md)

---

## 背景

桌面外壳决定了：包体积、冷启动速度、空闲内存、平台一致性、原生集成能力、开发效率与长期维护成本。

本项目的硬约束（见 [17 · 技术选型建议](../17-tech-selection.md#11-决策前置约束)）中，对外壳影响最大的是：

| 约束 | 目标 |
|------|------|
| 冷启动到可交互 | ≤ 1.2 s（中配） |
| 空闲内存 | ≤ 180 MB |
| Windows 安装包 | ≤ 80 MB |
| 便携版解压后 | ≤ 220 MB |
| 三平台支持 | Windows 必须；Linux/macOS 期望 |
| 零污染 | 便携版零注册表；安装版用户级 |
| 可复现构建 | 需支持 |

这些约束的组合比较严格——尤其是**体积 ≤ 80 MB** 与**空闲内存 ≤ 180 MB**。行业中许多主流方案（自带完整运行时类）在默认配置下难以达到这一量级，需要额外裁剪。

---

## 候选方案

### 方案 A：系统 WebView 方案
- **优点**：体积小；启动快；内存低；前端生态完整（可用任何 Web 技术栈）；原生侧有系统语言能力
- **缺点**：渲染依赖各平台 WebView 版本，存在差异；需处理版本兼容（尤其旧版 Windows）；原生侧开发门槛较高；调试跨语言边界较麻烦
- **满足约束**：体积 ✅ / 启动 ✅ / 内存 ✅ / 三平台 ✅ / 零污染 ✅（需自行实现安装器）

### 方案 B：自带运行时方案（Electron 类）
- **优点**：渲染完全一致；生态最成熟；开发效率最高；人才最好找；插件机制成熟
- **缺点**：包体积大（默认 80–150 MB，需大量裁剪才可能接近 80 MB）；内存占用高（默认 150–300 MB）；启动偏慢
- **满足约束**：体积 ⚠️ / 启动 ⚠️ / 内存 ⚠️ / 三平台 ✅ / 零污染 ⚠️（需自建安装器）
- **关键待验证**：是否能通过裁剪（移除未用模块、精简运行时、资源压缩）达到体积与内存目标

### 方案 C：原生 UI 框架
- **优点**：性能最好；体积可控；内存最低；原生体验最佳；无障碍支持最好
- **缺点**：三平台需分别开发或依赖跨平台层，成本高；前端生态受限；人才稀少；迭代速度慢
- **满足约束**：体积 ✅ / 启动 ✅ / 内存 ✅ / 三平台 ⚠️（成本）/ 零污染 ✅

### 方案 D：混合（原生外壳 + 嵌入式 Web 视图）
- **优点**：可针对性能敏感部分用原生实现，其余用 Web
- **缺点**：复杂度最高；两套技术栈；维护成本高
- **满足约束**：理论可行，但复杂度风险高

## 决策标准

1. **先过淘汰线**：PoC 1 / 2 / 3 / 4 / 7 必须通过。任一未通过即出局。
2. **在通过者中选综合最优**：按上述权重打分。
3. **优先选择能满足约束且开发效率更高的方案**：本项目需要在有限人力下完成大量功能，开发效率权重较高。
4. **允许"条件性选择"**：若某方案在关键项上接近但未达标，可记录为"若能在 X 周内解决 Y 问题则采纳"。

## 实测数据（2026-09-17 · PoC-A 系统 WebView 方案）

已完成 **方案 A（系统 WebView）** 的实测。原始数据见 `local-docs/reference/11-poc-results.md`。

### 被测对象

| 项 | 值 |
|----|----|
| 语言 / 工具链 | Rust 1.98.1 / `stable-x86_64-pc-windows-msvc` |
| 窗口 + WebView | `tao` 0.37 + `wry` 0.57（Tauri 的运行时核心，不含 Tauri CLI 与前端构建链） |
| 渲染引擎 | 系统内置 WebView2（Windows 11 自带，**不随包分发**） |
| 构建配置 | `opt-level="z"` + LTO + `codegen-units=1` + `panic="abort"` + `strip` |
| 测试环境 | 16 逻辑核 / 31.8 GB / Windows 11 Pro x64（**高于中配基准，结果是乐观估计**） |

### 结果

| # | 指标 | 实测 | 目标 | 上限 | 结论 |
|:-:|------|------|------|------|------|
| 1 | 冷启动到窗口可见 | **702 ms**（5 次中位） | ≤ 1200 ms | 1600 ms | ✅ 余量 41% |
| 2 | 空闲内存·空白页 | **359.9 MB** | ≤ 180 MB | 250 MB | ❌ 超上限 1.44 倍 |
| 3 | 空闲内存·万行表 | **529.1 MB** | ≤ 180 MB | 250 MB | ❌ 超上限 2.12 倍 |
| 4 | 万行滚动平均帧率 | **174.04 FPS**（P1 90.09） | ≥ 55 FPS | — | ✅ |
| 5 | release exe | **0.454 MB** | 安装包 ≤ 80 MB | 100 MB | ✅ 余量约 176 倍 |
| 6 | 退出残留进程 | **0** | 0 | 0 | ✅ |

### 关键拆分

```
外壳自身成本   = 359.9 MB   ← 架构决定，与业务无关
10 000 行 DOM  = +169.2 MB  ← 可用虚拟滚动消除
```

**结论：内存超标是架构成本，不是实现缺陷。** 即使把所有业务优化到极致（虚拟滚动、懒加载、按需渲染），下限仍在 360 MB 附近。**目标 180 MB 在此方案下无法达成。**

这是本 ADR 最重要的发现：它把"选型问题"变成了"目标问题"。

### 测量方法论事故（记录以免重蹈）

内存测了三版，前两版都错：

| 版本 | 做法 | 结果 | 错因 |
|:----:|------|------|------|
| v1 | 只统计主进程 | 20.4 MB | 严重低估——WebView2 开销在子进程 |
| v2 | 统计全部 `msedgewebview2.exe` | 914.0 MB | 严重高估——该进程被多应用共享，基线已有 6 个属其他程序 |
| **v3** | **PID 差分，只算新增** | **360 / 529 MB** | ✅ 正确 |

**测量多进程应用的内存必须做 PID 差分。** 只看进程名会同时犯低估和高估两种错。

### 未完成的部分

| 项 | 状态 |

## 当前状态

**PoC-A（系统 WebView）已实测完成，结论如上。**

**下一步必须做二选一的决策**（见下节「需要产品负责人决定的事」），然后：

1. 若决定放宽内存目标 → 补测方案 B 作为对照，确认方案 A 是性价比最高的选择，ADR 定稿
2. 若决定保住 180 MB 目标 → 必须做方案 C（原生 UI）的 PoC，并接受三平台开发成本与前端技术栈不可用的代价

## 需要产品负责人决定的事

| # | 问题 | 说明 |
|:-:|------|------|
| **Q1** | **内存目标是否放宽？** | 方案 A 空页即 360 MB。要保住 180 MB 就得换方案 C（原生 UI），代价是三平台各写一套、用不了 HTML/CSS 前端生态、`docs/18` 的设计系统需要重写实现。若放宽到 ≤ 500 MB 空闲（使用态 ≤ 800 MB），方案 A 完全可以胜任，且体积与启动优势巨大。**我的建议：放宽。** 理由是 36 万的体积差距（0.45 MB vs 竞品的 150 MB+）与 700 ms 的启动，对目标用户的价值高于内存数字；而且用户对"装了个软件占多少内存"的感知远低于"启动快不快、包大不大" |
| Q2 | 是否需要方案 C 的 PoC？ | 若 Q1 选择不放宽，则必须做，且要先接受成本 |
| Q3 | 是否接受 VC 运行时依赖？ | 未验证。若目标机器无 VC 运行时可考虑静态链接 CRT（`+crt-static`），体积会略增 |
| Q4 | 是否先放弃 Linux / macOS？ | 可显著降低方案 C 的成本，也让方案 A 的推进更快 |
| Q5 | 体积目标 80 MB 是否还有意义？ | 方案 A 实测 0.454 MB，这个目标已完全失去约束力。可保留作为"不得超标"的红线 |
