# 17 · 技术选型建议（候选方案与取舍）

> **本文档不绑定任何具体技术栈。**
> 它只做三件事：给出候选方案、列出各自优缺点、说明适用条件与评估方法。
> 最终决策由项目维护者通过 ADR 固化（见 [adr/](adr/)）。

---

## 一、选型原则

### 1.1 决策前置约束

任何技术选型都必须先满足以下**硬约束**，不满足的直接淘汰：

| # | 硬约束 | 来源 |
|---|-------|------|
| C1 | 能产出**零注册表写入**的便携版 | 原则 3 零污染 |
| C2 | 能产出**卸载残留为 0** 的安装版 | 原则 3 |
| C3 | 冷启动 ≤ 1.2 s、空闲内存 ≤ 180 MB 可实现 | 原则 10 安静 |
| C4 | 支持**完全离线**运行（含 AI 推理） | 原则 1 本地优先 |
| C5 | 支持数据库的**崩溃一致性**（事务 + WAL 或等价） | 原则 5 不丢数据 |
| C6 | 支持**字段级/库级加密**且密钥不落明文磁盘 | 原则 4 / 6 |
| C7 | 许可为宽松开源（MIT / Apache / BSD / 等价），可用于商业分发 | [15](15-open-source-governance.md) |
| C8 | 可做**可复现构建**，可生成 SBOM | 原则 7 可审计 |
| C9 | 支持**进程隔离**（渲染进程不直访文件系统） | [08](08-privacy-security.md) |
| C10 | 支持三平台（Windows 必须，Linux/macOS 期望） | 目标用户 |

### 1.2 评估维度与权重

| 维度 | 权重 | 说明 |
|------|:----:|------|
| 满足硬约束 | 淘汰制 | 不满足直接出局 |
| 性能可达性 | 高 | 启动、内存、渲染能否达标 |
| 生态与人才 | 高 | 是否有足够开发者愿意参与 |
| 长期可维护性 | 高 | 技术是否有活跃维护、是否有升级路径 |
| 包体积 | 中 | 影响体积指标 |
| 开发效率 | 中 | 影响迭代速度 |
| 平台一致性 | 中 | 三平台体验差异 |
| 学习曲线 | 低 | 影响新人贡献门槛 |

### 1.3 选型流程

```
① 明确约束（本文档 1.1）
② 提出候选（本文档各章节）
③ 打样验证（PoC）—— 每个关键层至少做一次最小验证
④ 测量关键指标（启动/内存/体积/可行性）
⑤ 记录 ADR（含备选方案与拒绝理由）
⑥ 若后续发现不满足约束，走 RFC 重新决策
```

> **原则：不确定时先打样，不要靠"据说"。** 尤其是启动时间与内存占用，必须实测。

## 二、桌面应用外壳

### 2.1 候选方案

| 方案 | 代表实现 | 语言 |
|------|---------|------|
| **A. 系统 WebView 方案** | Tauri、Wails | Rust / Go + 前端 |
| **B. 自带运行时方案** | Electron、NW.js | JS/TS |
| **C. 原生 UI 框架** | Qt、GTK、WinUI/AppKit、Flutter Desktop、.NET MAUI、Compose Multiplatform | C++/C#/Dart/Kotlin |
| **D. 混合方案** | 原生外壳 + 嵌入式 Web 视图 | 混合 |

### 2.2 对比

| 维度 | A 系统 WebView | B 自带运行时 | C 原生 UI |
|------|:-------------:|:-----------:|:---------:|
| 包体积 | **小**（10–30 MB） | 大（80–150 MB） | 中（30–80 MB） |
| 冷启动 | **快** | 中 | **最快** |
| 空闲内存 | **低**（60–120 MB） | 高（150–300 MB） | **最低** |
| 渲染一致性 | 受系统 WebView 版本影响 | **完全一致** | 完全一致 |
| 前端生态 | 极丰富 | 极丰富 | 受限 |
| 原生集成能力 | 强（Rust/Go 侧） | 中（需插件或原生模块） | **最强** |
| 开发效率 | 高 | **最高** | 低 |
| 平台一致性 | 中（需处理 WebView 差异） | **高** | 低（各平台各写） |
| 人才可得性 | 中 | **高** | 低（尤其跨平台） |
| 内存安全 | 高（若用 Rust） | 中 | 视语言 |
| 可复现构建 | **较易** | 较难（依赖多） | 中 |
| 无障碍支持 | 中（依赖 WebView） | 中 | **强** |

### 2.3 适用条件

| 方案 | 适合 | 不适合 |
|------|------|-------|
| **A 系统 WebView** | 对体积与内存敏感、团队有 Rust/Go 能力、能接受 WebView 差异 | 需要像素级一致的渲染、目标平台 WebView 版本过旧（如老旧 Windows） |
| **B 自带运行时** | 追求开发速度与渲染一致、团队以 JS/TS 为主、体积要求宽松 | 体积与内存目标严格（如本文的 80 MB / 180 MB） |
| **C 原生 UI** | 追求极致性能与原生体验、愿意投入更多人力 | 团队小、需要快速迭代、要三平台一致 |

### 2.4 与本项目约束的匹配分析

| 约束 | A | B | C |
|------|:-:|:-:|:-:|
| C3 冷启动 ≤ 1.2 s | ✅ 较易 | ⚠️ 需强优化 | ✅ |
| C3 空闲内存 ≤ 180 MB | ✅ | ⚠️ 需精细裁剪 | ✅ |
| 包体积 ≤ 80 MB | ✅ | ❌ 难达标 | ✅ |
| 三平台 | ✅ | ✅ | ⚠️ 成本高 |
| 开发效率 | ✅ | ✅ | ❌ |
| 可复现构建 | ✅ | ⚠️ | ⚠️ |

**观察**：本项目的体积与内存目标较为严格，方案 A 与 C 更匹配。方案 B 需要额外裁剪才可能达标。

> **不给出结论，交由 PoC 决定。** 建议至少对 A 与 C 做一次最小打样，实测冷启动与空闲内存。

### 3.1 前端框架候选

| 方案 | 体积 | 生态 | 学习曲线 | 虚拟滚动/大列表 | SSR/预渲染 |
|------|:----:|:----:|:-------:|:--------------:|:---------:|
| React | 中 | **最丰富** | 中 | 生态成熟 | 支持 |
| Vue | 中 | 丰富 | **最低** | 生态成熟 | 支持 |
| Svelte / SvelteKit | **小** | 中 | 低 | 需自建或选库 | 支持 |
| Solid | **小** | 小 | 中 | 需自建或选库 | 支持 |
| Preact | **最小** | 中（兼容 React） | 低 | 生态兼容 | 支持 |
| 原生 Web Components | **最小** | 小 | 中 | 需自建 | — |

### 3.2 关键要求（无论选哪个）

| 要求 | 说明 |
|------|------|
| 虚拟滚动 | 必须有成熟方案或可自建 |
| 主题能力 | 支持亮/暗/高对比度，支持运行时切换 |
| 高 DPI | 无模糊、无错位 |
| 无障碍 | 支持 ARIA、焦点管理、屏幕阅读器 |
| 键盘操作 | 完整键盘可达 |
| 大列表性能 | 万行列表 ≥ 55 FPS |
| 按需加载 | 支持代码分割与懒加载 |
| 无强制联网 | 不依赖 CDN 加载关键资源 |
| 字体策略 | 使用系统字体，不内嵌大字体包 |

### 3.3 界面基础组件

| 候选 | 特点 | 注意 |
|------|------|------|
| 自建组件库 | 完全可控、体积最小、风格统一 | 工作量大 |
| 开源组件库（无样式/可定制类） | 起点快、可深度定制 | 需评估体积与可定制性 |
| 开源组件库（成品风格类） | 最快 | 风格受限，可能与本项目"极简克制"定位冲突 |

**建议倾向**：使用**无样式或高度可定制**的基础组件，在其上自建设计系统。因为本项目的视觉定位（极简、克制、品牌一致）与安装向导的品牌一致性要求较高，成品风格库往往需要大量覆盖。

> 注意：**禁止使用任何会加载远程资源的组件（在线字体、图标 CDN、遥测版本）**。

### 3.4 编辑器（笔记/文档/SQL）

| 场景 | 候选方向 |
|------|---------|
| Markdown 笔记 | 成熟的 Markdown 编辑器内核 + 自建 UI |
| 富文本文档 | 成熟的富文本编辑框架 |
| SQL 编辑器 | 代码编辑器内核（支持语法高亮、补全） |

**要求**

- 支持自定义语法高亮与补全数据源
- 支持虚拟滚动（超长文档）
- 体积可控
- 许可宽松

## 四、数据层

### 4.1 数据库引擎候选

| 方案 | 类型 | 事务/WAL | 单文件 | 加密 | 嵌入式 | 许可 |
|------|------|:-------:|:------:|:----:|:------:|------|
| SQLite（及兼容实现） | 关系型 | ✅ 强 | ✅ | 需扩展或自建 | ✅ | 公共领域 |
| DuckDB | 分析型 | ✅ | ✅ | 部分支持 | ✅ | MIT |
| 自研存储引擎 | 自定 | 需自建 | ✅ | 自建 | ✅ | — |
| 内嵌键值库（如 RocksDB / LMDB 等） | KV | 各自不同 | ✅ | 视实现 | ✅ | 各自不同 |
| 内嵌文档库（如 各嵌入式文档 DB） | 文档型 | 各自不同 | ✅ | 视实现 | ✅ | 各自不同 |

### 4.2 评估要点

| 要点 | 说明 |
|------|------|
| **事务与 WAL** | 必须支持 ACID 与 WAL（或等价崩溃一致性机制），且可配置同步级别为"每次提交 fsync" |
| **单文件** | 便于携带、备份、迁移（这是产品核心设计） |
| **崩溃一致性验证** | 是否有成熟的崩溃测试工具与实践 |
| **中文支持** | 中文表名/字段名/全文检索分词 |
| **全文检索** | 内置 FTS 或可外挂 |
| **JSON 支持** | 原生 JSON 类型便于半结构化数据 |
| **加密** | 页级加密支持情况（原生或成熟扩展） |
| **性能** | 十万行量级查询、索引、JOIN 的实际表现 |
| **生态工具** | 第三方工具能否直接打开该文件（可迁移性） |
| **许可** | 宽松开源 |
| **长期维护** | 项目活跃度与稳定性 |

### 4.3 典型取舍

| 取舍 | 说明 |
|------|------|
| 关系型 vs 文档型 | 关系型更符合"办公数据"的心智（表、字段、关系）；文档型更灵活但查询能力弱 |
| 单引擎 vs 多引擎 | 单引擎降低复杂度；多引擎（OLTP + OLAP）性能更好但维护成本高 |
| 用现成 vs 自研 | 强烈建议用现成成熟引擎。**自研存储引擎的风险极高**，除非有充分理由与长期投入 |
| 内置 FTS vs 外挂索引 | 内置简单；外挂（如独立全文索引库）能力更强但需保证一致性 |

> **强烈建议**：数据层不要自研。存储引擎的崩溃一致性、并发控制、加密是深水区，成熟方案已解决这些问题。自制轮子在这个层面几乎必然是负债。

### 4.4 加密方案

| 层次 | 候选方向 | 注意 |
|------|---------|------|
| 库级加密 | 引擎原生加密扩展 / 自建页级加密层 | 避免自研密码算法；使用成熟 AEAD |
| 字段级加密 | 应用层加密后再写入 | 需处理索引问题（加密字段无法直接索引） |
| 备份加密 | 应用层 AEAD | 独立密钥 |
| 传输加密 | TLS 1.3 + 应用层 E2EE | 使用成熟库 |

**密码学红线**

| ❌ 禁止 | 理由 |
|--------|------|
| 自研加密算法 | 必然有缺陷 |
| 自研密钥交换协议 | 同上 |
| ECB 模式 | 泄露结构信息 |
| 固定 IV / Nonce | 灾难性 |
| 用哈希代替 KDF | 暴力破解成本过低 |
| 弱随机数源 | 密钥可预测 |
| 明文存储密钥 | 加密形同虚设 |

**推荐参数方向**

| 项 | 建议 |
|----|------|
| 对称加密 | AES-256-GCM 或 ChaCha20-Poly1305 |
| 密钥派生 | Argon2id（内存 ≥ 64 MB、迭代 ≥ 3）或 scrypt 等价强度 |
| 密钥交换 | X25519 ECDHE |
| 签名 | Ed25519 |
| 哈希 | SHA-256 / SHA-3 |
| 随机数 | 操作系统 CSPRNG |

> 具体参数在实现时依据当时硬件能力与安全建议确定，并记录在数据文件头以支持未来升级。

## 五、本地 AI 推理

### 5.1 候选方向

| 方案 | 说明 | 体积 | 硬件要求 |
|------|------|------|---------|
| 轻量本地推理运行时（CPU 优先） | 内嵌小型推理引擎，纯 CPU | 小（10–40 MB） | 无 |
| GPU 加速推理运行时 | 支持 CUDA / Metal / Vulkan 等 | 大（100–500 MB） | 需 GPU |
| 系统内置 AI 能力 | 使用操作系统提供的本地模型接口 | 最小 | 依赖平台 |
| 用户自建本地服务 | 对接用户自己运行的推理服务 | 最小 | 用户自备 |

### 5.2 评估要点

| 要点 | 说明 |
|------|------|
| **完全离线** | 模型加载与推理不得需要联网 |
| 模型可替换 | 不锁定特定模型格式或厂商 |
| 量化支持 | 支持量化模型以降低内存与提高速度 |
| CPU 可用性 | 无 GPU 时仍可用（这是大多数用户） |
| 内存管理 | 支持显式卸载模型、限制内存上限 |
| 许可 | 运行时与模型许可均需宽松/可商用 |
| 跨平台 | 三平台支持情况 |

### 5.3 模型选择维度

| 维度 | 说明 |
|------|------|
| 参数规模 | 小（1–3B）用于摘要/分类；中（7–14B）用于推理 |
| 量化级别 | 4-bit / 5-bit / 8-bit，权衡质量与体积 |
| 中文能力 | 必须评估中文理解与生成质量 |
| 结构化输出 | 生成 SQL / JSON 的可靠性 |
| 许可 | 模型许可是否允许商用与再分发 |
| 体积 | 影响下载门槛 |

### 5.4 关键设计

| 设计 | 说明 |
|------|------|
| **可插拔后端** | 抽象统一接口，允许替换推理引擎与模型 |
| **按需加载** | 不使用时完全释放（内存回到基线） |
| **按任务选模型** | 不同任务用不同规模的模型 |
| **降级策略** | 目标模型不可用时降级到已安装的最小可用模型 |
| **模型校验** | 下载后校验哈希，不匹配拒绝加载 |
| 推荐"不锁定单一模型" | 模型迭代快，锁定会成为负担 |

### 5.5 OCR 与语音转写

| 能力 | 候选方向 |
|------|---------|
| OCR | 成熟的本地 OCR 引擎（支持中英文）；AI 增强用于手写/复杂版式 |
| 语音转写 | 本地转写模型（如基于 Whisper 系的实现） |
| 嵌入模型 | 本地嵌入模型（用于语义搜索） |

**要求**：全部本地运行、语言包按需下载、下载后校验、可离线使用。

## 六、备份、加密与同步

### 6.1 备份实现方式

| 方案 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| 引擎自带备份 API | 使用数据库的在线备份能力 | 一致性有保证 | 依赖引擎能力 |
| 文件级快照 + WAL | 复制文件并记录 WAL 位置 | 可控 | 需处理一致性 |
| 逻辑导出（SQL dump） | 导出为 SQL | 格式开放 | 慢、体积大、不含附件 |
| 块级增量 | 跟踪变更块 | 增量快、体积小 | 实现复杂 |

**建议方向**：**引擎内置备份能力 + 页面变更跟踪**（若引擎支持）。避免纯文件复制（一致性风险）。

### 6.2 压缩与加密顺序

| 顺序 | 压缩率 | 安全性 | 建议 |
|------|:------:|:------:|------|
| 先压缩后加密 | 高 | 好 | ✅ 推荐 |
| 先加密后压缩 | 无（密文不可压缩） | 好 | ❌ 无意义 |

> **注意**：先压缩后加密会通过密文长度泄露压缩率信息（可能揭示数据熵）。对本项目的备份场景，这个泄露可接受；若用户需要极致隐私，可提供"先加密后压缩"选项（实际等于不压缩）。

### 6.3 同步方案（可选能力）

| 方案 | 说明 | 适用 |
|------|------|------|
| 局域网直连 | 同网段点对点 | 手机远程 |
| 自托管中继 | 用户自己的服务器转发密文 | 跨网络远程 |
| 文件级同步（用户自己的网盘目录） | 把数据目录放在用户自己的同步目录 | 简单，但有并发风险 |
| CRDT / OT | 冲突自动合并 | 复杂度极高，与"单主端"设计不符 |

**建议**：坚持**单主端 + 远程访问**模型，不做双向同步。若未来需要多桌面同步，"文件级同步 + 版本冲突提示"是成本最低的路径。

## 七、进程模型与打包

### 7.1 进程隔离方案

| 方案 | 说明 | 适用 |
|------|------|------|
| 多进程 + IPC | 主进程仲裁，各功能独立进程 | 桌面应用常规做法 |
| 子进程 + 受限 IPC | 插件、数据库、AI 各自独立进程 | 插件与重任务 |
| 沙箱容器 | 系统级沙箱 | 过重，桌面场景不必要 |

**要求**

| 要求 | 说明 |
|------|------|
| 渲染层不直访文件系统 | 必须经主进程能力接口 |
| 能力接口逐次鉴权 | 不信任调用方会话状态 |
| 崩溃隔离 | 子进程崩溃不影响主进程 |
| 资源限额 | 每个子进程有 CPU/内存上限 |

### 7.2 打包与安装器

| 需求 | 候选方向 |
|------|---------|
| 便携版 | 直接压缩包，无安装器 |
| Windows 安装器 | 支持无管理员权限安装、可自绘界面、可写最小注册表、支持静默安装参数 |
| Linux | AppImage（零污染首选）+ deb/rpm（可选） |
| macOS | .dmg + .app；提供卸载脚本 |
| 自绘安装界面 | 需选可定制 UI 的安装器方案，或自建安装器 |

**打包要求**

| 要求 | 说明 |
|------|------|
| 无管理员权限安装 | 默认用户级安装（`%LocalAppData%`） |
| 可写出 manifest | 记录创建的每一项，供卸载精确清理 |
| 支持自绘界面 | 品牌一致性要求 |
| 支持静默安装 | 企业部署 |
| 支持签名 | 三平台签名 |
| 可复现 | 相同输入产出相同哈希 |

> **关于自绘安装界面**：多数安装器框架的自绘能力有限。若品牌一致性要求高，可考虑**自建安装器**（用应用同一套 UI 技术栈），代价是开发成本。这是一个需要权衡的决策点。

## 十、选型反模式（明确避免）

| ❌ 反模式 | 为什么危险 |
|----------|-----------|
| 因为"流行"而选型 | 流行度与项目约束无关 |
| 因为"想学"而选型 | 项目不是学习平台 |
| 未做 PoC 就定选型 | 关键指标可能完全不达标，返工成本极高 |
| 同时引入多套同类框架 | 复杂度与体积双输 |
| 引入会静默联网的依赖 | 直接违反隐私承诺 |
| 引入许可不明或 copyleft 依赖 | 合规风险 |
| 自研存储引擎 / 密码学 | 深水区，成熟方案已解决 |
| 依赖 `latest` 版本 | 不可复现 |
| 依赖体积巨大的单一库解决小问题 | 体积膨胀 |
| 选型后不做记录 | 后人无法理解决策原因，容易反复推翻 |
